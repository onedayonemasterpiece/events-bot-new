# Связный рассказ в VK-дайджесте экскурсий: передача исполнителю

Дата: 16 ноября 2026 года. Автор изменения и последующего разбора — Claude (Fable). Исполнитель — Codex с доступом к серверу, ключам модели и публикатору ВК.

## Зачем это и в каком состоянии

Владелец хочет, чтобы текст поста к визуальному дайджесту экскурсий был живым связным рассказом в слегка блогерской манере, а не списком «название — ссылка». Требования собраны в [треде Slack](https://mira-projects.slack.com/archives/C0C9LS6L3J8/p1794825818667009) и в [разборе выпуска №349](https://github.com/onedayonemasterpiece/events-bot-new/blob/7fa073e4abd2ee2e9e0eb4d8988af1487e7d1987/docs/features/guide-excursions-monitoring/vk-rich-text-review-2026-11-16.md). Прочитайте оба целиком до начала работы.

В ветке `feature/guide-vk-narrative-20261116` (от `main@87b53f7eb`) лежит первая реализация. Она проверена только тестами с заглушкой модели. **Ни одного настоящего ответа модели ещё никто не видел**: у автора нет доступа к ключам и серверу. Владелец посмотрел написанный вручную образец и оценил его как «стало лучше, но не идеально». Дальше текст отлаживается на нескольких настоящих дайджестах — это и есть ваша задача.

От вас нужны три вещи:

1. прогнать writer на нескольких реальных наборах экскурсий и опубликовать результаты в тестовое сообщество;
2. вернуть материалы прогонов в виде, описанном ниже, чтобы по ним можно было править инструкцию модели;
3. исправить то, что сломается механически (ошибка вызова, формат, длина). Литературные правки инструкции по своему вкусу не вносите: их делает автор по вашим материалам. Если видите очевидную правку — запишите предложение в отчёт.

## Упоминания: осторожно с настоящими гидами

Модель помечает имена как `[[номер|имя в падеже]]`. Сборщик превращает пометку в `[id…|имя]` только для роли «Гид» с личным VK ID и только при `GUIDE_VISUAL_DIGEST_VK_MENTIONS=1`. По умолчанию выключено.

**Не включайте этот флаг на настоящих строках, даже в тестовом сообществе.** Упоминание уходит человеку уведомлением независимо от того, где опубликован пост, а владелец разрешил тестировать только на двух получателях: `id868977531` («Полюбить Калининград») и `id858363572` (Инна Никифорова). Для проверки упоминаний в рассказе подмените в строках перед сборкой `participant_medallions[].owner` на эти два ID и только тогда включайте флаг. Массовое включение — отдельное решение владельца.

Если квота позволяет, наборы A и F повторите на более сильной модели (`GUIDE_DIGEST_WRITER_MODEL=gemini-3.6-flash` на время прогона, штатные настройки не менять). ### Как снять материалы одного прогона

Запускать в окружении бота, строки брать тем же путём, что и ежедневный выпуск:

```python
import json, time
from guide_excursions import visual_digest as vd, digest_writer as dw

async def capture(db, ids, issue_id):
    async with db.raw_conn() as conn:
        await vd._enable_row_factory(conn)
        rows = await vd._fetch_rows_by_ids(conn, ids)
    from source_avatars import prepare_guide_avatars
    await prepare_guide_avatars(rows, db)
    payload, mention_ids = vd._vk_narrative_payload(rows)
    started = time.monotonic()
    narrative = await dw.ask_vk_narrative(payload, issue_id=issue_id)
    seconds = round(time.monotonic() - started, 1)
    import main
    final = await vd.build_visual_digest_vk_text(rows, issue_id=issue_id, db=db, vk_api_fn=main._vk_api)
    return {"ids": ids, "issue_id": issue_id, "model": dw.GUIDE_DIGEST_WRITER_MODEL, "seconds": seconds,
            "payload": payload, "narrative": narrative, "final_text": final, "chars": len(final)}
```

`build_visual_digest_vk_text` делает второй вызов модели, поэтому `narrative` и `final_text` — два разных ответа. Это полезно: видно разброс на одном входе. Если хотите одинаковый текст, соберите пост через `vd._assemble_vk_narrative` из уже полученного `narrative`.

Когда `narrative` равен `None`, найдите в логе строку `guide_vk_narrative issue_id=… outcome=…` и приложите её: там причина отказа.

## Что вернуть

Один файл `docs/features/guide-excursions-monitoring/vk-narrative-runs-2026-11.md` в этой же ветке. Автор разбора не читает `/home/dev/artifacts`, поэтому всё нужное для чтения должно быть в файле; сырые JSON и логи положите в обычный управляемый каталог артефактов и укажите путь.

На каждый прогон:

- набор, `issue_id`, подход к зачину, модель, время вызова, число знаков итогового поста, входные и выходные токены, если клиент их отдаёт;
- **вход модели целиком** (`payload`) — по нему видно, чего модели не хватило;
- **сырой ответ модели** (`narrative`) с пометками `[[…]]`;
- **итоговый текст поста** как он ушёл бы в ВК;
- для опубликованных — ссылка на пост и результат обратного чтения через API.

Один раз на весь отчёт:

- прежний компактный текст для набора A, для сравнения;
- снимок с телефона: как пост выглядит в ленте до раскрытия (видны ли «ЭКСКУРСИИ», период и хук) и после;
- нажимается ли телефон в формате `+7 (911) 858-58-49` в приложении ВК; если нет — проверить `+79118585849`;
- ведёт ли короткая ссылка записи на нужную форму;
- ваши наблюдения списком: предложения с выдуманным фактом, с личным посещением, со словом «встреча», со штампом, с неверной ролью. Цитируйте предложение и указывайте, чего нет во входе. Оценку «нравится / не нравится» не пишите — нужны конкретные места.

Отдельно ответьте на вопрос владельца из треда: **хватает ли сохранённого материала для богатого текста.** По каждому набору назовите экскурсии, у которых во входе не оказалось ни маршрута, ни темы, ни сведений о гиде, и проверьте по исходному посту, были ли они там. Если были — укажите шаг, где потерялись (извлечение, обогащение, срез текста, связь с постом).

## Известные открытые вопросы

- **Запись на 21 ноября.** У строки 747 в базе `booking_url` ведёт на `vk.com/varja39`, хотя в анонсе общая форма. Из-за этого у двух дат «Зелёных историй» разные контакты и сборщик покажет их отдельными строками. Это ошибка извлечения или выбора канонического варианта; место исправления предложено в §9.2 разбора. Исправлять отдельным изменением, не внутри writer.
- **Ферма.** Связь Марии Морозовой с экскурсией 763 в первоисточнике не подтверждена, но в базе она записана гидом, и модель её назовёт. Нужен источник роли либо решение, что имя убирается.
- **Длина.** Проверки длины перед `wall.post` нет: при пяти экскурсиях и потолке 2400 выходных токенов пост заведомо короче предела ВК. Если на наборе F получится иначе — это находка для отчёта, а не повод сразу добавлять обрезку.
- **Модель.** Отдельной настройки модели для рассказа нет намеренно. Добавлять её стоит только если прогоны покажут, что одна модель не подходит обоим writer.

## Ограничения

- Применить [devserver-simplicity](https://github.com/onedayonemasterpiece/codex-devcoveer-mcp/blob/main/skills/devserver-simplicity/SKILL.md): без новых состояний, флагов, очередей, повторов, второго публикатора и повторного извлечения. Каждая добавленная проверка — только на сбой, который вы наблюдали в прогоне, со ссылкой на него.
- Смысл текста правится инструкцией модели, а не регулярными выражениями по словам (`AGENTS.md`, LLM-first). Инструкция остаётся общей: имён, мест и оборотов из конкретных выпусков в ней быть не должно (`docs/llm/request-guide.md`).
- Не менять визуальную карточку: она в отдельном черновом PR 1026.
- Перед запуском: `python3 scripts/inspect/audit_google_ai_provider_paths.py`, ожидается `unapproved=0` и `allowlisted_debt=0`.
- Тесты: `pytest tests/test_guide_visual_digest.py tests/test_guide_local_llm_timeout_contract.py -q`. На 16 ноября — 18 и 2 пройдено.
- В отчёте честно разделите: что запущено и опубликовано, что только сгенерировано, что не удалось и почему.
