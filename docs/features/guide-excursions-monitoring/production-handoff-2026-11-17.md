## Почему отсутствовали репосты и истории

- Репосты. Кампания №14 пользовалась датой общего выпуска и выбирала только максимальный ID за текущий день. Так поздняя публикация №350 выпала после появления №351. У №351 старая ссылка оказалась зафиксирована ещё на стадии подготовки репоста. Теперь штатный обработчик учитывает дату VK-квитанции и ожидающей отправки, а у ещё не отправленного репоста заменяет ссылку при перевыпуске. Для №351 оба подготовленных назначения перевязаны к 414. У «Афиши» сохранён план 12:28:17 — через 35 минут 29 секунд после новой записи. Успешные отправки сохраняют исходный ключ. Проверка доставки — по `copy_history` записи в группе назначения.
- История №350. При ручной публикации оригинала в квитанции не было задания на историю. 17 ноября опубликована история по фактической карточке `photo-238875824_457239724`. Проверены нативные ID и кнопка, ведущая на 411.
- История утреннего №351. Включённый воркер дважды получил при загрузке картинки ответ без `upload_result`. Ответы тех двух попыток не сохранились целиком. Позднее в непубликующей парной проверке одного JPEG на одном аккаунте загрузчик вернул HTTP 200 с внутренней ошибкой VK 1 для прежней подписи и HTTP 500 с HTML для штатного значения more. Тот же файл с more ранее успешно загрузился и вышел в истории. Точная причина исходных ответов VK не установлена. Следующая попытка обычного воркера удалась, и VK подтвердил историю 456239102 с кнопкой на 413. При немедленной публикации исправленного №351 загрузка снова вернулась без `upload_result`. До `stories.save` дело не дошло. Этот путь раньше записывал только ошибку и пропускал повторную попытку. Новая история 456239104 опубликована в 11:54:48, с родной карточкой нового выпуска и проверенной нативной кнопкой «Ещё» на 414. VK вернул срок показа до 18 ноября, 11:54:48. В [#1058](https://github.com/onedayonemasterpiece/events-bot-new/pull/1058) немедленная отправка при ошибке до сохранения теперь оставляет историю штатному таймеру. Он повторяет загрузку после 15 минут. Если ответ на отправленный stories.save потерян, повторное сохранение не запускается: проверить ленту группы по ссылке на оригинал. Для кнопки в обеих ветках используется проверенное значение more («Ещё»).
- Для перевыпуска вызвана только ВК-ветка. Утренние отправки Telegram сохранены: [первая](https://t.me/wheretogo39/534), [вторая](https://t.me/youwillsee39/553). Отдельная утренняя ошибка MAX не входит в результат этой операции.

## Контроль следующего штатного запуска

1. 18 ноября в 10:30 по Калининграду проверить `ops_run.kind='guide_visual_digest'` и фактический состав нового выпуска. В `/healthz` должны быть `ready=true`, `tasks.daily_scheduler=ok` и `scheduler.guide_visual_digest=ok`.
2. Основную запись VK планируют с задержкой 600 секунд от момента отправки. После её выхода проверить постоянный URL и фото через `wall.get`. ID отложенной и вышедшей записей могут различаться. Для каждого `[id…|имя]` подтвердить роль и профиль. Не требовать двух тегов у каждого выпуска — их количество задаёт фактический состав.
3. История отложенного поста должна стать доступна к отправке через 900 секунд от запланированной публикации. Воркер проверяет очередь каждые пять минут. Проверить новую историю через `stories.getById` и её `link.url`, срок показа — по `expires_at`.
4. Кампания №14 проверяет назначения раз в пять минут. Смотреть фактический `due_at` в журнале каждого назначения, затем проверить `copy_history` у опубликованного репоста. Для «Афиши» целевой интервал — 30–180 минут после выхода оригинала. Для двух направлений одного выпуска учитывается разнос. 18 ноября отдельно проверить доступность «Анонсов» по их трёхдневному правилу. Для диагностики достаточно прочитать журнал и VK, повторная отправка по уже опубликованному ключу не требуется.

Рабочая SQLite — `/data/db.sqlite` в сервисе `events`. Значения времени в журнале приводить к UTC+2 для сопоставления с таблицей. Запрос только для чтения:

```sql
SELECT issue_id, provider, target_id, state,
       json_extract(payload_json, '$.due_at') AS due_at,
       json_extract(receipt_json, '$.source_url') AS source_url,
       json_extract(receipt_json, '$.post_urls[0]') AS published_url
FROM guide_visual_delivery
WHERE issue_id >= 350 AND provider IN ('vk', 'promo_vk_repost')
ORDER BY issue_id, provider, target_id;
```
