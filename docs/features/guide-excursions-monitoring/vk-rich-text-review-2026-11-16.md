# Богатый текст VK дайджеста экскурсий: материалы для Opus и Falble

Срез: 16 ноября 2026 года. Документ для анализа и последующей доработки существующей реализации. Это постановка и собранные доказательства, а не заключение Opus или Falble: их анализ в рамках подготовки этого документа не запускался.

Основной источник требований — [полный Slack тред владельца «Связанный текст об экскурсиях в дайджесте экскурсий в Вк»](https://mira-projects.slack.com/archives/C0C9LS6L3J8/p1794825818667009), включая дополнения о хуках, разнообразии подачи, шортере, телефонах, глаголах движения и хештегах. Другой контекст — текущий native диалог владельца о качестве дайджеста и [исходный тред контроля импорта](https://mira-projects.slack.com/archives/C0C9LS6L3J8/p1793741851400999).

## 1. Цель и фактическое состояние

Читатель сообщества «Ух ты, Калининград!» должен понять, чем интересны предстоящие экскурсии, кто их ведёт, чем отличаются маршруты и как записаться. Сейчас краткий VK список ссылок почти не передаёт эти сведения. Владелец поручил сделать связный, содержательный литературно-маркетинговый рассказ. Предположение, что это увеличит органический охват VK, — продуктовая гипотеза владельца; измерения прироста охвата не проводились.

| Объект | Что сделано / что осталось |
| --- | --- |
| Штатный VK текст | В коде работает короткий механический builder: вступление, названия, ссылки/телефоны, хештеги. Автоматический writer длинного связного VK рассказа не реализован. |
| Предыдущие наработки | Есть LLM writer коротких copy-blocks, hooks, fact packs, профили гидов и семантическая редактура. Их нужно использовать и исследовать историю, а не писать всё с нуля. |
| Тест богатого рассказа | Координатор подготовил один текст и опубликовал в разрешённом sandbox. API прочитан обратно; 2211 символов, картинка 1080×1350. Это разовый редакционный прототип, не результат нового production writer. |
| Тест mention | Отдельный пост с двумя разрешёнными тестовыми аккаунтами сохранён VK. API вернул конструкции упоминаний; UI-кликабельность и получение уведомления адресатом не приняты. |
| Production | Новый длинный writer и массовые mentions не включены. Изменение визуальной компоновки — отдельный draft PR 1026, не входит в эту задачу. |

## 2. Требования владельца к тексту

1. Это **дайджест экскурсий по Калининградской области от «Ух ты, Калининград!»** — принадлежность подборки должна читаться прямо в тексте.
2. Первые две строки дают сильный общий хук: зачем открыть продолжение. Слово «ЭКСКУРСИИ» и даты сохранить. Хук брать из содержания, а не из generic обещаний.
3. Для каждой экскурсии — развёрнутый самостоятельный абзац; между экскурсиями — естественные смысловые переходы. Названия заметны через **КАПС**.
4. Текст от первого лица, с эмоцией и личным отношением. Позднее уточнение владельца ограничивает этот голос: **не создавать впечатления, что автор всё посетил или сам обязательно поедет**. Пример владельца: «А в воскресенье можно посетить осетровую ферму…». Нужен голос редакции, а не выдуманный отзыв очевидца.
5. Писать естественно, по правилам сторителлинга и маркетинга, без нейросетевых клише. Не превращать всё в одинаковый шаблон. Между выпусками допустимы разные редакционные подходы; способ получить разнообразие нужно предложить, а не заранее вводить новые режимы/состояния.
6. Дать полезную информацию о гиде, его подходе и сильных сторонах **только по материалам источников/профиля**. Если фактов мало, не выдумывать регалии, опыт, личные качества или отзывы.
7. Не повторять одну мысль в разных строках. Краткий текст картинки и длинный текст поста имеют разные задачи; просто растянуть заголовок повторами — не улучшение.
8. Использовать существующий `main_hook` и другие содержательные формулировки, когда их доказательства относятся к этой экскурсии. Примеры из карточки: «С музыкой, играми и квестами», «По местам, куда обычно не водят туристов», «С историей людей и темой природы», «С дегустацией эксклюзивных закусок». Само присутствие формулировки на карточке не заменяет проверку первоисточника и области применимости.
9. Сохранять даты, время, фактическую цену и понятную запись. Не придумывать неизвестное время/цену/транспорт. Телефон нужно проверить на реальную кликабельность в VK.
10. **Все внешние ссылки сокращать через VK шортер; ссылки на сам VK не сокращать.** Уже есть штатный helper, использовать его.
11. Оставить немного уместных хештегов, особенно городских. Они были в прежней короткой версии и не должны потеряться при улучшении.
12. Уместиться в фактический лимит выбранного VK транспорта. В проверенном MCP описании был лимит 4096 символов; это не доказательство универсального лимита нативного VK wall. Проверить ограничение конкретного writer → publisher пути, учитывать ссылки/mentions/хештеги при расчёте длины.

### Глаголы движения: важное уточнение из Slack

Для подтверждённой пешеходной экскурсии владелец просит «пойдём», «пройтись» и аналоги; для автобусной/железнодорожной — «поедем». Даже без названного вида транспорта, если источник явно описывает выезд из Калининграда в другой населённый пункт/за город, владелец разрешает формулировку «поедем» и синонимы поездки.

Это редакционная формулировка по установленному направлению поездки, **не разрешение записывать `transport=bus` в факты или рисовать автобусный значок по географии**. Не путать «открытая/сборная группа» со способом передвижения. Согласовать это с ограничением первого лица: «можно поехать» не обещает личного участия автора.

## 3. Факты, роли и сохранённые данные

Владелец подозревает, что для богатого текста сохраняется слишком мало исходного материала. Это **гипотеза для проверки**, а не установленная причина. Нужно проследить один набор первоисточников через extraction → сохранение → обогащение → payload writer → VK текст и назвать конкретное место потери, если оно есть.

Роли различать: автор/источник поста, гид, организатор/проект. Гид и организатор могут совпадать, могут быть разными; возможны два гида и совместные проекты. Примеры владельца: Ноза Усманова и проект «80 лет единства»; Татьяна Удовенко и Amber Fringilla. Название публикующего сообщества само по себе не доказывает, кто ведёт конкретный маршрут. Победа команды в конкурсе не означает персональную награду каждого её гида.

Полезные существующие данные:

| Данные | Для чего исследовать |
| --- | --- |
| `summary_one_liner`, `digest_blurb` | Уже извлечённое/написанное краткое содержание. Это не автоматически полный материал для длинного рассказа. |
| `fact_pack_json` / `fact_pack`, `main_hook`, evidence | Содержательные факты, их происхождение и хук. Проверять scope: программа / маршрут / конкретная дата. |
| `route_summary`, `meeting_point`, `duration_text` | Тема, маршрут и логистика; не переносить из другого маршрута того же автора. |
| `guide_names`, `organizer_names`, профили | Идентичность и подход гида; отдельная идентичность проекта. |
| `date`, `time`, `price_text`, `seats_text`, `booking_url`, `booking_text` | Практическая ценность и запись, без выдумывания пустых полей. |
| `guide_monitor_post`, `guide_occurrence_source`, `guide_fact_claim` | Первичный пост, связи с датированными экскурсиями, происхождение утверждений. |
| `guide_template` и rollup фактов | Накопленная история маршрута, hooks и профили; проверить применимость к текущей дате. |

`search_digest` и `short_description` владелец назвал как аналогию из событий, а не как подтверждённые названия полей guide path. Не создавать их копии без исследования текущей схемы.

### Обязательная защита от переусложнения

Применить [devserver-simplicity](https://github.com/onedayonemasterpiece/codex-devcoveer-mcp/blob/main/skills/devserver-simplicity/SKILL.md), [LLM request guide](../../llm/request-guide.md) и текущий `AGENTS.md` репозитория.

Человек и действие: читатель каждого VK выпуска должен получить содержательную подборку вместо короткого списка ссылок. Наблюдаемый дефект: `build_visual_digest_vk_text` не использует доступный rich copy/facts для связного текста; v1 имеет перечисленные редакционные недостатки. Числовой бюджет строк владелец не задавал; нужен минимальный diff с фактическим net lines, без искусственно придуманного лимита.

Не добавлять новую очередь, cron, recovery loop, слой состояний, обход лимитов/ключей, независимый publisher, вторую базу фактов или повторный extraction ради удобства writer. Один различающий regression case: текущие четыре реальные occurrences на входе → связный grounded рассказ с датами, без выдуманного автобуса/личного посещения и без утраты записи. До реализации сравнить с текущим коротким builder и v1; после — прогнать тот же набор через обычный writer и sandbox publisher.

В PR реализации приложить таблицу:

| Добавленный элемент | Наблюдаемый дефект | Проверенный существующий механизм и почему его недостаточно | Оставлен / удалён |
| --- | --- | --- | --- |

Указать net production lines, что сознательно не добавлено, что удалено, как читатель увидит результат. Для этого документа production lines = 0, runtime механизмов не добавлено.

## 8. Приёмка будущей доработки

- Реальный обычный writer создаёт связный VK текст из выбранных системой экскурсий. Разовая ручная редактура не выдаётся за автоматизацию.
- Сохраняются все выбранные даты и контакты, CAPS названия, брендинг, первый хук и немного городских хештегов. Две встречи одного маршрута не теряются при редакционном объединении.
- Каждое конкретное утверждение связано с подходящими source/profile facts; в тексте нет выдуманных транспорта, времени, цены, наград и личного посещения.
- Есть конкретная ценность о гидах, когда факты доступны; при бедном источнике текст короче, а не фантазийнее. Программные преимущества не приписаны каждому маршруту автоматически.
- На одном и том же source bank выполнено сравнение до/после, включая negative controls: нет транспорта; общий project claim; два гида; guide+организатор; неизвестная цена/время; несколько дат; длинный набор с ограничением длины; телефон вместо booking URL.
- Ссылки вне VK проходят существующий шортер; штатные VK ссылки, receipts и cadence обычных сообществ сохранены. Телефон проверен нажатием в реальном UI.
- Результат обычной генерации опубликован только в разрешённый sandbox, прочитан обратно, текст и фото просмотрены. Сохранённые bracket mentions отдельно от проверенного UI mention и отдельно от полученного адресатом уведомления.
- Массовые mentions остаются выключены до отдельного решения владельца. Layout PR 1026 не попадает в text rollout.

Приёмка rich text, приёмка mentions и доставка визуальной компоновки — разные результаты. Зелёные тесты transport extraction или публикация координаторского v1 не закрывают эти три работы.
