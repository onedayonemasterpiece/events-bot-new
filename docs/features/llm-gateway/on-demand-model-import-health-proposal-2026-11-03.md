# Events Bot: тихие LLM-уведомления и диагностика через dot/MCP по запросу

**Статус:** предложение на 2026-11-03. Ниже описано целевое поведение; оно НЕ реализовано этим документом.  
**Цель владельца:** резко уменьшить сообщения в eventsBot, не пропустить реальный пожар и в любой момент спросить dot, почему мало импортировано событий, какие модели/квотные проекты/ключи испытывают проблемы и надо ли переносить нагрузку.

## Решение

**Не делать** отдельный дашборд, регулярный отчёт каждые N часов, cron для сводок, новую базу инцидентов, искусственные запросы к моделям ради health-check или отдельный сервис мониторинга.

1. **Тихий штатный режим.** Ошибки отдельных LLM-вызовов (500, 503, краткий 429, RPM/TPM, переход на fallback) остаются в структурированных логах и существующем ledger, но не отправляются человеку как отдельные сообщения.
2. **Уведомление только о результате, требующем действия.** Существующие итоги импорта/мониторинга сохраняются; одна заметная тревога — если существенный запуск действительно не завершён, остановлен/просрочен, нет работоспособного разрешённого маршрута, или остались технические terminal без автоматического повтора. Нельзя называть отдельный provider-error CRITICAL-отказом импорта, пока дальнейшие fallback ещё могут завершиться успешно. Одну и ту же неустранённую проблему не повторять поминутно; при восстановлении можно сообщить однократно.
3. **Главная пользовательская подсказка уже существует:** сколько новых событий появилось в ежедневном анонсе. Необычно низкий объём — повод задать dot вопрос, а не автоматический вывод, что сломались LLM (могло быть мало подходящих источников).
4. **dot — основной путь выяснить причину.** По запросу даёт короткую оценку за последние 6 часов (модели и лимиты) и 24 часа (импорт), с таблицами и ссылками на доказательства. Codex — только если нужна более глубокая диагностика/ремонт.
5. **Минимальное расширение MCP лишь для недостающих данных.** Текущий eventsBot MCP уже читает ops_run/joboutbox через operations_snapshot, incidents_search, incident_get, но **не отдаёт** полную статистику Google limiter по моделям/проектам/ключам. Для полноценного ответа dot требуется компактный, read-only, вызываемый *только по запросу* срез; это не «отчёт», который кто-то должен читать каждый день.

## Почему не ограничиться только Codex

Кодовый агент способен исследовать репозиторий, логи и лимитер, и для редких расследований его достаточно. Но регулярное использование кодового исполнителя ради вопроса «что сейчас с импортом?» — лишний шаг, иногда с зависимостью от окружения/прав/контекста. dot должен дать ограниченный проверяемый ответ, не запускать код, не менять ключи и не обращаться к провайдерам с пробными LLM-запросами.

**Компромисс по работе:** сначала исправить шум и убедиться, что dot может читать текущий eventsBot MCP с нужным read scope. Если нужен разбор по ключам (он здесь нужен), добавить **один небольшой on-demand read-only метод** типа llm_operations_status (имя предварительное), а не набор метрик, таблиц хранения, агентов и расписаний. Не расширять тяжёлый обязательный operations_snapshot сетевым запросом к Supabase: он имеет отдельный строгий бюджет и историю таймаутов.

## Что должно быть в ответе dot

### Сводка моделей (по умолчанию 6 часов)

| Модель (канонический ID) | Успех / ошибки среди отправленных | Отказы допуска RPM/TPM/RPD | Provider 429 / 5xx | Последний подтверждённый успех | Текущее состояние / действие |
|---|---|---|---|---|---|
| Каждая настроенная основная и резервная модель | Подтверждённые количества, без двойного счёта retries | Отдельно, **без provider send** | Отдельно от локального limiter | Время или «нет данных» | Работает / временно ограничена / RPD исчерпан / устойчиво не отвечает / данных мало |

Неуспех одной физической попытки не означает неуспех логического запроса. Фраза «переход на резерв» означает **попытку** fallback; успешность резерва подтверждается отдельным terminal success. Отсутствие запросов не означает «здоров». Устойчивый отказ означает отсутствие подтверждённых успешных вызовов при достаточном числе реальных обращений за заявленный период, с указанным числом и последним успехом. Никаких придуманных процентов или статусов.

### Распределение по проектам квот и ключам (по запросу или раскрытие деталей)

| Модель | Квотный проект (безопасный стабильный псевдоним) | Ключ (стабильный безопасный псевдоним) | Отправленные вызовы / успехи | 429 / 5xx | Доля фактической нагрузки | RPD проекта |
|---|---|---|---|---|---|---|
| Одна строка на используемую комбинацию | scope-A | key-A1 | N / N | N / N | N% | использовано/лимит; время сброса |

**Обязательная семантика:**
- Основная единица квоты Google — **quota_scope × model**, то есть модель внутри Google Cloud project. Несколько ключей **одного проекта** делят его RPM/TPM/RPD; их квоты нельзя складывать. Несколько подтверждённо независимых проектов показываются отдельно.
- Разбивка по ключам нужна для оценки фактического распределения нагрузки, доступности key lane, отказов авторизации и понимания, можно ли перераспределить обращения. Если под одним scope все ключи достигли RPD, замена ключа *внутри того же проекта* не поможет.
- Показывать **действующие лимиты и использованную долю по scope**, а не выдавать локальные настройки за независимо подтверждённые лимиты Google. Различать недопуск из-за нашего ledger, реальный provider 429 и ошибку конкретного ключа/доступа.
- Только безопасные псевдонимы ключей/проектов, без значений API-ключей, UUID, секретных переменных, provider payload, raw request/response и приватных текстов. Псевдонимы должны быть сопоставимы между соседними запросами в пределах разрешённого владельцу доступа.
- RPD считать по календарю провайдера (для Google — Pacific day); время сброса показывать в Europe/Kaliningrad, с указанием источника ограничения. Срезы обращений — UTC-время с явным окном.

### Здоровье импорта (24 часа и сравнение с обычным уровнем)

Коротко: когда последний успешный запуск, какие источники были просмотрены, сколько создано и обновлено событий, сколько подтверждённо «не событие», сколько ожидает retry/deferred, сколько осталось technical terminal **без автоматического повтора**, растёт ли очередь и есть ли просроченные плановые запуски. Для необычно низкого числа созданных событий дать 2–3 объяснения с доказательствами: мало поступило/подошло источников; LLM-технические ошибки; очередь/расписание/публикация. **Источник, пост, событие и операция — разные единицы**: один пост может создать несколько событий. Не сравнивать их числа как одну метрику.

Отдельно написать, если импорт выполнен через резерв, а исходная модель остаётся проблемной. При отсутствии надёжной связи между конкретным LLM-вызовом и исходом источника **не приписывать** ему потерю или спасение события.

### Формат ответа dot

Сначала один абзац «Импорт в норме/частично/требует вмешательства: почему». Затем компактная таблица моделей; если видна квотная проблема — 1–6 строк по квотным проектам/ключам. В конце одно конкретное действие: «ничего», «подождать сброса», «уменьшить пики», «перераспределить на другой разрешённый scope/модель», «проверить доступ», «передать в Codex». Ссылки на ops_run/job и время актуальности обязательны. Пример вопроса: **«dot, почему сегодня мало новых событий? Проверь импорт за сутки и модели, ключи и квоты за 6 часов. Нужен ли ремонт?»**

## Классификация без ложных пожаров

| Наблюдение | Диагноз для человека | Действие |
|---|---|---|
| RPM/TPM, короткий provider 429, затем подтверждённые успехи | Временное ограничение, модель не объявляется неработающей | Без уведомления; при частых пиках — совет о распределении |
| Локальный RPD исчерпан по scope/model | Этот маршрут не примет новую нагрузку до сброса | Указать остаток, время сброса и альтернативный scope/модель |
| Provider 429 с неопределённой причиной | Ограничение подтверждено, причина пока неизвестна | Показать cooldown/retry-after; не утверждать RPD |
| 500/503/timeouts вперемежку с успехами | Нестабильность без доказанной полной недоступности | Показать долю и последнюю успешную попытку |
| Много реальных обращений, длительное отсутствие успехов | Подозрение на устойчивую недоступность | Предложить перераспределение; срочный сигнал, если нет резервного маршрута и работа сорвана |
| 401/403/ключ отключён/биллинг | Отказ доступа конкретного ключа или scope | Проверка прав/оплаты; не обвинять модель целиком |
| Модель переименована/выведена либо 404 по endpoint | Вероятная несовместимость версии/маршрута | Проверить API-контракт и предложить замену |
| Невалидный JSON, truncated, semantic quality failure | Не обязательно проблема доступности | Разбирать stage, промпт и валидность результата отдельно |

Это **описательная диагностика**, не автономный маршрутизатор. Ни dot, ни MCP не должны без отдельного разрешения менять конфигурацию, лимиты, ключи, публикации или переключать production-трафик.

## Источники данных и ограничения

- Канонические агрегаты Google уже предусмотрены в google_ai_requests, google_ai_request_attempts, google_ai_usage_counters, google_ai_model_limits, google_ai_api_keys, google_ai_provider_cooldowns. Использовать read-only проекции с ограниченным временем/объёмом, без сырого SQL от MCP-клиента и без прямых LLM-probe. Отказы **до** reserve/send должны иметь отдельный счётчик/источник: нельзя выдавать их за provider calls. Для OpenAI/прочих моделей покрытие проверять отдельно и честно помечать «нет метрик», а не нулём.
- Есть [read-only Smart Update audit](../../operations/smart-update-prod-audit.md), где уже описаны агрегаты limiter, sanitization и различие logical/physical attempts. Его нынешний runbook привязан к **legacy Fly**; это **референс схемы анализа**, не готовая команда для текущего RunCoveer production. Не запускать старую Fly workflow как будто она проверяет текущий сервис.
- [Events MCP](../../operations/private-events-mcp.md) уже предоставляет проверяемые ops_run/joboutbox, но его обычный operations_snapshot не содержит limiter Supabase. Новый query должен изолировать ошибки внешнего источника, отвечать «данные недоступны» и не ломать чтение импортов.
- Если dot пока не имеет доступа к тому же operations:read MCP, сначала проверить эту возможность. Если доступа нет, не обещать «dot всё знает»; временная глубинная диагностика остаётся через Codex.
- История структурированных логов ограничена ротацией и бюджетом [runtime logs](../../operations/runtime-logs.md); отсутствие старых данных не приравнивать к отсутствию ошибок.

## Минимальный порядок действий

1. **P0 — убрать спам в существующей точке доставки** notify_llm_incident. Процессные provider errors/переключения уходят в логи; сохранить фактические terminal-сигналы, не трогая ретраи, лимитер, цепочки fallback, импорт и публикацию. Защититься от дублей между consumer/kind; не делать бесконечный silence для нового критического исхода. Проверить, что при сломанном импорте сообщение всё ещё приходит.
2. **P1 — проверить текущий путь dot → eventsBot MCP → состояния импортов** на реальном owner-доступе. Исправить узкую известную проблему поиска ops_run по интервалу, если она воспроизводится: ISO timestamp сравнивается с SQLite datetime string. Не менять полный snapshot ради косметики.
3. **P1a — ровно один короткий read-only MCP срез по лимитеру/ключам**, только если P1 подтвердит отсутствие нужной информации. Периоды 6/24 часа, ограниченные результаты, scope/model/key counts, последняя успешная попытка, RPD/reset, cooldown, классы ошибок и evidence coverage. Без cron, materialized report и секретов. Можно сделать отдельным методом, чтобы не подмешивать Supabase network latency в operations_snapshot.
4. **P2 — только при реальном использовании и подтверждённом пробеле:** улучшить корреляцию логического запроса → fallback → итог источника, покрытие негуловских провайдеров или сравнение с 7-дневной нормой. Не делать заранее.

## Критерий готовности

- В обычном дне нет десятков сообщений о переходе с Gemma/Gemini на резерв; полные технические факты не теряются.
- При terminal-отказе важного импорта без retry сигнал приходит один раз, включая источник/операцию и необходимость действия. Нет ложного «CRITICAL» только из-за одиночного 429/500/503.
- На запрос dot отвечает **с актуальным временем**: состояние импорта, модели, причины ограничения и распределение по независимым квотным проектам/ключам. Если слой не доступен — явно сообщает, какой именно.
- Можно отличить «основная модель не отвечает, но fallback спас работу» от «не удалось импортировать источник»; нельзя выдумывать долю спасённых событий.
- Ни новые фоновые задания, ни регулярные отчёты, ни обязательные платные/пробные вызовы, ни изменение ключей/квот не появляются.

## Что сознательно не входит в предложение

Отдельный dashboard, webhook для всех модельных попыток, универсальный мониторинг всех провайдеров, сравнительный benchmark моделей, автоматическая замена моделей, новая система оповещений/инцидентов или обещание, что dot наблюдает всегда: **dot отвечает по запросу, а существующий runtime отвечает за фактическую работу и terminal-уведомления**.
