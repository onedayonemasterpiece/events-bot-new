# Canonical venue/location directory, coordinates and map links

> **Status:** product and data plan; no schema migration, geocoding traffic, map-provider integration or production UI change is authorized by this document.  
> **Updated:** 26 August 2026.  
> **Primary consumers:** event pages, Search, agent-assisted discovery, transport/directions surfaces and external MCP clients.

## 1. Product decision

A reusable first-party location directory is required. Event rows must not remain the only place where venue names and addresses live as loosely normalized text.

The target chain is:

```text
source-backed venue/place facts
→ canonical location identity
→ verified address and coordinates
→ derived provider links and map actions
→ Event/location relation
→ site, Search and MCP projections
```

Coordinates and map links are useful independently of the planned agent interface. They also enable the assistant to answer questions such as:

- «Где это находится?»;
- «Что из этого ближе к центру?»;
- «Покажи на карте»;
- «Есть ли что-то рядом с Музеем Мирового океана?»;
- «Как открыть место в Яндекс Картах или 2ГИС?».

The model must never invent an address, coordinate, distance or provider URL. It may select only server-provided typed location facts and actions.

## 2. Canonical entity boundary

The directory represents public event places, not private user locations.

Minimum location kinds:

```text
venue
outdoor_site
meeting_point
route_point
campus_or_complex
online
unknown
```

A canonical location may contain several navigational points:

- the venue/site centroid;
- the public entrance;
- an event-specific meeting point;
- a transport boarding point;
- a route waypoint.

These points must not be silently collapsed when they differ materially. An Event occurrence references the canonical location and may additionally reference an event-specific room, entrance or meeting point.

## 3. Minimum data contract

The first implementation proposal must define a versioned schema with at least:

```yaml
location_id: stable canonical ID
kind: venue | outdoor_site | meeting_point | route_point | campus_or_complex | online | unknown
name: canonical public name
aliases: bounded normalized aliases
status: verified | partial | approximate | conflicting | needs_review | not_applicable

address:
  country_code: RU
  region: string | null
  locality: string | null
  district: string | null
  street: string | null
  house: string | null
  unit_or_room: string | null
  postal_code: string | null
  formatted: string | null

geo:
  latitude: decimal | null
  longitude: decimal | null
  crs: WGS84
  precision: entrance | building | site | street | locality | approximate | unknown
  verified_at: timestamp | null

navigation_points:
  - navigation_point_id: stable ID
    kind: entrance | meeting_point | boarding_point | route_point | centroid
    latitude: decimal | null
    longitude: decimal | null
    label: string | null
    note: string | null

provider_refs:
  yandex_maps_place_id: string | null
  two_gis_place_id: string | null
  openstreetmap_element: string | null
  other: bounded typed list

provenance:
  source_refs: bounded evidence refs
  last_verified_at: timestamp | null
  revision: stable revision/hash
```

Exact field names are candidates until the implementation task audits the current persistence model. The semantics above are required.

### Coordinate rules

- Latitude and longitude use WGS84 decimal degrees.
- Missing coordinates remain `null`; a city centroid is not a venue coordinate.
- `approximate` coordinates are visibly distinguished from a verified entrance/building point.
- Conflicting provider/source coordinates remain `conflicting` and do not become a trusted navigation action automatically.
- An LLM extraction without source evidence is not coordinate verification.
- Provider IDs and URLs are references, not canonical geographical truth.

## 4. Map links and provider actions

The canonical record stores coordinates, address and optional provider place IDs. User-facing links should normally be generated by a trusted server-side resolver rather than copied from model output.

Planned typed actions:

```yaml
map_actions:
  - provider: yandex_maps | two_gis | openstreetmap | google_maps | geo_uri
    action: open_place | show_point | build_route
    url: server_generated_https_url
    label: localized display label
    target_kind: place | entrance | meeting_point | boarding_point
```

Rules:

- only an allowlisted provider and URL template may be emitted;
- the frontend and MCP response receive a bounded typed action, not arbitrary HTML/Markdown supplied by a model;
- a stable provider place ID is preferred when it has been verified;
- coordinates plus canonical address are the fallback;
- route-building links are optional and must not imply a verified travel time;
- broken-link and wrong-place checks are part of recurring data QA;
- provider terms, attribution and link format are reviewed before activation.

P0 should support at least the providers actually useful to the audience. The exact enabled list is an implementation/owner decision, not hard-coded by this plan.

## 5. Event relation and projections

Events and occurrences should refer to `location_id` rather than duplicate a venue identity in every projection.

Required projections:

### Event/search snapshot

```yaml
location:
  location_id: string
  name: string
  formatted_address: string | null
  locality: string | null
  geo_status: verified | partial | approximate | conflicting | needs_review
  latitude: decimal | null
  longitude: decimal | null
  map_actions: bounded list
```

A compact card does not need to render all fields, but the server result must preserve enough typed data to open the location and map actions safely.

### Agent UI block

```yaml
block_type: location
location_id: string
headline: string
address: string | null
navigation_note: string | null
map_actions: bounded list
confidence: verified | approximate | unresolved
```

### MCP projection

The external agent contract should expose the same canonical facts, with no model-generated coordinates or links.

Candidate read-only tools:

```text
locations.search
locations.get
locations.resolve_for_event
events.search            # includes compact location projection
events.get               # includes canonical location relation
```

The website may call the underlying domain services directly. MCP is an adapter for external agents and must not become a required hop for the first-party site.

## 6. Data acquisition and verification

### P0 — census and schema

- [ ] Inventory all current venue/location/address fields and projections.
- [ ] Measure unique normalized names, aliases, missing addresses and obvious collisions.
- [ ] Identify temporary meeting points, route points, outdoor sites and online events.
- [ ] Define canonical identity, merge/split rules and occurrence relation.
- [ ] Define versioned schema, provenance and revision contract.
- [ ] Define provider-link allowlist and server-side URL builder boundary.

### P1 — bootstrap and review

- [ ] Seed canonical locations from existing accepted event facts.
- [ ] Preserve exact source evidence for names and addresses.
- [ ] Run bounded geocoding only through an approved service path.
- [ ] Record provider, request evidence and verification status without storing secrets.
- [ ] Flag low-confidence, conflicting and duplicate candidates for review.
- [ ] Verify high-frequency venues and all current/future events first.
- [ ] Keep unknown locations usable as text without presenting false map certainty.

### P2 — site and Search projections

- [ ] Export `location_id`, canonical display name and map actions into trusted snapshots.
- [ ] Add a consistent «Где это?» / «Открыть на карте» action to approved surfaces.
- [ ] Support location-based query constraints without requiring the LLM to parse raw addresses alone.
- [ ] Add location/message blocks to the agent-assisted Search experiment.
- [ ] Add link integrity and wrong-place regression fixtures.

### P3 — MCP and advanced discovery

- [ ] Publish bounded read-only location tools through the existing MCP security model.
- [ ] Allow agents to resolve an Event to a canonical place and approved map actions.
- [ ] Add optional nearby/radius search only after coordinate coverage and distance semantics are proven.
- [ ] Add travel-time or public-transport planning only through separately approved data/services; straight-line distance is not travel time.

## 7. User position and privacy boundary

The location directory contains public place data. It does not authorize persistent collection of a user's precise location.

Any future «рядом со мной» flow must:

- request browser permission only after an explicit user action;
- work without permission by accepting a named area/place;
- use the position ephemerally unless a separate consent/storage decision exists;
- avoid sending precise user coordinates to an LLM when a server-side spatial query is sufficient;
- distinguish straight-line distance, route distance and estimated travel time;
- expose a clear location-permission and deletion boundary.

## 8. Quality and acceptance metrics

Minimum data-quality readout:

- active/future Event coverage by canonical `location_id`;
- verified-address coverage;
- verified-coordinate coverage;
- entrance/meeting-point coverage where needed;
- duplicate and conflicting-location counts;
- broken/wrong map-link rate;
- Event→location relation correction rate;
- map-action open rate and downstream event-value rate;
- agent location-answer factual error rate, target `0` for invented coordinates/links.

A high coverage percentage is not sufficient when popular venues are wrong. The report must include frequency-weighted coverage and a reviewed critical-venue cohort.

## 9. Explicit non-goals for the first pass

- no full GIS platform;
- no continuous user tracking;
- no automatic route optimization;
- no model-authored coordinates, distances or map URLs;
- no forced embedded map on every card;
- no replacement of canonical Event/address evidence with a provider record;
- no assumption that several similarly named venues are one identity;
- no MCP-specific duplicate location database.

## 10. Closure criterion

The location foundation is ready for broad product use only when one versioned canonical location identity is shared by Event data, static/search snapshots and MCP projections; current/future event coverage is measured; coordinates carry precision and provenance; provider actions are generated through an allowlisted resolver; uncertain places fail honestly; and an agent can answer «где это?» using only verified typed facts.
