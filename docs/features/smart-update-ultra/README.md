## Уточнение владельца: первый vision-проход сразу возвращает OCR

Для источника с изображениями первая модель со зрением за один **содержательный проход после получения evidence** возвращает решение о событиях/изменениях, найденные children и прочитанный OCR с привязкой к каждому изображению. Если событие подтверждено, OCR значимого текста этих изображений обязателен; отдельного обязательного OCR-вызова после положительного решения нет. Там, где источник отрицательный, полезно сохранить уже прочитанный текст для контроля пропусков.

Это уточняет разделение стадий в первоначальном Candidate A: `vision decision + OCR + initial facts` — единый первичный результат, а не обязательные последовательно дублирующие vision-запросы. Получение файлов через инструменты может потребовать служебных шагов, поэтому один task/turn не следует без измерения называть одним физическим запросом к модели.

После сохранения этого результата текстовые модели используют OCR и факты, ищут актуальные совпадения и готовят create/merge/lifecycle plan. Они не обязаны заново читать картинки. При конкретной неоднозначности layout/неразборчивости допускается адресный дополнительный vision-pass с записанной причиной.

Различать:

- `text="", unreadable=false`: изображение реально открыто, текста нет;
- нечитаемый текст: явное unknown/неразборчивость, не придуманные слова;
- файл не открыт/альбом не собран: технически неполное evidence, не подтверждённое отсутствие события.

`events` содержит только посещаемые активности. Сезонный перерыв, окончание сезона и изменение расписания не становятся дополнительными мероприятиями: это lifecycle/context. У каждого исходного материала и дочернего события сохраняется свой scope; OCR не должен сваливать даты и названия разных карточек в одну неподписанную строку.

## Минимальный лабораторный контракт

Нужно проверять не только JSON syntax, но и закрытые enums, типы, соответствие disposition наполнению events/actions, полноту evidence, правильную роль изменений и поддержку фактов исходником. Например, events+actions требуют `MIXED`, а изменение времени — канонический `RESCHEDULE_TIME`, не произвольные `reschedule`/`time_changed`.

Результат OpenCode `completed` означает завершение исполнения, **не принятие схемы, семантики или записи в БД**. Неудачные ответы, ошибки транспорта и permission waits сохраняются с фактической стадией. Поздняя корректировка prompt не удаляет прежнюю ошибку.

Модельная атрибуция по стадиям обязательна: requested/actual model, provider, prompt/schema version, исходный пакет, попытка, response/technical outcome. Service wait, permission wait и inference duration не смешиваются в одну сравнительную скорость модели. Нулевые tokens/cost в ошибочном ответе не следует считать доказанным объёмом состоявшегося инференса.

## Исследование вместо разработки по предположениям

Сначала компонентный стенд на DevCoveer с сохранёнными исходниками и независимой разметкой. Для создания и объединения — согласованный production snapshot и отдельные disposable shadow copies. Исходная копия неизменяема; все внешние публикационные эффекты заблокированы. Тестирование фактического Smart Update commit boundary не заменяется простым INSERT/UPDATE в игрушечной таблице.

Текущий snapshot не является эталонной истиной и может уже содержать тестовый пост. Для CREATE допускается явно описанный counterfactual fixture только в shadow, с корректными связями. Исторические fixtures, сегодняшние чтения старых постов и свежие публикации считаются раздельно. Время оценки фиксируется явно.

До prompt tuning разделить DEV и untouched HOLDOUT по группам связанных событий/репостов. Проверенные и настроенные на них примеры не объявляются holdout позднее. Разметка проверяется по оригиналам; ответ тестируемой модели не создаёт золотой эталон сам для себя. Малый smoke-корпус не устанавливает достоверный процент качества на суточном потоке.

## Экскурсии

Включить отдельный guide-набор в компонентное исследование уже сейчас, но не смешивать доменные данные. Общими являются сбор, joint vision/OCR, модельные роли, очереди, ограничения и audit lineage. Отдельными остаются GuideProfile, ExcursionTemplate, ExcursionOccurrence, GuideFactClaim и digest eligibility.

Обязательные guide-проверки: несколько дат/маршрутов в одном анонсе; изменение времени без нового выхода; sold-out/waitlist; перенос/отмена; on-request/private предложение без ложного публичного сеанса; post-report как полезный template/profile context; общие контакты и цены без переноса между маршрутами. `Нет публичного датированного выхода` не означает `нет полезных сведений для экскурсионного продукта`.

Существующая документация содержит исторические Gemma-only и более поздние смешанные defaults. В исследовании новый разрешённый владельцем multi-provider маршрут оформляется отдельным кандидатом, а не молчаливым изменением production-конфигурации.

## Как фиксируются результаты

После каждого завершённого микропрогона: сохранить исходник/хэш и точный prompt → получить terminal output и технический receipt → записать независимую оценку и ограничения → обновить run report в PR. Оригиналы, полные session receipts без hidden reasoning и изображения остаются в private retained artifact directory; в GitHub идут воспроизводимые скрипты, schemas/prompts и обезличенные отчёты.

При прерывании продолжение начинается с существующего worktree, task IDs, операции и сохранённого результата. Повторный snapshot/вызов модели не запускается только потому, что чат потерял ответ. Заблокированная операция не переносится скрыто на другой механизм. Невыполненные snapshot/live-VK/domain-write проверки остаются явно открытыми, даже когда текстовый или visual smoke успешен.
