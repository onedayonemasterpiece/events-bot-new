# Промпт для кодового агента: portable-автопрезентатор на Playwright

## Роль и ожидаемый результат

Ты — кодовый агент. Не ограничивайся архитектурным описанием: создай полностью рабочий proof of concept, исходный код, инструкции запуска, локальный demo-сайт, сервер управления и скрипт сборки portable-комплекта для Windows 10 x64.

Нужно получить систему, в которой:

1. На Windows-ноутбуке запускается portable-приложение из одной папки.
2. Ничего не требуется устанавливать на презентационный ноутбук.
3. В portable-папке находятся:
   - portable Node.js;
   - приложение-агент;
   - все `node_modules`;
   - Chromium, установленный Playwright;
   - конфигурация;
   - `start.cmd`.
4. Агент открывает видимый Chromium. Не использовать Edge и не искать системные браузеры.
5. Я открываю на телефоне страницу на своем интернет-домене.
6. На странице есть одна большая кнопка: **«Запустить сценарий “Сегодня”»**.
7. После нажатия сервер отправляет команду агенту через интернет.
8. Агент:
   - открывает заданный сайт;
   - находит пункт меню **«Сегодня»**;
   - визуально подводит декоративный курсор к элементу;
   - выполняет настоящий клик через Playwright;
   - сообщает результат обратно на страницу телефона.
9. На ноутбуке не должно быть входящего сетевого порта. И телефон, и агент сами подключаются к серверу исходящими соединениями.
10. Для локального тестирования весь сценарий должен запускаться без внешнего домена через `localhost`.

Целевая платформа portable-комплекта: **Windows 10 x64**.

---

## Важные ограничения

Обязательно соблюдай следующие ограничения:

- Использовать **Playwright**.
- Использовать Chromium, скачанный и зафиксированный Playwright.
- Не использовать Microsoft Edge.
- Не использовать установленный Google Chrome.
- Не использовать `channel: "msedge"` или `channel: "chrome"`.
- Не использовать Selenium.
- Не использовать Electron.
- Не использовать AutoHotkey, WinAPI, `pyautogui` и управление системной мышью.
- Не выполнять клик через `element.click()` внутри `page.evaluate()`.
- Реальное действие должно выполняться через Playwright, например `locator.click()`.
- Декоративный курсор нужен только для визуализации движения. Он не заменяет реальный клик.
- На презентационном ноутбуке не должны требоваться:
  - установка Node.js;
  - установка браузера;
  - `npm install`;
  - PowerShell-скрипты;
  - права администратора;
  - изменение системного `PATH`;
  - открытие входящих портов.
- Все версии зависимостей должны быть зафиксированы без `^`, `~` и автоматического обновления.
- Не использовать `--no-sandbox`.
- Не отключать проверку TLS-сертификатов.
- Не передавать с телефона произвольный JavaScript, URL или CSS-селектор. Телефон может отправить только идентификатор заранее известного сценария.
- Не логировать секретные токены.

## Архитектура

Создай монорепозиторий из двух основных приложений:

```text
Телефон
https://presenter.example.com/control/
        │
        │ HTTPS + Socket.IO
        ▼
Relay Server
        │
        │ Socket.IO, исходящее соединение агента
        ▼
Portable Agent на Windows 10
        │
        ▼
Playwright Chromium
        │
        ▼
Целевой сайт
```

### Компонент 1: Relay Server

Сервер:

- работает как обычное Node.js-приложение;
- использует Express и Socket.IO;
- отдает мобильную страницу `/control/`;
- для локального теста отдает тестовый сайт `/demo-site/`;
- принимает подключение управляющей страницы;
- принимает подключение portable-агента;
- связывает их по `roomId`;
- пересылает только разрешенные команды;
- хранит текущее состояние комнаты в памяти;
- не требует базы данных для proof of concept;
- имеет endpoint `/health`;
- рассчитан на работу за HTTPS reverse proxy;
- сам может слушать HTTP на внутреннем порту `3000`.

### Компонент 2: Portable Agent

Агент:

- запускается из одной папки на Windows;
- использует portable Node.js из подпапки `runtime`;
- использует локальный Playwright Chromium из подпапки `browsers`;
- подключается к relay server через Socket.IO;
- не слушает входящие порты;
- запускает Chromium в `headless: false`;
- выполняет сценарий локально;
- сообщает статусы серверу;
- сохраняет логи и скриншот при ошибке.

- TypeScript для исходного кода;
- Node.js;
- Playwright;

- Socket.IO;

## Сетевой протокол

Используй Socket.IO.

Оба клиента сами создают исходящие соединения с сервером:

- телефон → сервер;
- Windows-агент → сервер.

На ноутбуке не открывать HTTP-сервер и не слушать локальный порт.

### Аутентификация

Подключение должно передавать через Socket.IO `auth`:

```ts
type ClientAuth =
  | {
      role: "admin";
      roomId: string;
      token: string;
    }
  | {
      role: "agent";
      roomId: string;
      token: string;
      agentId: string;
    };
```

Сервер должен проверять:

- роль;
- `roomId`;
- токен;
- допустимый формат полей.

Для proof of concept можно хранить одну комнату и два токена в переменных окружения сервера:

```env
ROOM_ID=demo
ADMIN_TOKEN=replace-with-long-random-admin-token
AGENT_TOKEN=replace-with-long-random-agent-token
PUBLIC_BASE_URL=https://presenter.example.com
PORT=3000
```

### Ссылка для телефона

Страница управления должна поддерживать ссылку вида:

```text
https://presenter.example.com/control/#room=demo&token=ADMIN_TOKEN
```

Токен находится во fragment/hash, чтобы он не попадал в обычный HTTP access log.

JavaScript страницы читает `room` и `token` из `location.hash` и использует их только в `socket.auth`.

Не выводить полный токен на экран и не писать его в консоль.

### События

Реализуй минимум следующие события:

```ts
type RunScenarioCommand = {
  commandId: string;
  scenarioId: "today";
  issuedAt: string;
};

type AgentStatus =
  | {
      state: "connected" | "idle";
      agentId: string;
      updatedAt: string;
    }
  | {
      state: "running";
      agentId: string;
      commandId: string;
      scenarioId: "today";
      updatedAt: string;
    }
  | {
      state: "completed";
      agentId: string;
      commandId: string;
      scenarioId: "today";
      updatedAt: string;
    }
  | {
      state: "error";
      agentId: string;
      commandId?: string;
      scenarioId?: "today";
      message: string;
      updatedAt: string;
    };
```

События Socket.IO:

```text
scenario:run
scenario:accepted
agent:status
room:state
```

Требования:

- сервер принимает от администратора только `scenarioId: "today"`;
- сервер сам валидирует структуру команды;
- агент подтверждает получение;
- двойное нажатие не должно запускать два сценария параллельно;
- повторная команда с тем же `commandId` должна игнорироваться;
- пока сценарий выполняется, кнопка на телефоне заблокирована;
- после переподключения управляющая страница получает актуальное состояние комнаты;
- если агент не подключен, команда не отправляется, а страница показывает понятное сообщение.

Socket.IO должен поддерживать стандартное переподключение. Оставь доступными WebSocket и HTTP long-polling.

## Мобильная страница `/control/`

Сделай простую адаптивную страницу без frontend-фреймворка.

На странице должны быть:

- заголовок «Автопрезентатор»;
- индикатор соединения с сервером;
- индикатор подключения Windows-агента;
- крупная кнопка:
  **«Запустить сценарий “Сегодня”»**;
- текущий статус:
  - «Агент не подключен»;
  - «Готов»;
  - «Выполняется»;
  - «Готово»;
  - «Ошибка»;
- текст последней ошибки;
- время последнего обновления.

Поведение:

- кнопка доступна только когда агент подключен и не выполняет сценарий;
- при нажатии генерируется `commandId` через `crypto.randomUUID()`;
- после нажатия кнопка сразу блокируется;
- интерфейс удобен на экране телефона;
- исключить случайное двойное нажатие;
- не добавлять лишние настройки и конструктор сценариев.

Создай `config.example.json`:

```json
{
  "serverUrl": "http://localhost:3000",
  "roomId": "demo",
  "agentToken": "replace-with-long-random-agent-token",
  "agentId": "presenter-win10-main",
  "siteUrl": "http://localhost:3000/demo-site/",
  "browser": {
    "kiosk": false,
    "startMaximized": true,
    "slowMoMs": 0,
    "navigationTimeoutMs": 30000,
    "actionTimeoutMs": 15000
  },
  "scenario": {
    "today": {
      "target": {
        "strategy": "testId",
        "value": "today-menu"
      },
      "fallbackText": "Сегодня",
      "success": {
        "strategy": "testId",
        "value": "today-page"
      }
    }
  },
  "visualCursor": {
    "enabled": true,
    "moveDurationMs": 700,
    "pauseBeforeClickMs": 250,
    "pauseAfterClickMs": 500
```

Учти, что для `data-demo` Playwright должен быть настроен так, чтобы `getByTestId()` использовал атрибут `data-demo`, либо реализуй явный locator `[data-demo="..."]`.

- если `config.json` отсутствует, агент должен завершиться с понятной ошибкой;
- не создавать молча рабочую конфигурацию с небезопасными токенами;
- сообщить, что нужно скопировать `config.example.json` в `config.json`;
- проверить все поля через схему;
- не печатать `agentToken` в лог.

## Запуск Chromium

Используй только Chromium, входящий в Playwright.

Перед импортом или запуском Playwright установи:

```text
PLAYWRIGHT_BROWSERS_PATH=<portable-root>\browsers
```

В runtime это должно делаться программно или через `start.cmd`.

Не использовать системный браузер и не задавать `channel`.

Предпочтительный вариант:

```ts
chromium.launchPersistentContext(profileDir, {
  headless: false,
  viewport: null,
  bypassCSP: true,
  args: [
    "--start-maximized"
  ]
});
```

Если в конфигурации `kiosk: true`, добавляй `--kiosk`.

Требования:

- профиль хранить внутри portable-папки, например `data/browser-profile`;
- не использовать профиль системного Chrome;
- при повторном запуске корректно обрабатывать lock-файл профиля;
- использовать один управляемый browser context;
- использовать одну основную страницу;
- закрывать лишние пустые вкладки;
- корректно завершать browser context по `Ctrl+C` и при штатном выходе;
- если браузер аварийно закрылся, следующая команда должна попытаться запустить его заново.

## Сценарий `today`

Создай один сценарий с идентификатором:

```text
today
```

Алгоритм:

1. Проверить, что Chromium запущен.
2. Получить основную страницу.
3. Перейти на `config.siteUrl`.
4. Дождаться `domcontentloaded`.
5. Найти пункт меню «Сегодня».
6. Основной locator брать из конфигурации.
7. Если основной locator не найден, использовать точный текстовый fallback `Сегодня`.
8. Убедиться, что найден один видимый интерактивный элемент.
9. Выполнить `scrollIntoViewIfNeeded()`.
10. Получить `boundingBox()`.
11. Вставить поверх сайта декоративный курсор.
12. Плавно переместить декоративный курсор в центр элемента.
13. Выполнить настоящий `locator.hover()`.
14. Показать короткую визуальную анимацию нажатия.
15. Выполнить настоящий `locator.click()`.
16. Не использовать DOM-вызов `element.click()`.
17. Дождаться элемента успеха из конфигурации.
18. Отправить статус `completed`.
19. При любой ошибке:
    - отправить статус `error`;
    - сохранить скриншот;
    - сохранить понятный лог;
    - оставить браузер открытым, если это возможно.

Пример принципиально правильного клика:

```ts
await target.hover();
await target.click({
  timeout: config.browser.actionTimeoutMs
});
```

Пример запрещенного клика:

```ts
await page.evaluate(() => {
  document.querySelector("...")?.click();
});
```

## Декоративный курсор

Playwright выполняет реальное браузерное взаимодействие, но системная стрелка Windows не обязана визуально перемещаться. Поэтому добавь простой DOM-overlay.

Требования:

- курсор создается под уникальным id, например `#autopresenter-cursor`;
- `position: fixed`;
- `pointer-events: none`;
- очень высокий `z-index`;
- не перехватывает клик;
- имеет плавное перемещение;
- имеет короткую анимацию нажатия или ripple;
- повторная инъекция не создает дубликаты;
- после навигации overlay можно безопасно создать заново;
- overlay должен работать на локальном demo-сайте и на обычном сайте;
- при ошибке инъекции реальный Playwright-клик все равно должен выполняться;
- `bypassCSP: true` используется только для возможности технического overlay, а не для обхода авторизации или политик сайта.

Декоративный курсор — визуальная часть. Источником фактического действия остается Playwright locator.

## Очередь и защита от повторов

В агенте должна существовать простая последовательная очередь.

Правила:

- одновременно выполняется не более одного сценария;
- новая команда во время выполнения получает отказ `busy`;
- `commandId`, уже выполненный или принятый ранее, не выполняется повторно;
- хранить последние, например, 100 `commandId` в памяти;
- после перезапуска память можно очистить — постоянная база для PoC не нужна.

## Логи и диагностика

Portable-папка должна иметь каталог:

```text
logs/
```

Логировать:

- время запуска;
- версию Windows и архитектуру;
- версию Node.js;
- версию Playwright;
- путь к Chromium;
- URL сервера без токена;
- `roomId`;
- подключение и переподключение;
- получение команды;
- начало и завершение сценария;
- краткую ошибку.

Не логировать:

- `ADMIN_TOKEN`;
- `AGENT_TOKEN`;
- полный объект Socket.IO auth;
- cookies;
- содержимое localStorage;
- HTML целевого сайта.

При ошибке сценария сохранять:

```text
logs/error-YYYYMMDD-HHmmss.png
```

Добавь режим:

```text
start.cmd --self-test
```

или отдельный:

```text
self-test.cmd
```

Self-test должен проверить:

- наличие `config.json`;
- наличие `runtime/node.exe`;
- наличие локального Chromium;
- возможность запустить Chromium;
- возможность открыть `about:blank`;
- затем закрыть браузер и вернуть код выхода `0`.

Self-test не должен требовать доступа к целевому сайту.

## Portable-сборка

Нужен PowerShell-скрипт для запуска **на машине сборки**, а не на презентационном ноутбуке:

```text
scripts/build-portable.ps1
```

Сборку выполнять на Windows x64, чтобы Playwright скачал Windows-версию Chromium.

Скрипт должен:

1. Проверить чистую установку зависимостей через `npm ci`.
2. Собрать TypeScript.
3. Очистить предыдущий каталог `release`.
4. Создать:

```text
release/Autopresenter-Win10-x64/
```

5. Скачать официальную ZIP-версию заранее зафиксированного Node.js для Windows x64.
6. Распаковать весь portable Node.js в:

```text
release/Autopresenter-Win10-x64/runtime/
```

7. Скопировать собранный код агента.
8. Скопировать только production-зависимости агента.

`config.json` в release можно создать как копию example только для локального demo-режима. В README явно написать, какие поля заменить перед реальным показом.

### `start.cmd`

Он должен:

- работать при запуске двойным кликом;
- корректно работать из пути с пробелами;
- менять рабочий каталог на корень portable-папки;
- выставлять `PLAYWRIGHT_BROWSERS_PATH`;
- запускать именно `runtime\node.exe`;
- передавать абсолютный путь к `config.json`;
- возвращать код ошибки;
- при ошибке оставлять окно открытым с понятным сообщением.

Пример общей идеи:

```bat
@echo off
setlocal
cd /d "%~dp0"
set "PLAYWRIGHT_BROWSERS_PATH=%~dp0browsers"
"%~dp0runtime\node.exe" "%~dp0app\agent.js" --config "%~dp0config.json"
set "EXIT_CODE=%ERRORLEVEL%"
if not "%EXIT_CODE%"=="0" (
  echo.
  echo Autopresenter exited with code %EXIT_CODE%.
  pause
)
exit /b %EXIT_CODE%
```

Не копируй пример слепо: сделай надежную реализацию с кавычками и проверкой файлов.

## Безопасность

Для proof of concept реализуй минимально необходимую безопасность:

- разные токены для admin и agent;
- сравнение токенов без вывода в лог;
- whitelist допустимых `scenarioId`;
- проверка входных сообщений;
- ограничение частоты команд, например не чаще одной команды в секунду;
- запрет команд от неподтвержденного socket;
- admin не может отправлять URL;
- admin не может отправлять selector;
- admin не может отправлять JavaScript;
- агент берет URL и locator только из локального `config.json`;
- CORS страницы управления — same-origin;
- production не должен работать с пустыми токенами;
- сервер должен завершаться с ошибкой при небезопасной конфигурации.

## Обработка ошибок

Нужны понятные сообщения для следующих ситуаций:

- неверный токен;
- агент не подключен;
- агент уже занят;

- Chromium отсутствует;

- найдено несколько неоднозначных элементов;
- элемент невидим;
- клик не выполнен;
- страница успеха не появилась;
- браузер был закрыт вручную.

На мобильной странице показывать короткое сообщение. В локальном логе — техническую подробность и stack trace.
