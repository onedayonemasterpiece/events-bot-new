# Сравнение вариантов страницы события: MVP и UI/UX (A vs B)

Ниже представлен критический разбор и слияние двух спецификаций: **A** (Product/MVP) и **B** (Opus UI/UX/SEO), опираясь на контрольное событие (ID 5878, «Песни СССР») и требования первого vertical slice.

## 1. Какой вариант сильнее для первого vertical slice?
**Победитель для MVP — Вариант A (Internal spec).**
Вариант A жестко ограничен текущими реалиями данных (Telegraph) и требует только статического HTML. Вариант B (Opus) превосходен визуально и концептуально, но требует данных, которых у нас пока нет в структурированном виде: галереи фото (обычно есть только одна афиша), размеченных FAQ и работающего JSON API для подгрузки рекомендаций. Для MVP мы берем **логику данных из A и UI-решения из B**.

## 2. Порядок блоков Mobile
Вариант B вводит отличную практику — **Sticky bottom CTA**, которая спасает конверсию при длинном скролле описания. Однако B ставит галерею до описания, что избыточно для MVP.
**Оптимальный порядок:**
1. Хлебные крошки (B)
2. Hero-изображение с бейджами (B)
3. H1 + Дата/Время + Локация (B)
4. Короткое саммари/search_digest (A)
5. **Primary CTA** (A/B)
6. Action bar (Календарь, Поделиться) (B)
7. Fact block (Длительность, Пушкинская карта) (B)
8. Описание (A/B)
9. Другие даты (если есть) (A)
10. Промо-блок (B)
11. Похожие события (A/B)
12. Анти-пузырь (Другие жанры) (B)
13. Источник/Telegraph (B)
*Примечание: Sticky CTA (B) появляется поверх контента, как только основной CTA уходит за верхний край экрана.*

## 3. Desktop grid и sidebar
Вариант B предлагает отличную 12-колоночную сетку (8 колонок контент, 4 колонки сайдбар). Однако **B совершает ошибку, помещая `H1` в узкий сайдбар**. Длинные названия концертов сломают верстку и ухудшат читаемость.
**Решение:** берем сетку Opus (B), но переносим хлебные крошки и H1 в основную левую колонку (как в A). Сайдбар должен быть строго транзакционным (Дата, Локация, Цена, CTA, Facts).

## 4. CTA / Share / Calendar
Оба варианта сходятся на использовании Web Share API с фоллбэком на копирование ссылки.
* **CTA-контракт:** берем таблицу стейтов из A (Купить, Зарегистрироваться, Бесплатно) + визуальные токены и тени из B.
* **Календарь:** Генерация `.ics` на сервере (B) — идеальное решение для статики.

## 5. SEO / GEO / Schema / Fact blocks
**Безоговорочная победа Варианта B.**
B предлагает мощнейший пакет для поисковиков и нейросетей:
* `geo.region`, `geo.position`, `ICBM` теги.
* Скрытый HTML-комментарий `llm-context: event` для парсеров LLM.
* Наличие `llms.txt` на уровне домена.
* JSON-LD `MusicEvent` и `BreadcrumbList`.
* **Что исключаем:** `FAQPage` schema (так как на старте у нас нет структурированных Q&A). Fact block выводим семантическим списком `<dl>` (B).

## 6. Риски персонализации и filter bubble
Вариант A предлагает мешать 1 слот диверсификации в общую ленту рекомендаций. Вариант B предлагает выделить диверсификацию в отдельный блок **«Другие жанры рядом»**.
**Решение:** Подход B («Другие жанры рядом») намного честнее, прозрачнее для пользователя и исключает ощущение "сломанного алгоритма", когда в "Похожих" вдруг появляется совершенно другой жанр. Берем механику B, но рендерим ее **строго статически** (без client-side JSON-запросов на старте).

## 7. Промо-кампании без потери доверия
Вариант A допускает встраивание промо-карточки прямо в блок рекомендаций. Вариант B выделяет для промо **отдельный слот** между блоком источников и рекомендациями.
**Решение:** Подход B безопаснее для репутации. Отдельный нативный слот с рамкой `--color-promo` и четкой пометкой «Партнёр» не вызовет баннерной слепоты и сохранит доверие к органическим рекомендациям.

## 8. Что удалить как over-engineering (для первого релиза)
1. **Client-side fetch для рекомендаций (`/api/v1/related`):** В MVP страница должна быть на 100% сгенерирована статически (A).
2. **Photo gallery:** Источник пока не гарантирует наличие качественных фото, кроме главного постера.
3. **FAQ блок (аккордеон):** Требует ML-парсинга описаний или ручной разметки.
4. **Сложный учет frequency_cap для промо на клиенте:** В MVP промо просто вшивается статически.

## 9. P0-блокеры (что нельзя пускать в прод)
1. **H1 в сайдбаре на десктопе** — сломает визуальный баланс для длинных названий.
2. **Зависимость CTA от JS** — кнопки "Купить билет" должны вести по `href` даже при отключенном/заблокированном JS.
3. **Пустые блоки** — если нет данных о Пушкинской карте или организаторе, `<dt>/<dd>` фактов не должны рендериться (предотвратить появление надписей "null" или пустых строк).
4. **Сдвиги макета (Layout shifts)** — никаких отложенных подгрузок блоков, меняющих высоту страницы.

## 10. Итоговый Merged Skeleton (20–40 пунктов)

Ниже представлена утвержденная структура страницы (HTML/UI), объединяющая надежность A и эстетику/SEO B.

### Head & SEO (Невидимая часть)
1. `<title>`: Название — Дата, Локация, Город | Полюбить Калининград Анонсы.
2. Canonical URL + `robots` `max-snippet:-1`.
3. Meta `geo.position`, `geo.region`, `ICBM`.
4. OpenGraph и Twitter Cards (image: URL постера).
5. JSON-LD: `Event` / `MusicEvent`.
6. JSON-LD: `BreadcrumbList`.
7. Скрытый блок для AI: `<!-- llm-context: event ... -->`.
8. Preload главного Hero-изображения.

### Header (Глобальный)
9. Брендированная плашка «Полюбить Калининград Анонсы» (A).
10. Компактная навигация (Сегодня, Выходные).

### Layout (Desktop: 12 колонок. Mobile: 1 колонка)
11. **Mobile:** Контент идет последовательно вниз.
12. **Desktop:** Main Column (8 колонок) + Sticky Sidebar (4 колонки).

### Main Content Column (Левая часть на десктопе, основа на мобайле)
13. Хлебные крошки (напр., Афиша > Светлогорск > Концерты).
14. `H1` Название события (всегда в основной колонке).
15. Hero-изображение (aspect ratio 16:9 или 16:10, без сильных градиентов).
16. Бейджи поверх Hero: Тип события (Концерт), Статус (Бесплатно).
17. Краткое саммари (`search_digest`, 1-2 предложения) — *только на мобайле или сразу под H1*.
18. Развернутое описание (Markdown content).
19. Другие даты этого же события (Блок-список).
20. Источник данных (ссылка на Telegraph/VK).
21. Промо-слот #1 (Статический, пометка «Партнёр», рамка `--color-promo`).
22. Секция `H2`: Похожие события (3-4 статичные карточки по логике площадка+жанр).
23. Секция `H2`: Другие жанры рядом (2 карточки, анти-пузырь).

### Sticky Sidebar (Десктоп) / Встроенный блок (Мобайл)
24. Строка Даты и Времени.
25. Строка Локации + Город + Ссылка на карту.
26. **Primary CTA:** Кнопка «Купить билет» / «Зарегистрироваться». Цвет: `--color-accent`.
27. Status Indicator: «Билеты в продаже» (`--color-success`) / «Распродано» (`--color-danger`).
28. **Action Bar:** Добавить в календарь (ссылка на `.ics`).
29. **Action Bar:** Поделиться (Web Share API / dropdown).
30. **Action Bar:** Скопировать ссылку.
31. Fact Block (`<dl>`): Тип, Длительность, Возрастной ценз (если есть).

### Интерактивные и плавающие элементы (Только UI)
32. **Mobile Sticky CTA:** Плавающая панель снизу с дублем кнопки «Купить билет».
33. Появление Mobile Sticky CTA: через IntersectionObserver, когда главная кнопка скрыта.
34. Toast-уведомление «Ссылка скопирована» (client-side).

### Footer (Глобальный)
35. Копирайт, политика источника.
36. (Временное) Ссылка на legacy Telegraph-страницу для сверки в первые месяцы.
