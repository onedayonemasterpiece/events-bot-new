# Юридический release-gate персонализации в РФ

> **Статус:** принято как продуктово-архитектурное решение; реализация и комплект публичных документов ещё не закрыты.  
> **Дата среза:** 2026-08-02.  
> **Родительский план:** [`release-plan.md`](release-plan.md).  
> **Scope:** персональная выдача, локальный и серверный профиль интересов, поведенческие сигналы, рекомендательные технологии и связанные документы сайта `kenigevents.ru`.  
> **Ограничение:** документ фиксирует release-contract проекта и не заменяет финальную проверку формулировок практикующим юристом перед production-включением.

## Решение

Для основной персонализации сайта **не вводится обязательный предварительный
переключатель** «Разрешить / Запретить персонализацию», отдельный checkbox или
cookie-wall.

Основная рабочая модель:

1. Пользователь сначала получает полезную общую, редакционную или контекстную
   выдачу без серверного профиля интересов.
2. Персонализированная функция запускается только после понятного активного
   действия пользователя, непосредственно связанного с рекомендациями.
3. Такое действие является началом использования персонализированного подбора и
   акцептом соответствующей части Пользовательского соглашения.
4. Обработка данных, действительно необходимая для предоставления этой функции,
   проектируется на основании пункта 5 части 1 статьи 6 Федерального закона
   № 152-ФЗ — исполнение договора с субъектом персональных данных.
5. Пользователь может удалить профиль и прекратить персональный подбор через
   команду «Сбросить персональные рекомендации», не встречая обязательный
   переключатель при первом посещении.

Формула «продолжая пользоваться сайтом, пользователь соглашается на
персонализацию» может использоваться только как дополнительное информирование.
Она **не является** activation event, договорным акцептом или доказательством
согласия на серверное профилирование.

## Почему выбран именно этот вариант

Статья 6 Закона № 152-ФЗ предусматривает самостоятельные основания обработки,
включая исполнение договора. При этом договор не может устанавливать бездействие
субъекта условием его заключения. Статья 438 ГК РФ допускает акцепт посредством
действий по выполнению условий оферты, но прямо отделяет такие действия от
молчания.

Если проект всё же называет юридическим основанием «согласие», применяются более
строгие требования статьи 9 Закона № 152-ФЗ: согласие должно быть конкретным,
предметным, информированным, сознательным и однозначным, а также оформляться
отдельно от иной подтверждаемой информации. Поэтому скрытое согласие через
обычный просмотр страницы создаёт ненужный доказательственный риск.

Договорная модель не является способом обойти закон. Она допустима только если:

- персонализированный подбор реально является запрошенной пользователем
  функцией сервиса;
- обработка ограничена данными, необходимыми для этой функции;
- до активации не создаётся скрытый долговременный профиль;
- необязательная аналитика, маркетинг и сторонний трекинг не маскируются под
  исполнение договора;
- фактическая реализация совпадает с Пользовательским соглашением, Политикой
  обработки персональных данных и Правилами применения рекомендательных
  технологий.

## Влияние на общий release plan

Публичный статический сайт с общей выдачей может быть выпущен до закрытия этого
release-gate при одновременном выполнении всех условий:

- серверная персонализация выключена;
- серверный профиль интересов не создаётся;
- поведенческие сигналы для персонализации не отправляются;
- персональный режим не заявлен пользователю как работающая функция.

Этот gate становится **P0-блокером** до включения любого из следующих процессов:

- долговременный anonymous или account-linked профиль интересов;
- серверная переупорядоченная выдача «Для меня»;
- передача `impression`, `open`, `dwell`, `ticket_click`, `map_click` и иных
  сигналов в профиль рекомендаций;
- синхронизация персонализации между устройствами;
- персональные рекомендации через email, SMS или push;
- применение предпочтений пользователя при ранжировании на стороне сервера.

## Состояния пользователя

### `not_started`

Состояние по умолчанию до первого осмысленного действия.

Разрешено:

- общая статическая выдача;
- редакционные подборки;
- фильтрация по выбранной дате, городу и категории в рамках текущего запроса;
- минимальные технические данные, необходимые для безопасности, доставки
  страницы и сохранения чисто интерфейсных настроек;
- локальное краткоживущее состояние страницы, не превращённое в долговременный
  поведенческий профиль.

Запрещено:

- создавать серверный interest profile;
- привязывать просмотры и прокрутку к устойчивому `visitor_id` для будущего
  ранжирования;
- считать закрытие уведомления активацией;
- использовать обычный page view, scroll, dwell или возврат на сайт как акцепт
  персонализированного сервиса;
- отправлять слабые сигналы в очередь персонализации «на будущее».

### `active`

Состояние устанавливается после допустимого activation event и фиксации версии
условий. После этого разрешается использовать только документированный набор
сигналов и только для заявленной цели персонального подбора.

### `reset`

Пользователь вызвал «Сбросить персональные рекомендации».

Обязательное поведение:

- удалить или необратимо отвязать профиль интересов и связанные сигналы в
  пределах утверждённого SLA;
- вернуть общую выдачу;
- очистить локальный профиль;
- не считать сам факт дальнейшего просмотра повторной активацией;
- разрешить повторный старт только после нового допустимого activation event.

## Допустимые activation events

Activation event должен быть понятным пользователю и функционально связанным с
персональным подбором.

Допустимы:

- сохранение выбранных интересов;
- завершение настройки персональных рекомендаций;
- включение режима «Только интересные мне» или «Для меня»;
- первая отметка «Нравится»;
- первая отметка «Не интересно»;
- сохранение параметров персонального подбора: город, радиус, бюджет, время,
  предпочитаемые форматы — если UI прямо объясняет, что параметры используются
  для рекомендаций.

Не считаются activation event:

- открытие страницы;
- прокрутка;
- время на странице;
- показ карточки;
- hover или focus;
- закрытие cookie-информера;
- нажатие «Понятно»;
- авторизация сама по себе;
- установка PWA сама по себе;
- переход по обычной ссылке или применение разового фильтра.

`share` не рекомендуется использовать как первый activation event: пользователь
может поделиться событием не потому, что оно интересно лично ему.

## Однократное уведомление в точке активации

Перед первым activation event или непосредственно в его UI-контексте должно быть
доступно короткое объяснение и ссылка на подробные правила.

Рекомендуемый текст:

> Мы учтём это действие в персональных рекомендациях. Совершая его, вы начинаете
> пользоваться персонализированным подбором на условиях Пользовательского
> соглашения. Как работают рекомендации

Требования:

- это не checkbox и не отдельная кнопка «Согласен»;
- пользователь совершает само функциональное действие;
- уведомление не должно маскироваться, быть недоступным для клавиатуры или
  screen reader;
- ссылка ведёт на стабильную версию условий и Правила применения
  рекомендательных технологий;
- activation event не отправляется до доступности текста и версии документов;
- UI не должен утверждать, что пользователь дал «согласие на персональные
  данные», если основанием выбрано исполнение договора.

## Доказательство активации

Для каждого первого запуска серверной персонализации фиксируется минимальная
аудит-запись:

```text
subject_key                    pseudonymous visitor/account key
personalization_started_at     UTC timestamp
activation_action              interest_save | like | not_interested | personal_mode
terms_version                  version/hash of User Agreement
privacy_version                version/hash of Privacy Policy
recommendation_rules_version   version/hash of Recommendation Rules
activation_surface             route/surface where action occurred
implementation_version         client/API contract version
```

Не следует хранить в такой записи:

- полный текст страницы;
- введённые пользователем свободные тексты без необходимости;
- email, OTP, access token или иные секреты;
- подробный device fingerprint;
- рекламные идентификаторы сторонних систем.

Аудит-запись подтверждает акцепт функции, а не выдуманное «согласие на всё».

## UI-контракт без предварительного opt-in

На первом посещении не показываются:

- блокирующее окно «Разрешить персонализацию?»;
- обязательный выбор «Включить / Выключить»;
- заранее выбранный checkbox;
- отказ от основной функциональности сайта при отсутствии согласия на
  необязательные цели.

Допускается неблокирующий информационный cookie/localStorage notice с кнопкой
«Понятно». Нажатие этой кнопки только закрывает уведомление и ничего не включает.

В настройках размещается действие:

> **Сбросить персональные рекомендации**  
> Будут удалены профиль интересов и история сигналов персонализации. Общая лента
> событий останется доступной.

Постоянный переключатель «Персонализация включена / выключена» не является
обязательным продуктовым элементом. После reset повторная персонализация требует
нового явного функционального действия.

## Матрица правовых оснований

| Процесс | Проектное основание | Предварительный выбор |
|---|---|---|
| Доставка страницы, безопасность, anti-abuse, минимальное состояние интерфейса | исполнение договора и/или законный интерес в строго необходимом объёме | нет |
| Основной персональный подбор после activation event | исполнение договора, п. 5 ч. 1 ст. 6 Закона № 152-ФЗ | отдельное согласие не используется |
| Скрытое долговременное профилирование с первого page view | не принято в проект | запрещено до отдельного решения |
| Необязательная продуктовая аналитика, не нужная для оказания функции | отдельное основание; при использовании согласия — отдельный consent flow | да, если нет иного надёжного основания |
| Сторонние рекламные пиксели, ремаркетинг, межсайтовый трекинг | отдельное согласие | да |
| Персональные рекламные email/SMS/push | отдельное предварительное согласие и отдельный unsubscribe/отзыв | да |
| Специальные категории персональных данных | только специальное законное основание; для обычного сервиса чаще письменное согласие | низкофрикционная модель не применяется |

Нельзя объединять основной персональный подбор, аналитику, маркетинг,
рассылки и сторонний трекинг в одну неделимую цель.

## Рекомендательные технологии

Персональная сортировка событий по собранным предпочтениям подпадает под рабочее
определение рекомендательных технологий статьи 10.2-2 Закона № 149-ФЗ.

До production-включения обязательны:

1. Общедоступное уведомление на русском языке с установленной формулировкой:

   > На информационном ресурсе применяются рекомендательные технологии.

2. Ссылка из уведомления на отдельную страницу, где размещена установленная
   информация о сборе, систематизации и анализе сведений о предпочтениях.
3. Отдельный документ «Правила применения рекомендательных технологий».
4. В правилах — фактическое описание:
   - процессов и методов сбора, систематизации и анализа;
   - способов предоставления информации на основе предпочтений;
   - используемых видов сведений;
   - источников этих сведений.
5. Фамилия и инициалы владельца для физического лица либо наименование для
   юридического лица, а также email для юридически значимых сообщений.
6. Беспрепятственный, бесплатный доступ без регистрации.
7. Уведомление не накладывается поверх другого контента.

Рекомендуемое размещение: постоянная ссылка в footer и повторное контекстное
объяснение около персональной выдачи. Cookie-popup не заменяет требования к
рекомендательным технологиям.

## Обязательные публичные документы

До включения `active`-состояния должны быть опубликованы и согласованы между
собой:

1. Пользовательское соглашение / условия персонализированного сервиса.
2. Политика обработки персональных данных.
3. Правила применения рекомендательных технологий.
4. Cookie/localStorage notice.
5. Отдельные формы согласия для процессов, реально основанных на согласии.
6. Порядок обращения субъекта персональных данных и удаления профиля.

### Пользовательское соглашение

Должно определять:

- персонализированный подбор как функцию сервиса;
- точный список действий, запускающих функцию;
- объём предоставляемой функции;
- порядок прекращения и reset;
- факт обработки данных для исполнения этой функции;
- отсутствие автоматического акцепта через молчание или обычный просмотр.

Рабочая формулировка:

> Персонализированный подбор событий является функциональностью Сервиса.
> Пользователь начинает использовать указанную функциональность при выборе и
> сохранении интересов, совершении отметки «Нравится» или «Не интересно» либо
> включении режима персональной выдачи. Совершение одного из указанных действий
> является акцептом условий предоставления персонализированного подбора. Для
> исполнения указанных условий Оператор обрабатывает псевдонимный идентификатор,
> заданные Пользователем параметры и сведения о взаимодействии с событиями в
> объёме, необходимом для формирования рекомендаций, на основании пункта 5 части
> 1 статьи 6 Федерального закона № 152-ФЗ. В случаях, когда законодательство
> требует согласия, оно запрашивается отдельно.

Формулировку перед публикацией проверяет юрист с учётом фактического оператора и
реализованного data flow.

### Политика обработки персональных данных

Отдельная цель:

> Формирование, отображение, сохранение и улучшение персонального подбора событий
> по запросу пользователя.

Для цели перечисляются:

- категории субъектов;
- точные категории данных;
- источники данных;
- операции;
- правовое основание;
- сроки и условия хранения;
- получатели/обработчики;
- местонахождение базы;
- трансграничная передача, если она существует;
- порядок блокирования, уничтожения и ответа субъекту.

Нельзя ограничиваться общей фразой «для улучшения качества сервиса».

### Cookie/localStorage notice

Информационный текст без псевдосогласия:

> Сайт использует локальное хранилище и технические идентификаторы для работы
> интерфейса, безопасности и сохранения настроек. Серверный профиль рекомендаций
> создаётся только после выбора интересов, первой отметки «Нравится / Не
> интересно» или включения персональной выдачи. Подробнее — в Политике обработки
> персональных данных и Правилах применения рекомендательных технологий.

Кнопка «Понятно» не записывает `personalization_started_at`.

## Идентификаторы и модель данных

Устойчивый `visitor_id`, связанный с поведением и профилем интересов, считается
персональными данными для проектирования и контроля, даже если оператор не знает
ФИО пользователя.

Для основной функции не использовать обобщённый флаг:

```text
consent_ok = true
```

Целевые поля:

```text
personalization_state = not_started | active | reset
personalization_started_at
personalization_activation_action
personalization_terms_version
personalization_privacy_version
personalization_rules_version
personalization_reset_at
profile_version
retention_policy_version
```

Отдельные consent-поля применяются только к соответствующим целям:

```text
analytics_consent_state
marketing_email_consent_state
marketing_push_consent_state
third_party_tracking_consent_state
```

Изменение юридического основания не должно выполняться задним числом простым
переименованием поля. Старые записи с `consent_ok` требуют migration policy:

- не считать их доказательством договорной активации;
- не переносить в `active` без подтверждаемого activation event;
- при отсутствии достаточного evidence вернуть пользователя в `not_started`;
- удалить или обезличить накопленные сигналы согласно утверждённой политике.

## API и транспортный gate

До `personalization_state=active` API обязан отклонять или не создавать:

- `impression`;
- `open`;
- `dwell`;
- `quick_skip`;
- `ticket_click`;
- `map_click`;
- `calendar_add`;
- `remind_set`;
- любые server-side profile updates.

Допустимый порядок:

```text
static/general page
  -> user sees activation explanation
  -> meaningful action
  -> atomic activation receipt
  -> profile creation/update
  -> later documented signals
```

Недопустимый порядок:

```text
page view
  -> create visitor profile
  -> collect signals
  -> later show cookie notice
```

Activation receipt и первое профильное изменение должны быть атомарны или
идемпотентно восстанавливаться. Повтор запроса не создаёт несколько профилей и не
подменяет первоначальную версию документов.

## Минимизация и сроки хранения

Точные сроки не устанавливаются законом одной универсальной цифрой; их должен
обосновать оператор для каждой цели. До юридического утверждения рабочие
проектные пределы:

- подробные сигналы персонализации — не более 90 дней;
- агрегированный профиль — не более 12 месяцев после последней персональной
  активности;
- activation receipt — в пределах срока, необходимого для доказательства
  основания и защиты требований;
- немедленное прекращение использования профиля после reset;
- уничтожение или необратимое обезличивание после достижения цели либо
  наступления условия прекращения обработки.

Эти цифры являются проектным proposal, а не ссылкой на установленный законом
фиксированный срок. Юрист и ответственный за персональные данные должны утвердить
их до D0 персонализации.

## Специальные категории и чувствительные темы

События могут косвенно указывать на политические взгляды, религиозные или
философские убеждения, состояние здоровья и иные специальные категории статьи
10 Закона № 152-ФЗ.

Для сохранения низкофрикционной модели проект обязан:

- маркировать потенциально чувствительные события внутренним
  `sensitive_topic`;
- не превращать просмотр или реакцию на такое событие в долговременную
  характеристику пользователя;
- не создавать сегменты вида «религиозные убеждения», «политические взгляды»,
  «заболевание/лечение»;
- не использовать такие сигналы для cross-surface рекомендаций;
- допускать показ через общую выдачу, поиск, дату, место и редакционные
  подборки;
- проводить отдельную юридическую оценку до любого изменения этого запрета.

Наличие события религиозной, политической или медицинской тематики в каталоге
само по себе не запрещено. Release-blocker — вывод и долговременная фиксация
чувствительной характеристики пользователя.

## Несовершеннолетние

До отдельной правовой модели сервис не должен:

- просить ребёнка указать возраст для профилирования;
- создавать сознательно детские поведенческие профили;
- выводить договорную модель из бездействия несовершеннолетнего;
- связывать профиль ребёнка с маркетинговыми рассылками.

Семейные и детские события могут присутствовать в общей выдаче и в настройках
взрослого пользователя без вывода о возрасте самого пользователя.

## Локализация и обработчики

До production-включения необходимо доказать:

- где выполняется первоначальная запись, систематизация, накопление, хранение,
  уточнение и извлечение данных граждан РФ;
- что первичная база соответствует части 5 статьи 18 Закона № 152-ФЗ;
- фактический регион каждого Supabase/Postgres/YDB/логового хранилища;
- договоры поручения обработки и перечень обработчиков;
- наличие или отсутствие трансграничной передачи;
- отражение местонахождения базы и обработчиков в документах и уведомлении
  Роскомнадзора.

Иностранный регион Supabase нельзя «исправить» формулировкой в Политике.
Серверный профиль не включается, пока data-flow и местонахождение первичной базы
не подтверждены evidence.

## Уведомление Роскомнадзора и внутренние документы

До начала автоматизированной обработки оператор проверяет применимость статьи 22
Закона № 152-ФЗ и при отсутствии исключения подаёт либо актуализирует уведомление.
Для цели персонализации должны совпадать:

- цель обработки;
- категории данных и субъектов;
- правовое основание;
- операции и способы обработки;
- сроки/условия прекращения;
- местонахождение базы;
- сведения о трансграничной передаче;
- меры безопасности и ответственный.

Также обязательны внутренние документы и меры по статье 18.1: политика,
локальные акты по целям, срокам и уничтожению, оценка вреда, контроль, обучение и
техническая защита.

## Отдельные согласия

Core personalization contract не распространяется автоматически на:

- стороннюю аналитику, не необходимую для функции;
- рекламные пиксели и ремаркетинг;
- передачу профиля внешним рекламным системам;
- рекламные email, SMS и push;
- специальные категории данных;
- публикацию/распространение персональных данных;
- автоматизированные решения, создающие юридические последствия или существенно
  затрагивающие права пользователя.

Для каждой такой цели проектируется отдельный legal basis и, когда требуется,
отдельное предварительное согласие с доказательством, версией и отзывом.

## Документационные конфликты

Этот документ отменяет для production следующие прежние prototype-допущения:

- «простой ОК включает analytics/personalization»;
- `consent_ok=true` как универсальное основание основной персонализации;
- «local rerank after consent» без разграничения договора, согласия и

- сбор серверной телеметрии до осмысленной активации.

## Acceptance checklist

### Документы

- [ ] Определён оператор персональных данных и владелец информационного ресурса.
- [ ] Пользовательское соглашение содержит персонализированную функцию и точные
      activation events.
- [ ] Политика содержит отдельную цель, данные, основания, сроки и обработчиков.
- [ ] Опубликованы Правила применения рекомендательных технологий.
- [ ] Размещена обязательная формулировка и ссылка по Приказу РКН № 149.
- [ ] Cookie/localStorage notice не выдаёт «Понятно» за согласие.
- [ ] Отдельные согласия отделены по целям.
- [ ] Документы прошли финальную юридическую проверку по фактическому data flow.

### Реализация

- [ ] До activation event серверный профиль не существует.
- [ ] Page view, scroll, dwell и закрытие notice не активируют персонализацию.
- [ ] Activation notice доступен до/в момент первого действия.
- [ ] Сохраняются action и версии документов.
- [ ] `consent_ok` не управляет core personalization.
- [ ] Reset удаляет/отвязывает локальный и серверный профиль.
- [ ] После reset обычный просмотр не реактивирует профиль.
- [ ] Специальные категории исключены из долговременного профиля.
- [ ] Ненужные сторонние scripts не загружаются до отдельного основания.
- [ ] Primary storage location и processors подтверждены.

### Автотесты

- [ ] Новый посетитель: `0` profile writes и `0` personalization signal writes.
- [ ] Page view/scroll/dwell: состояние остаётся `not_started`.
- [ ] Like с доступным уведомлением: ровно один activation receipt и один профиль.
- [ ] Повторный like/retry: идемпотентность, без второго activation receipt.
- [ ] «Не интересно» как первый action: та же contract/version фиксация.
- [ ] «Для меня» как первый action: та же contract/version фиксация.
- [ ] Недоступен backend: действие не даёт ложного `active`; общая выдача работает.
- [ ] Старая версия документов: контролируемая миграция без фиктивного согласия.
- [ ] Reset: профиль и сигналы недоступны; общая выдача остаётся.
- [ ] Повторный просмотр после reset: `not_started`, без writes.
- [ ] Sensitive event action: долговременная sensitive feature не создаётся.
- [ ] Bot/search crawler: static fallback, `0` profile writes.
- [ ] Screen reader/keyboard: уведомление и ссылка доступны.
- [ ] Рекомендательное уведомление доступно без регистрации и не перекрывает
      контент.

## NO-GO conditions

Персонализацию нельзя включать в production при любом из условий:

- profile write происходит до activation event;
- обычное продолжение использования считается согласием или акцептом;
- нет доказуемой версии Пользовательского соглашения, Политики или Правил;
- `consent_ok` остаётся универсальным флагом основной персонализации;
- reset удаляет только UI, но сохраняет активный серверный профиль;
- нет обязательного уведомления о рекомендательных технологиях;
- Правила не описывают фактически используемые сведения и методы;
- первичная база персональных данных граждан РФ находится за пределами РФ без
  применимого законного исключения;
- не проверена обязанность уведомления Роскомнадзора;
- специальные категории попадают в долговременный профиль;
- аналитика, реклама или рассылки включаются договорным основанием основной
  функции без отдельной оценки;
- публичные документы и реальный data flow расходятся;
- отсутствует финальный legal sign-off.

## Rollback

При нарушении gate:

1. отключить server-side ranking/profile writes feature flag;
2. оставить общую статическую выдачу;
3. остановить ingestion персональных сигналов;
4. сохранить минимальный технический incident evidence без чувствительных
   данных;
5. определить затронутый cohort;
6. блокировать, удалить или обезличить данные по утверждённому incident runbook;
7. исправить документы и реализацию;
8. повторить полный acceptance pack до возврата функции.

Rollback персонализации не должен блокировать просмотр событий, CTA, календарь,
карты и общие подборки.

## Итоговый release verdict

**GO для реализации без предварительного opt-in** возможен только в модели:

```text
общая выдача
  -> понятное активное действие
  -> versioned contract activation receipt
  -> минимальный персональный профиль
  -> прозрачные рекомендательные правила
  -> доступный reset
```

Модель ниже остаётся **NO-GO**:

```text
первый page view
  -> скрытый visitor profile
  -> сбор поведения
  -> «продолжая пользоваться, вы соглашаетесь»
```
