# Фокус-группа статического сайта

> **Статус:** продуктовый brief и обязательный contract обратной связи.
>
> Надёжность сетевых и Yandex-зависимых операций определяется в
> [отказоустойчивости Yandex-зависимостей](../../operations/yandex-dependency-resilience.md),
> а исполняемые проверки — в
> [стратегии автотестирования](../../operations/static-site-autotest-strategy.md)
> и [scenario registry](../../testing/static-site-autotest-scenarios.v1.yml).

## 1. Цели

1. Протестировать сайт перед публичным запуском.
2. Сформировать ядро постоянной аудитории.
3. Получить обратную связь по удобству, корректности данных и предложениям по
   доработкам.
4. Добиться установки PWA и повторного использования сайта.
5. Научить пользователей основным возможностям:
   - делиться событием;
   - добавлять событие в календарь;
   - отмечать явно неинтересные события;
   - пользоваться разделом «Для меня»;
   - видеть влияние персонализации;
   - познакомиться с почтовыми уведомлениями;
   - пользоваться умным поиском.
6. Проверить не только happy path, но и понятность сайта при частичных сетевых
   отказах, не перекладывая диагностику и повторную отправку на участника.

## 2. Мотивация

Два билета в театр на любые спектакли получает случайно выбранный активный
участник из пула выполнивших условия:

- найдено не менее 80% артефактов;
- дана как минимум обязательная NPS-оценка;
- дополнительным вкладом считаются текстовые сообщения, структурированные ошибки
  события и скриншоты.

Участие в розыгрыше требует подтверждённого email. Отказ вспомогательной
аналитики или YDB-проекции не может лишить пользователя уже подтверждённого
вклада.

## 3. Ограничения и идентичность

- участник авторизован через email OTP или Yandex;
- Yandex OAuth является одним способом входа, но не единственным: при его
  недоступности должен оставаться email-вход;
- один и тот же logical feedback/action не должен учитываться дважды после
  reload, повторного нажатия или восстановления сети;
- browser-local pending state не считается окончательной серверной доставкой,
  но сохраняется до подтверждения или явного terminal disposition.

## 4. Основная механика

- NPS по каждому типу страницы. Поставленная оценка остаётся видимой для текущей
  `page_revision`; после выпуска новой revision пользователь снова может оценить
  страницу.
- Возможность дать текстовую обратную связь и приложить скриншот.
- Структурированная ошибка события: неверная дата/время/место/цена/ссылка,
  дубликат, событие отменено или иная категория.
- Артефакты-пасхалки разбросаны по интерфейсу так, чтобы их требовалось найти.
- Автоматический розыгрыш в день окончания фокус-группы — 31 августа 2026 года.
- Статистика собирается минимально и экологично; продуктовые действия и
  обязательная обратная связь не зависят от доступности необязательной
  аналитической проекции.

## 5. Контракт надёжной обратной связи

### 5.1. Нельзя подтверждать отправку по факту попытки

Пользователь видит окончательное «Отправлено»/«Сохранено» только после durable
acknowledgement канонического владельца данных. Начавшийся `fetch`, ответ
промежуточного API Gateway или запись необязательной телеметрии не являются
подтверждением основной обратной связи.

Допустимые состояния:

| Состояние | Что видит пользователь |
|---|---|
| `committed` | «Отправлено» либо «Сохранено» |
| `local_pending` | «Сохранено на устройстве. Отправим после восстановления соединения» |
| `partial` | точный перечень отправленных и ожидающих компонентов |
| `ambiguous` | «Не удалось подтвердить отправку. Автоматически не повторяем, чтобы не создать дубль» |
| `retryable_failed` | операция остаётся в очереди с понятным статусом |
| `terminal_failed` | явная ошибка и безопасное действие восстановления |

### 5.2. Компонентные receipts

NPS, текст, structured event error, screenshot и analytics projection имеют
отдельные receipts. Например:

```text
nps: committed
text: committed
screenshot: retryable_failed
analytics: pending
```

Интерфейс в таком случае сообщает: «Оценка и текст отправлены. Скриншот ожидает
повторной отправки». Он не говорит ни «Всё отправлено», ни «Ничего не
сохранилось».

### 5.3. Idempotency и очередь

- каждое действие получает stable `action_id` один раз;
- повтор после reload/reconnect использует тот же идентификатор;
- payload не удаляется до server acknowledgement или явного terminal outcome;
- reconnect flush выполняется single-flight с bounded backoff и jitter;
- превышение TTL/attempt limit не должно молча удалить сообщение;
- YDB/telemetry failure не откатывает уже принятую NPS/текстовую обратную связь;
- screenshot direct-only failure не должен блокировать отправку текста.

### 5.4. Мисскоммуникация запрещена

Запрещено:

- показывать общий зелёный success, если screenshot или другой обязательный
  компонент не подтверждён;
- просить участника повторно отправить уже committed feedback;
- сообщать о потере основного действия из-за отказа служебной статистики;
- говорить «Яндекс не работает» по отказу конкретного relay/YDB endpoint;
- скрывать pending/ambiguous состояние за бесконечным spinner.

## 6. Полевая диагностика 2026-08-03

У одного участника Mobile Safari показал одновременно:

- прямой Supabase Auth/Data — доступны;
- Yandex relay Auth/Data — нет соединения;
- resilient Auth/Data — доступны через direct;
- YDB control/API Gateway — нет соединения.

Правильная продуктовая интерпретация:

> Основные функции доступны напрямую. Резервный маршрут и служебный канал
> Yandex с этого устройства сейчас не отвечают. Уже подтверждённые сайтом
> действия не требуется отправлять повторно.

Это не доказательство глобального падения всего Yandex. Диагностика должна
различать relay, YDB control, OAuth, Postbox и другие capabilities.

## 7. Требования к диагностической странице

- названия endpoints понятны и не маскируются абстрактными «второй путь» и
  «контрольный канал»;
- итог выделяет доступность **основных функций**, а затем перечисляет degraded
  optional/reserve capabilities;
- результат не отправляет писем и не изменяет пользовательские данные;
- PII-free receipt содержит код проверки, время, build/revision, состояния
  capabilities и выбранный route;
- receipt не содержит email, OTP, токены, текст feedback, screenshot URL или
  bearer secret;
- пользователь может безопасно скопировать строку результата или прислать
  скриншот;
- один failed control probe не делает весь итог красным, если core path
  подтверждён.

Требуемые подписи:

- «Резервный маршрут через Yandex»;
- «Данные через Yandex relay»;
- «Служебный канал YDB — не влияет на сохранение основных действий»;
- «Устойчивый вход/данные» — фактический итог после выбора direct/relay.

## 8. Обязательные сценарии

Помимо штатных journeys фокус-группы, до публичного rollout должны быть
реализованы и зарегистрированы:

1. relay/YDB недоступны, direct работает — truthful degraded copy и отсутствие
   потерь;
2. direct недоступен, relay работает — критические операции проходят через
   relay без дублей;
3. оба клиентских маршрута недоступны — no-mail, no-false-success, local pending;
4. текст feedback принят, screenshot недоступен — component partial state;
5. YDB analytics недоступна — основная обратная связь committed, projection
   pending;
6. reload/reconnect — один logical feedback создаёт один durable effect;
7. Yandex OAuth недоступен — email OTP остаётся доступным;
8. outbox переполнен/истёк — нет silent eviction, есть terminal disposition;
9. Android Emulator и iOS Simulator проверяют ту же семантику и системные
   клавиатуры там, где присутствует ввод.

## 9. Операторская статистика

Минимальный read-only отчёт должен различать:

- `committed` feedback;
- browser-local/server pending;
- partial component delivery;
- ambiguous operations;
- retry backlog/oldest age;
- terminal failures;
- YDB projection lag отдельно от количества основной обратной связи;
- duplicate prevention/idempotency hits;
- platform/network class и диагностический degraded class без PII.

Нулевой счётчик YDB во время её отказа нельзя интерпретировать как отсутствие
действий пользователей. Release/operator dashboard должен показывать backlog и
неполноту проекции.

## 10. Release boundary

Фокус-группа и публичный rollout получают `NO-GO`, если:

- основная обратная связь может потеряться при Yandex/YDB outage;
- UI подтверждает отправку до durable acknowledgement;
- partial component failure скрывается;
- один logical action может быть записан дважды;
- optional telemetry влияет на core route health;
- pending payload молча удаляется;
- изменён критический flow, но отсутствует terminal browser/Android/iOS evidence;
- диагностическая страница сообщает глобальный отказ вместо точной capability.

Сценарии и gates добавляются одновременно с реализацией функции; planned
coverage нельзя представлять как пройденное.
