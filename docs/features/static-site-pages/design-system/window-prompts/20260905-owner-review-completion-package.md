## Схема запуска и владения

Один основной кодовый агент отвечает за реализацию, интеграцию и готовый
к проверке кандидат. При реальной пользе — максимум два внутренних работника
с непересекающимися owning paths, в рамках действующего лимита контракта.
Не создавать дополнительный слой W0/W1/оркестраторов.

Два окна ChatGPT можно запустить параллельно с ним:
VISUAL — межстраничные роли, действующие основания и дизайнерские расхождения;
DATA — предметные вопросы к данным, счетчикам и семантике.
REVIEW запускается в отдельном независимом окне после нового real-кандидата.

Только CODE пишет runtime/components/foundations, объединяет патчи,
регенерирует существующие SoT outputs и обновляет текущий STATUS/AR-register.
VISUAL/DATA публикуют предметные результаты в #621, не меняют параллельно
те же файлы и не объявляют рекомендации принятыми владельцем.
При необходимости сохраняют большой пакет как отдельный evidence-артефакт,
а не создают альтернативный STATUS или registry.

Внутреннюю работу CODE делить по зависимостям, не по страницам.
Начальная разумная граница — shared cards/media/runtime и shell/actions/
keyboard. Общие foundations, интеграцию и итоговые generated files сохраняет
основной агент. Сначала проверить фактические пересечения; если два пакета
правят один owner, выполнять последовательно, а не плодить локальные копии.
Дочерние worktrees допустимы по правилам репозитория; общий delivery branch
остаётся существующим.

## CODE — комплексная задача кодовому агенту

Продолжи сохранённые исправления KenigEvents до одного проверяемого real-
кандидата с согласованными общими UI-ролями. Это полноценный инженерный цикл,
а не задача только на запуск тестов или публикацию чужого кода. Анализируй
неустановленные технические причины самостоятельно; не требуй компонентного
анализа от владельца. Не проектируй сайт или дизайн-систему заново.

Прочитай общие источники выше, инструкции репозиториев, применимые
static-site-design-system/static-site-autotest skills и существующие test /

Проверь реальную возможность выполнять исходники, браузерные действия,

редактор исходников; локальный кодовый runtime для этого и используется.

Переиспользуй уже установленные причины и доказательства. При старте запиши

переходи к реализации. Не заканчивай на плане и не требуй подтверждения на

### Объём результата

Обработай остаток AR-register и межстраничную согласованность общих ролей.
Список симптомов не ограничивает исправление причастного общего owner:
мигрировать нужно все его product consumers, а не только страницу с жалобой.
Обратное тоже верно: этот этап не разрешает произвольный редизайн или
переписывание несвязанных функций.

Для покрытия используй существующий product scope/consumer graph. Проверь,
что он не пропускает реально используемые роли и runtime consumers.
Прежние 11 диагностических маршрутов не являются полным определением scope.
Покрытие фиксируй в существующих спецификациях/AR-записях, не новом реестре.

**Общие роли.** Согласуй страницу-заголовок, раздел, карточку, body, metadata,
подпись контрола, поверхности, семантические цвета, отступы, формы, состояния
и иконки через существующих owners. Проверяется семантическая роль, не просто
тег h1/h2: редакционный hero, время на таймлайне и название карточки могут
быть разными ролями. Различия требуют основания в задаче/архетипе/состоянии;
факт старого наличия отдельного токена не является таким основанием.

VISUAL помогает подготовить матрицу оснований. До её получения продолжай
неоспоримые card/runtime/keyboard fixes. Не придумывай новую палитру. Если
существующие источники не разрешают существенное противоречие вроде темы
целой страницы, предъяви конкретное сравнение и минимальное решение по
протоколу действующего контракта. Не узаконивай случайный дизайн задним числом
и не останавливай из-за одного решения независимую работу.

**Карточки и медиа.** Устрани подтверждённые несовпадения внутренних media/
body tracks в flow/packed композициях, нерегулярные неполные ряды и проблемы
плотности/фрейминга. Внешнее равенство прямоугольников недостаточно. Сохрани
admission, предметно допустимый порядок, содержимое, важный текст афиш и
медальоны. Не выравнивай за счет удаления событий, опасного кропа, clipping
текста или увеличения единственной карточки. Проверь static, hydrated,
client-created и реально обновляющиеся consumers. Локальный профиль/фабрика
карточек — отдельная диагностическая ячейка, не замена organic feed.

**Поведение.** Закрой конкретные action/keyboard/event-detail gaps из
AR-register, включая событие5370, медальон, видимые подписи и смысловую
навигацию по чтению. Проверь cold/warm/loading, смену состояний и возврат.
Floating Island доведи схематически через существующий shell: состав,
действия, focus, состояния и неперекрытие, без окончательного визуального
стиля. Мобильная навигация обязательна. DATA возвращает фактический разбор
публичных/локальных счетчиков и подозрительных записей; не изобретай нулевые
public counts, не подменяй сущность события клубом/фестивалем в API.

**Данные.** Подтверждённые причины в exporter/runtime/adapter исправляй с
регрессией. Исходные факты, производство и DB не редактировать по догадке.
Недоступные доказательства отмечать конкретно; не объявлять их проверенными.
Исправление данных не должно незаметно менять контрольный before/after-срез.

### Рабочий цикл и проверки

На каждый законченный пакет: воспроизведение → owner/impact → исправление
источника и consumers → существующие регрессии → личный осмотр → commit →
remote read-back. Применяй version/migration rules действующего контракта;
не создавай второй checker, registry, пакет или build pipeline.

Усиль существующие тесты так, чтобы они обнаруживали известные false PASS:
неправильную роль при правильном token marker, override/наследование,
разные внутренние границы карточек при одинаковой внешней высоте,
растянутый singleton, скрытый вместо видимого проверяемый consumer,
перекрытие breadcrumb/control и правильный HTTP с неправильным назначением.
Ожидания не снимать с той же страницы автоматически как ее собственный эталон.

Проверяй 1440×900, 390×844, 1920×1080 и причастные breakpoint seams,
loaded/missing/broken media и длинный реальный контент. Не подменяй личный
визуальный осмотр отсутствием overflow. Native mobile-system evidence
определяется действующим scenario registry, а не desktop viewport.

Выбирай недорогие L0/L1 проверки по риску; не запускай полный каталог на
эмуляторах. После каждого изменения не нужна полная опубликованная сборка:
focused диагностика идёт по существующему пути. Перед передачей independent
review нужен настоящий интегрированный real-кандидат.

### Интеграция, сборка и конец задачи

Готовые проверенные пакеты согласованно интегрируй в executable trunk по
действующим правилам репозитория. Обновление ветки исходников не равно
переключению production. При наличии release-side effects или ограничений
не обходи их; сообщи точную границу, сохрани готовые изменения.

Полный опубликованный real-кандидат делай только существующим единым Kaggle-
путём. Первый причинный before/after — на том же snapshot, clock, slice300 и
полном product page-class scope. Если исходный snapshot недоступен, не
подменяй его незаметно свежим и не называй сравнение same-snapshot.
Свежие данные, когда они нужны для проверки исправления upstream, проверяй
отдельно с отдельной идентичностью и ясной причиной.

Регенерируй и проверь существующую source-bound структурную проекцию;
исторический packet для source8b не доказывает готовность нового SoT.
Полная материализация Penpot не нужна до этого ревью; A=S=P без P не заявлять.

Обнови STATUS, AR-register и целевую документацию/маршрутизацию по фактам.
Передай в #621 одну ссылку на кандидата, manifest, exact SHA/snapshot/clock,
покрытие ролей/consumers, тесты, browser evidence и явные остатки.

Агент не принимает свою работу за независимого ревьюера. Сначала передаётся
«кандидат для независимой проверки», не «нормализация завершена».
Замечания REVIEW возвращаются в эту же задачу и исправляются там. Без внешнего
вердикта честно укажи, что его ожидаешь; не имитируй автоматически работающие
окна ChatGPT. После успешной независимой проверки — сборка для owner review,
а не утверждение, что сам владелец её принял. Production не переключать.
