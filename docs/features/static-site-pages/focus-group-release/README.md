## 1. Простая модель программы

```text
нет метки
  → заглушка выключает интерфейс

приглашение / QR
  → локальная метка до 31 августа, 18:00
  → обычный статический сайт

неавторизованный участник
  → может тестировать сайт и отправлять локально устойчивую обратную связь
  → не участвует в розыгрыше

email / Яндекс подтверждён
  → серверный participant
  → артефакты, NPS и бонусные шансы могут войти в eligibility
```

Не создаётся отдельное приложение фокус-группы, сложный кабинет или серьёзный
периметр безопасности. Люди пользуются тем же статическим сайтом, который затем
может быть открыт публично.

## 2. Soft gate: заглушка действительно выключает интерфейс

Без метки обычная афиша визуально не показывается и не доступна с клавиатуры или
screen reader. Заглушка — единственная активная поверхность страницы.

Рекомендуемый технический контракт для SSG:

1. HTML может находиться в документе, потому что это не security boundary.
2. До первого paint короткий inline-controller читает локальную метку.
3. По умолчанию документ находится в состоянии `data-focus-locked`:
   - основной app shell скрыт;
   - основные landmarks получают `inert`/`aria-hidden`;
   - показывается заглушка.
4. Валидная метка снимает locked state и открывает обычный интерфейс.
5. При отключённом JavaScript остаётся заглушка.
6. Все prelaunch pages остаются `noindex,nofollow,noarchive` и не входят в
   публичный sitemap.

Если пользователь вручную изменил DOM/localStorage и снял заглушку, это не
считается взломом или инцидентом. Задача gate — не криптографическая защита, а
отсутствие случайного незавершённого запуска.

### Заглушка

```text
Полюбить Калининград · Анонсы

Анонсы готовятся к открытому запуску

Сейчас сайт проверяют участники фокус-группы. Приглашение или QR-код откроют
афишу на этом устройстве. Фокус-группа завершится 31 августа в 18:00, после чего
мы примем решение об открытом запуске.
```

Можно добавить одну короткую фразу о ценности сервиса и фирменную графику. Не
нужны публичная форма регистрации, обратный отсчёт до обещанной даты запуска или
описание внутренних тестов.

## 3. NPS виден постоянно, детали открываются по кнопкам

Внизу каждой поддерживаемой страницы, непосредственно перед footer, расположен
постоянно видимый NPS-блок. Шкала `0–10` доступна сразу, без открытия modal или
нажатия «Оценить».

Пользовательский поток:

```text
видит 0–10
  → нажимает число
  → ответ сразу сохраняется/ставится в outbox
  → шкала сворачивается в «Ваша оценка: N · Изменить»
  → при желании открывает текст или добавляет скриншот
```

Отдельных видимых анкет «общий NPS», «полезность», «предложение» и «ошибка
события» нет. Подробный макет и обоснование по реальным NPS-паттернам — в
[`nps-ui.md`](nps-ui.md).

## 4. Что собирается

Минимальный feedback row:

```text
participant/device subject
score 0–10
optional text
optional private screenshot
page_family
page_path
page_revision
release_sha
event_id nullable
client_request_id
created_at
```

`page_revision` и release SHA не видны пользователю. Они нужны, чтобы:

- снова предложить NPS после содержательного обновления страницы;
- не смешивать оценки разных версий интерфейса;
- понять контекст текста или скриншота.

Повторная доставка одного `client_request_id` создаёт одну запись. При отсутствии
сети UI честно говорит, что ответ сохранён на устройстве и будет отправлен
позже.

## 5. Статистика: собираем, но не строим отчётную систему

Отдельный ежедневный workflow, JSON и Markdown-отчёт не являются требованием.
Владельцу достаточно в любой момент попросить кодового агента выполнить
read-only запрос к Supabase/операторским таблицам и объяснить результат.

Поэтому до seed необходимо обеспечить только:

- нормализованные и документированные поля;
- service-role/read-only путь запроса;
- отсутствие PII в ответе, если запрос предназначен для передачи в чат;
- корректную связь participant → NPS/text/screenshot → artifacts → chances;
- возможность проверить полноту и дубли.

Не нужен data warehouse, scheduled digest или отдельная витрина статистики.

## 6. Артефакты и розыгрыш

В существующем прототипе уже зафиксированы 12 артефактов `FG-E01…FG-E12`.
Порог `80%` означает 10 находок.

Eligibility:

- подтверждённый email или Яндекс;
- успешная серверная registration;
- минимум 10 из 12 server-receipted артефактов;
- хотя бы один NPS-ответ до cutoff.

Шансы:

- 1 базовый;
- +1 за наличие принятого непустого текста;
- +1 за наличие принятого скриншота;
- максимум 3.

Так обратная связь действительно повышает шанс, но количество сообщений не
стимулирует спам и оператор не оценивает «качество» мнения.

Cutoff и автоматический draw — 31 августа 2026 года в 18:00 по Калининграду.
Победитель получает письмо и имеет 3 календарных дня на ответ. После финального
подтверждения всем подтверждённым участникам отправляется благодарность и
сообщение о победителе.

## 7. Минимальный backlog до первой волны

1. **FG-01 — soft gate:** общий locked state, актуальная заглушка, fixed cutoff.
2. **FG-02 — NPS UI:** постоянно видимая шкала, numeric saved state, optional
   text/screenshot buttons, revision contract.
3. **FG-03 — Auth acceptance:** final browser/Android/iPhone/Yandex paths.
4. **FG-04 — PWA return:** Android install/relaunch и честный iPhone home-screen
   path.
5. **FG-05 — key journeys:** Share, Calendar, «Не интересно», «Для меня».
6. **FG-06 — artifacts:** 12 server receipts, progress 10/12, eligibility.
7. **FG-07 — queryable stats:** read-only запрос проверяет данные без отдельного
   report workflow.
8. **FG-08 — prize:** published rules, immutable snapshot, weighted draw,
   reserve participant and email lifecycle.
9. **FG-09 — rehearsal:** один полный exact-target synthetic прогон и cleanup.

## 8. Ворота запуска

### Seed 20–30 участников

Нужны terminal PASS для FG-01…FG-09. Допустим один явно документированный iPhone
fallback, если native OTP keyboard остаётся дефектным, но email magic link или
Яндекс реально проходят на iPhone.

### Расширение до 80

- нет массовой P0/P1 проблемы;
- feedback не теряется и не дублируется;
- code-agent query возвращает непротиворечивые counts;
- оператор успевает просматривать тексты/скриншоты.

### Расширение до 200

- cap проверен на границе;
- PWA return и Auth стабильны;
- server artifact receipts считаются корректно;
- draw rehearsal выполнен на synthetic snapshot.

## 9. Что намеренно не строим

- серьёзный auth-proxy для всего статического HTML;
- множество пользовательских feedback-форм;
- публичный leaderboard;
- ежедневные отчётные artifacts;
- сложную систему приоритетов и SLA;
- массовые mobile-emulator прогоны всего каталога;
- оценку полезности/тона текста для шансов в розыгрыше.
