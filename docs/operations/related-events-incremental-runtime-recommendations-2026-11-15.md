# KenigEvents — рекомендации по инкрементному расчёту похожих событий

**Дата аудита:** 15 ноября 2026 года (Europe/Kaliningrad)  
**Статус:** технические рекомендации, **не** отчёт о внесённых исправлениях или об успешном восстановлении production.  
**Репозиторий:** [onedayonemasterpiece/events-bot-new](https://github.com/onedayonemasterpiece/events-bot-new).  
**Затрагиваемые потребители:** карточки похожих событий для VK и «Похожие» на статическом сайте KenigEvents.

## 1. Решение в одном абзаце

Сохранить **один существующий Kaggle-исполнитель**, текущие алгоритмы retrieval/reranking, строгую семантическую проверку, pgvector, существующие векторы и durable single-flight. Изменить **единицу инкрементальности** с «весь каталог / один завершённый JSON» на **отдельное изменившееся событие (anchor) с версионированным результатом**. Для новых или семантически изменённых событий искать кандидатов **среди всего актуального каталога**, а проверять и сохранять только затронутые подборки. VK получает готовую подтверждённую подборку сразу, не ожидая обработки остальных событий и не завися от Astro. Сайт читает тот же принятый набор, а не заново запускает модель.

**Ключевое ограничение владельца:** никаких плановых полных перерасчётов эмбеддингов, повторных дорогостоящих аудитов всех 724 событий, обхода квот, второго Kaggle-исполнителя или второго writer. Полный пересчёт допустим лишь при доказанной несовместимости контракта/модели, по отдельному управляемому решению и бюджету.

### 2.1. Причина из кода

В [экспортёре](../../site/scripts/export-production-preview-data.py) кеш `cache_valid` требует равенства `event_ids`, **всех** `event_fingerprints` и глобальной `related_corpus_revision`. При его промахе `build_pgvector_related_chain(events, ...)` заново проходит по `events`; внутри цикла выполняет RPC `COMPACT_RELATED_RPC` отдельно для каждого anchor. Это **не** значит, что все эмбеддинги заново генерируются, но повторно инициируется поиск соседей по всем событиям.

Следовательно, одно добавленное/изменённое событие способно инициировать O(N) RPC для существующего N-каталога вместо O(Δ) для новых/изменённых anchor, а единый `event_related.json` выдаётся потребителю лишь после завершения соответствующей общей работы.

**Важное ограничение исправления:** передать только 20 новых событий в старый аргумент `events` **нельзя**. Эта коллекция одновременно служит и списком anchor, и разрешённым множеством кандидатов (`by_id / allowed_ids`). Такое «ускорение» отрежет старые релевантные события. Нужно разделить множества семантически и на уровне интерфейса.

### 2.2. Уже исправленное — не реализовывать повторно

PR [#974](https://github.com/onedayonemasterpiece/events-bot-new/pull/974), [#975](https://github.com/onedayonemasterpiece/events-bot-new/pull/975), [#976](https://github.com/onedayonemasterpiece/events-bot-new/pull/976) затрагивали сохранение прогресса/отказ от лишних ворот и порядок vector → related; в действующей документации явно предусмотрено выполнение готовой related-задачи перед новым vector sync. **Это не обеспечивает инкрементальность per-anchor и не устраняет ожидание общего артефакта.** Не возвращать прежнюю гонку в попытке просто убрать `static_build_active`.

## 3. Целевой контракт

| Аспект | Сейчас / риск | Требуемое поведение |
| --- | --- | --- |
| Цель расчёта | Весь `events` | `anchor_event_ids` = ID новых/семантически изменённых/затронутых событиями-кандидатами |
| Источник кандидатов | Тот же `events` | `candidate_universe` = все допустимые актуальные события; не сужать до Δ |
| Эмбеддинги | Хеш по событию и виду документа уже есть | Переиспользование при совпадении текста, версии входа и модели; **нулевые** вызовы для неизменившегося документа |
| Поиск соседей | RPC на каждый anchor при глобальном cache miss | RPC только на изменённые и доказанно затронутые anchor; для остальных — сохранённый результат |
| Gemma | Может удерживать полный пакет; ошибки/тайм-ауты | Проверка только новых или изменённых пар/списков с текущей политикой и ограниченным бюджетом; поштучная фиксация успеха |
| Сохранение | Общий JSON и глобальный кеш после завершения работы | Durable versioned result для каждого anchor, подтверждённый входным снимком/ревизией и алгоритмом |
| VK | Ждёт общий расчёт | Берёт готовый результат anchor без ожидания чужих anchor и без зависимости от Astro |
| Статический сайт | Может инициировать общий расчёт | Использует те же принятые подборки; собственные HTML/JSON строятся отдельно |
| Перезапуск | Общий запуск способен застрять на recovery/adoption | Не терять уже принятые anchor; после recovery продолжать только недостающие |
| Квота | Большие пакеты расходуют суточные запросы | Явное admission по фактической квоте, нет повторов без изменения входов, нет тайного full rebuild |

Под «готовым результатом» понимается валидный результат **именно для данной версии anchor, набора кандидатов и политики**. `verified_empty` (модель проверила, подходящих нет) отличается от `not_computed` / `provider_error`; отсутствие кандидатов нельзя выдавать за удачную проверку. Поведение VK при `verified_empty` сохраняет действующий продуктовый контракт; не ослаблять его неявным fallback.

## 4. Рекомендуемая схема — один исполнитель, два потребителя

1. **Effectful изменение события** в canonical SQLite формирует компактную запись `event_id + semantic_input_hash + change_kind`; изменения фото/URL/метрик, не влияющие на смысл, не вызывают новый embedding или semantic audit.
2. **Векторный этап** сравнивает `search_v3` и `related_v1` по **собственным** текстовым хешам, версии контракта и модели. Только cache misses проходят через действующий Google shared limiter и записываются в Supabase. При неизменности — ноль provider calls.
3. **Планировщик вычисляет anchor delta**: новые/изменённые события и ограниченный impacted-set (см. `5). Сохраняется existing single-flight; не создаётся отдельный Kaggle kernel, новая очередь конкурентных writer или второй процесс синхронизации.
4. **Тот же Kaggle, профиль related-only**, получает неизменяемый snapshot и список anchor, но использует полный candidate universe. Находит pgvector-соседей, применяет текущие фильтры (даты, серии/«Другие даты», eligibility, исключения), ранжирование и семантическую проверку.
5. **Поштучная приёмка**: по каждому полностью проверенному anchor формируется валидируемый hash-bound receipt. Авторитетный host принимает idempotent CAS по версии; ошибки других anchor не отменяют уже принятую работу. Вход/выход и происхождение проверки должны быть связаны с immutable run. Промежуточный результат не должен обходить текущую проверку целостности JSON и источник данных.
6. **VK consumer** читает готовую подборку конкретного anchor. **Site consumer** формирует статические файлы из тех же результатов. Новые события, поступившие после заморозки Kaggle snapshot, попадают в следующий обычный Δ-проход, а не изменяют вход текущего.
7. **Восстановление** после сбоя сверяет результат с canonical store; повторно запрашивает модель только для непринятых/устаревших версий и не допускает позднего результата поверх свежего.

Схема хранения может быть реализована поверх существующего валидируемого кеша и SQLite-таблицы статусов; **новый распределённый сервис и новая инфраструктура не требуются**. Проектное решение о размещении authoritative receipt нужно принять в рамках одного PR после проверки текущих контрактов, без дублирования источников истины.

## 5. Правильная инкрементальность при появлении новых соседей

Недостаточно обновить рекомендации только нового события: оно может стать лучшим кандидатом в выдаче старого anchor.

**Затронутое множество (`impacted-set`):**

- Каждый новый/семантически изменённый anchor.
- Существующие anchor, чья сохранённая top-K выдача включает изменённого/удалённого кандидата (обратный индекс использований).
- Существующие anchor, в чью top-K выдачу **может** войти новое событие (вычислить ближайших к новому вектору по текущему pgvector и проверить порог входа/top-K), с учётом фильтров eligibility и взаимности графа.
- Anchor, затронутые переходом даты, завершением/отменой, merge/alias, сменой допустимости, изменением релевантного времени/места.

Использовать существующие индексы и векторы. Отдельно проверить совместимость scoped-обработки с `apply_pgvector_graph_reciprocity`: нельзя менять правила взаимности молча. На тестовом замороженном каталоге результат scoped-обновления должен быть эквивалентен эталонному полному расчёту для затронутых anchor; сам эталон выполняется **локально на fixture/сохранённых векторах**, без новых Google/Gemma вызовов.

Если безопасное определение impacted-set пока не доказано, первая поставка должна хотя бы ускорить **первую публикацию новых anchor** при сохранении старых списков с явной меткой свежести, а не выдавать её за полную инкрементальность.

## 6. Ограничение расходов на модели — обязательный инвариант

- **Запрет планового full re-embedding.** Для warm/обычного прохода считать отдельно `new_documents`, `changed_related_v1`, `changed_search_v3`, `reused_vectors`, `provider_calls`. Число вызовов может быть больше количества новых событий только при объяснимых отличиях документов/видов; каждый вызов имеет конкретный `event_id + doc_kind + text_hash`.
- **Нулевой повтор:** неизменные текст/модель/контракт => 0 Google embedding calls, 0 Gemma calls, 0 повторных pgvector RPC по незатронутым anchor.
- **Квоты важнее графика.** Соблюдать существующий общий лимитер RPM/TPM/RPD, запрет обхода через смену ключей/проектов; при `429` фиксировать `quota_blocked`, оставлять подтверждённые результаты доступными и возобновлять после фактического admission. Не делать цепочки retry, потребляющие новую суточную квоту ради недоказанного улучшения.
- **Семантический аудит** кешировать по версии модели, policy signature, anchor hash, ID/хешам реально предъявленных кандидатов. Изменение кандидатов не оправдывает повторную проверку всех anchor. Строгий режим `gemma_verify` и пороги не ослаблять ради выпуска.
- **Бюджет прогонов:** лимит anchor/пар, wall-time, provider calls и retry на одну волну. Значения выбрать по фактическим лимитам и наблюдениям, не использовать прежние `1000` как разрешение тратить 1000 вызовов каждый проход. В отчёте обязательно прогноз «сколько новых вызовов требуется до запуска».
- **Полная синхронизация** возможна только как отдельно санкционированная миграция изменившегося контракта; до неё — dry-run с diff хешей и стоимостью. Смена версии без обоснования не должна инвалидировать весь кеш.

## 7. Очереди, сбои и честные статусы

Сохранять уже реализованные immutable snapshot, single-flight, exact run/dataset adoption, CAS и guards. Пересмотреть **границы** guard, а не просто отключать его:

- Векторный этап должен быть способен обслужить следующую Δ-волну после фиксации необходимого согласованного snapshot, не дожидаясь Gemma по предыдущей волне; при этом текущий Kaggle читает свою неизменяемую версию.
- По одному anchor допустимы `ready_verified`, `ready_verified_empty`, `pending_vector`, `pending_retrieval`, `pending_audit`, `quota_blocked`, `retryable_error`, `superseded`; эти состояния явно отображать в диагностике. Не путать «полностью обработан» с «обработан весь снимок».
- При частичном успехе 10 из 30, после отказа модели/перезапуска **10 сохраняются**, остальные 20 продолжают работу без дублирования принятых вызовов.
- Поздний результат старой ревизии не затирает более новый; очередь может coalesce дубли, но не теряет ID, для которых есть незавершённые обязательства.
- Для public VK фиксировать отдельное состояние: `similar_ready`, `vk_postponed`, `vk_live`, `vk_captcha_wait`. CAPTCHA не может помечаться как «похожие не готовы».
- No-op и восстановление должны сохранять принятые сертификаты/хеши, а не инициировать повторный Kaggle или повторную проверку без изменения входа.

## 9. Проверки приёмки (все обязательные)

| Сценарий | Проверяемый результат |
| --- | --- |
| Новое событие A, 724 старых | Retrieval по A ищет среди A + старых; реально может выбрать старое событие. Число RPC по неизменным 724 — **0**. |
| 20–30 новых событий за проход | Размер работы масштабируется по Δ + доказанному impacted-set, а не по N=724; в отчёте отдельно RPC, provider calls, секунды и количество готовых anchor. |
| Повтор тех же входов | **0** новых embedding calls, **0** Gemma calls, **0** повторных retrieval RPC; принятый результат и хеш неизменны. |
| Правка только фотографии/ссылки | **0** новых embedding calls/semantic audit, если смысловые поля не изменились. |
| Новый сильный сосед для старого B | B включён в impacted-set и обновлён; не требуется повторять проверку всех старых событий. |
| Нет подходящих соседей | `verified_empty` подтверждён реальным завершением проверки; не подменяется тайм-аутом или пустым необработанным кешем. |
| Ошибка/429 у anchor C | Готовые A/B доступны потребителям; C остаётся в явном блокированном состоянии; никаких обходов квоты. |
| Остановка после 10 готовых из 30 | После восстановления принятые 10 не переделываются и не перезапрашивают модель; остальные продолжаются идемпотентно. |
| Смена ревизии во время Kaggle | Старый receipt не перезаписывает новый; более позднее событие попадает в следующую Δ-волну. |
| Сайт | На одном и том же входном снимке сайт использует те же validated related IDs/версии, что и VK, без новых вызовов модели. |
| Два **естественных** последовательных импорта | Для каждого выбранного свежего anchor есть готовый принятый результат и фактический публичный VK readback с корректной карточкой; CAPTCHA проверяется отдельно. |
| Возврат к штатному расписанию | Нет зависшей `static_build_active`/vector barrier, нет второго writer, нет растущей очереди без прогресса; каждое ограничение имеет код причины и время следующего допустимого действия. |

**Предлагаемые SLO (целевые, не якобы измеренные):** при доступных квотах — p95 от фиксации нового события до `similar_ready` ≤5 минут, для полного cache hit ≤60 секунд; метрика «возраст самого старого ожидающего первого VK-поста» обязательна. Перед утверждением SLO снять baseline и разделить собственное время расчёта, ожидание модели, Kaggle scheduling и VK CAPTCHA.

Результат **не принимать** по одному успешному ручному прогону, зелёному `/healthz`, наличию JSON или одному опубликованному вчера посту.

## 10. Instrumentation / минимальный отчёт прохода

Для каждой волны сохранять структурированный receipt:

- `snapshot_id`, `repo_sha`, `input_watermark`, время, `anchor_count`, `candidate_universe_count`, `impacted_count`.
- `new_embedding_calls_by_kind`, `reused_embeddings_by_kind`, `quota_remaining/blocked_reason`, без ключей и секретов.
- `retrieval_rpc_count`, `retrieval_cache_hits`, `gemma_calls`, `gemma_cache_hits`, `gemma_errors`, частота ошибок/тайм-аутов.
- `accepted_ready`, `verified_empty`, `pending` по причинам, `oldest_pending_age`, `published_vk_with_card` и `published_vk_without_card` с утверждённым основанием.
- Время `vector_ready` → `retrieval_ready` → `audit_ready` → `host_accepted` → `vk_live`; отдельно время website build.

Сделать простой нулевой dry-run, показывающий, **что** требует пересчёта и **сколько** запросов будет сделано до старта, без фактических Google/Gemma/Kaggle вызовов.

## 12. Чего не делать

**Не делать** новую векторную базу, дублирующий Kaggle pipeline, фоновые full rebuild «на всякий случай», повторную генерацию BGE/Gemini для неизменившихся документов, автоматическое повышение квот, обход ключами, невалидированное потребление промежуточного JSON, отключение защит по ревизиям, публикацию непроверенных кандидатов под видом строгой похожести, искусственное ожидание «пустого» production или отчёт об успехе до настоящего E2E.

**Готовность к реализации:** документ фиксирует контракт и критерии; изменение кода и production-релиз должны оформляться отдельно и подтверждаться фактическими readback/метриками.
