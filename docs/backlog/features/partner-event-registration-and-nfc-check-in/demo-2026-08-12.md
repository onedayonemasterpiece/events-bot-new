> **Критерий успеха:** показан один воспроизводимый сквозной путь от включения регистрации партнёром до XLSX фактической явки.

## Что именно должно быть доказано

Демонстрация не должна быть набором несвязанных экранов. Она доказывает один vertical slice:

1. партнёр сам включает регистрацию у существующего события;
2. пользователь регистрируется на static-first странице;
3. предзаполненное невалидное ФИО обнаруживается до отправки и исправляется пользователем;
4. зарегистрированный пользователь касается NFC-метки и автоматически получает check-in;
5. второй пользователь приходит без регистрации, касается той же метки, регистрируется и чекинится в одном потоке;
6. система показывает идемпотентность повторного касания;
7. система формирует XLSX регистраций и XLSX фактических check-in;
8. оба файла доставляются на email партнёра, а delivery receipt доступен в evidence.

## Demo boundary

### P0 — обязательно к 11 августа

- event occurrence с точным временем и `Europe/Kaliningrad`;
- защищённая партнёрская ссылка управления одним событием;
- включение/выключение регистрации и настройка email получателя;
- runtime manifest, по которому static event page показывает форму;
- авторизованное предзаполнение;
- full-name preflight с состоянием `correction_required`;
- обычная регистрация и отмена либо хотя бы безопасная деактивация тестовой записи;
- NFC NDEF URL и QR fallback на тот же opaque checkpoint token;
- check-in зарегистрированного пользователя;
- атомарный walk-in `register + check-in`;
- идемпотентность повторного tap;
- XLSX generator для `registrations_t_minus_1h` и `checkins_t_plus_30m`;
- email delivery с terminal receipt;
- E2E evidence и presentation deck.

### P1 — только если P0 полностью закрыт

- Telegram-дубль XLSX;
- MAX-дубль XLSX;
- capacity/waitlist;
- партнёрская заявка на новое событие;
- сохранение исправленного ФИО в глобальный профиль;
- ручной check-in оператором;
- rotating checkpoint token.

P1 не имеет права задержать либо дестабилизировать P0.

## Минимальный технический контракт

Названия endpoints могут измениться, но responsibility boundary должен сохраниться:

- `GET registration-config` — публичная безопасная конфигурация формы без PII;
- `POST registrations` — регистрация с consent version и idempotency key;
- `POST registrations/{id}/cancel` — отмена/деактивация;
- `GET check-in/{opaque-token}` — загрузка безопасного контекста event/checkpoint;
- `POST check-ins` — идемпотентная фиксация либо transaction `register + check-in`;
- `GET/POST partner event registration config` — управление только разрешённым occurrence;
- scheduler command для `T-1h` и `T+30m`;
- report generator и delivery worker с receipt.

Демо-ускорение времени допускается только через явно test-only clock/command. Оно не должно менять production semantics и должно быть видно в evidence. Нельзя выдавать ручной вызов двух генераторов за доказательство работающего production scheduler: в презентации это маркируется как проверка генератора, а scheduler contract доказывается отдельным тестом.

## Подготовка физических материалов

К 11 августа должны быть готовы:

- одна запрограммированная NFC-метка с NDEF HTTPS URL;
- карточка/табличка с NFC-меткой и напечатанным QR fallback;
- Android-устройство с включённым NFC и браузером, на котором пройден реальный tap;
- резервное устройство либо заранее проверенный QR flow;
- тестовое событие и два тестовых пользователя;
- подтверждённый email партнёра;
- локально сохранённые копии обоих XLSX на случай задержки внешней почты, при этом live delivery всё равно должна быть отдельно доказана receipt.

NFC-демонстрация считается честной только после физического чтения метки устройством. Простое открытие URL вручную доказывает web flow, но не доказывает NFC carrier.

## Demo script

### Сцена 1. Партнёр включает регистрацию

- открыть защищённую ссылку управления;
- показать название и occurrence события;
- задать окно регистрации, окно check-in и email;
- включить регистрацию;
- открыть публичную страницу и показать появившийся модуль.

### Сцена 2. Предзаполнение и исправление ФИО

- войти тестовым пользователем, у которого профиль содержит очевидно непригодное значение;
- показать предзаполнение и состояние `Требуется исправить ФИО`;
- исправить значение;
- показать точную строку, которая попадёт организатору;
- подтвердить и зарегистрироваться;
- показать registration state.

### Сцена 3. NFC auto check-in

- коснуться физической NFC-метки Android-устройством;
- показать, что открыто именно нужное событие;
- дождаться автоматического идемпотентного POST;
- показать `Вы на месте`, timestamp и метод `nfc`;
- коснуться повторно и доказать отсутствие второй записи.

### Сцена 4. Регистрация на входе

- открыть NFC/QR flow на устройстве без существующей регистрации;
- заполнить компактную форму;
- подтвердить ФИО;
- получить единый результат `Регистрация создана · Вы на месте`;
- показать, что в хранилище одна registration и один check-in.

### Сцена 5. Отчёты партнёру

- показать `T-1h` workbook и его листы;
- показать `T+30m` workbook с фактическими check-in и walk-in count;
- открыть письмо партнёра либо delivery evidence;
- показать terminal receipt без вывода секретов;
- связать содержимое XLSX с действиями двух тестовых пользователей.

### Структура презентации

1. **Проблема организатора:** регистрация и фактическая явка живут отдельно, ручные списки устаревают.
2. **Продуктовое обещание:** регистрация на странице события, tap на входе, два готовых списка.
3. **Путь пользователя:** заранее зарегистрирован / пришёл без регистрации.
4. **Live demo:** partner enable → registration → NFC → walk-in → XLSX.
5. **Почему static-first сохраняется:** публичный HTML статический, мутации и PII изолированы в runtime.
6. **Качество данных:** предзаполнение не равно истине; пользователь подтверждает экспортируемое ФИО.
7. **Ценность партнёру:** ожидаемые участники, реальная явка, простое self-service включение.
8. **Безопасность и надёжность:** opaque token, time window, idempotency, no PII in URL/static/analytics, delivery receipt.
9. **Следующий этап:** партнёрский event intake с source provenance и редакционным gate; Telegram/MAX; production hardening.

Слайды не должны подменять live evidence мокапами. Макеты допустимы только для явно отмеченного post-demo scope.

## Основные риски и защита от ложного пути

| Риск | Решение до demo |
| --- | --- |
| строить полноценный кабинет вместо vertical slice | scoped partner link только к одному occurrence |
| NFC превращается в отдельное native-приложение | обычный NDEF HTTPS URL, web runtime, QR fallback |
| предзаполнение выдаётся за достоверное ФИО | обязательный preview и correction gate |
| форма утягивает PII в static build/analytics | runtime-only PII, `no-store`, sanitized telemetry |
| отчёты существуют только как локальный файл | email delivery + terminal receipt |
| ручной trigger выдают за scheduler | раздельно доказать generator и scheduler semantics |
| event creation раздувает MVP | только existing-event enablement; intake — P1 |
| Telegram/MAX задерживают обязательную доставку | email P0, дополнительные каналы P1 |
