# «Тема дня — Калининград»

> Статус: **docs-first / discovery, без реализации**. Рабочий slug: `topic-of-the-day-kaliningrad`. Канал, VK-сообщество, YDB-таблица, Kaggle kernels, токены и публикации в рамках этой задачи не создаются.

## Замысел

Новый канал выпускает не более одного редакционного дайджеста в день о главном событии или явлении, которое накануне независимо освещали региональные авторы и паблики Калининградской области.

Публикация должна:

- кратко объяснить саму тему и отделить подтверждённые факты от мнений;
- показать, **кто и чем был полезен**: дал больше фактов, сильнее объяснил, показал лучшие медиа, снял видео, высказался эмоциональнее или конструктивнее, собрал больше обсуждения;
- вплести ссылки на оригинальные публикации прямо в текст;
- завершиться компактным перечислением остальных источников, которые писали о теме;
- учитывать видимые `views`, реакции/лайки, репосты/пересылки и комментарии, но не превращать популярность в единственный критерий;
- не повторять уже опубликованную тему без существенного нового развития;
- выпускаться в Telegram, а затем в VK в формате карусели.

## Главные продуктовые решения

1. **Ищем не буквальное большинство постов, а наиболее широко поддержанную независимыми источниками тему.** Один крупный паблик и десять его репостов не считаются десятью голосами.
2. **Два embedding-моделя — recall, а не финальный редактор.** `multilingual-e5-base` и `bge-m3` находят соседей; LLM проверяет границы кластера, формулирует тему, факты, расхождения и роли авторов.
3. **Один источник/владелец даёт кластеру максимум один голос.** Несколько постов одного автора объединяются; сети зеркал и репосты схлопываются в одну ownership-группу.
4. **Метрики сравниваются с собственным бейзлайном источника и возрастом поста.** Сырые просмотры разных пабликов несопоставимы; они используются как ограниченный дополнительный сигнал.
5. **«Антивектор» — не один отрицательный вектор.** Нужна память опубликованных тем: точные идентификаторы, структурированный fingerprint, два вектора и LLM-проверка, появилось ли материально новое развитие.
6. **Зафиксировано: `0..1` публикация в день.** Пустой день допустим: при слабом покрытии, неясной теме, конфликтующих фактах или повторе автопубликация запрещена.
7. **Новая фича живёт в отдельном проекте/runtime.** Для MVP допустимо использовать ту же физическую YDB, но только через отдельную таблицу/namespace и отдельный service account; Region Talk читается по versioned read-only contract.
8. **В YDB сохраняется только ценное долговечное состояние.** Сырой дневной корпус, все embeddings и временные media scores живут в сжатых run-artifacts с TTL. В БД остаются run summary, top candidates, publication ledger и компактная память опубликованных тем.
9. **Оркестратор управляет DAG, Kaggle выполняет тяжёлую работу вплоть до публикации.** Внешний publish вызывается только отдельным финальным Kaggle stage после immutable publication pack, policy/approval gate текущего режима, lease и idempotency gate.
10. **Формулировка «наиболее…» относится только к реально просмотренному корпусу.** Нельзя выдавать вывод за мнение всего региона, если часть источников недоступна.
11. **Зафиксировано: на каждое используемое source photo наносится видимая прямая ссылка на оригинальный пост.** Та же ссылка остаётся кликабельной в тексте публикации; подпись на изображении не заменяет rights/safety gate.
12. **Зафиксировано для начального rollout: публичный выпуск отправляется после просмотра и ручного одобрения.** Это временный canary gate, а не постоянный режим продукта.
13. **Зафиксировано: можно использовать любое фото из публичного source post.** На изображении обязательна прямая ссылка на оригинальный пост; private/deleted/unavailable и safety-blocked media не используются.
14. **Зафиксировано: официальные ведомства и организаторы тоже дают голос теме.** Для них действует то же ограничение — максимум один голос на ownership group.
15. **Зафиксировано для ручного canary: просмотр и approve проходят в закрытом Telegram admin-чате двумя кнопками.** Единственный разрешённый администратор принимает решение один; второго голоса не нужно.
16. **Зафиксировано: целевое время выпуска — 10:00 `Europe/Kaliningrad`.** Если manual approve пришёл позже, выпуск публикуется сразу после approve.
17. **Зафиксировано: происшествия, политика, конфликты и криминал обычно исключены.** Допускается узкое краеведческое исключение, когда центральная тема — судьба местного наследия, например снос здания — объекта культурного наследия (ОКН).
18. **Зафиксирован приоритет: как можно быстрее перейти к full auto.** Activation gate — 10 подряд рассмотренных editions без критических ошибок и зелёный live E2E; после этого система автоматически публикует high-confidence выпуск в 10:00, а ambiguous/no-topic cases безопасно пропускает.
19. **Зафиксировано: heritage/ОКН exception входит в full auto сразу.** Дополнительный ручной набор примеров для этой категории не требуется; общие scope/fact/safety gates сохраняются.
20. **Зафиксировано: full auto не отправляет предварительный admin-alert и не ждёт cancel window.** При успехе достаточно самой публичной публикации; внутренний ledger/audit artifact сохраняется молча.
21. **Зафиксировано: `no_topic` не проходит молча.** В закрытый Telegram admin-чат отправляется служебное уведомление о пропуске дня.
22. **Зафиксировано: Telegram и VK — независимые publication targets.** Успех, ошибка, reconcile и retry одного канала не блокируют и не повторяют другой.
23. **Названия/адреса Telegram-канала и VK-сообщества отложены.** Архитектура использует target ids/config и не фиксирует branding заранее.
24. **Зафиксировано: `no_topic` notification содержит краткую причину.** Длинный отчёт и список альтернатив в Telegram не нужны; полные evidence остаются во внутреннем artifact.
25. **Зафиксировано: Telegram публикует только одну Bento-карточку.** Формат — один `sendPhoto` с caption; Telegram album и отдельная отправка исходного видео не используются.
26. **Зафиксировано: retries ограничены и зависят от класса ошибки.** Transient failure получает несколько попыток, permanent/auth/permission/captcha/invalid-payload прекращает target сразу, а unknown send outcome сначала reconciles и не повторяет public send вслепую.

## Граница проекта и переиспользование

Документация временно хранится в `events-bot-new`, но реализация должна быть выносимой:

```text
events-bot / Region Talk YDB (read-only source catalog + optional post evidence)
                         │ versioned compact export/read contract
                         ▼
topic-day orchestrator (отдельный проект, расписание, run/lease state)
                         │ immutable per-run inputs
                         ▼
Kaggle: corpus → E5+BGE → clusters → LLM roles → media/render → publish
                         │
                         ▼
topic_day_state_kv + Telegram/VK publication ledger
```

Не следует:

- добавлять таблицы фичи в core Fly SQLite;
- использовать Supabase персонализации как очередь или operational ledger;
- писать обратно во внутренние row kinds Region Talk;
- копировать весь Region Talk YDB в новый проект;
- сохранять каждую картинку, pairwise similarity или embedding отдельной строкой БД.

## Что уже можно считать доказанным

- В репозитории есть рабочие шаблоны запуска Telegram/Kaggle, status callback, heartbeat, resource lease, immutable per-run input и артефактов.
- Region Talk на реальном корпусе показал практическую ценность двух независимых vector lanes и то, что keyword-only recall недостаточен.
- В проекте уже используется per-source/per-age нормализация просмотров и лайков (`docs/features/post-metrics/README.md`).
- Есть проверенные Telegram/VK publisher primitives, но их нельзя считать готовой публикацией именно для нового канала без отдельного live dry-run.

## Что пока не доказано

- выбор одной главной локальной темы из всех постов за сутки;
- качество topic clustering и пороги «достаточного большинства»;
- точность ролей «самый фактичный / компетентный / эмоциональный / конструктивный»;
- антиповтор против истории нового канала;
- стабильный сбор комментариев и пересылок для всех типов источников;
- качество media scoring на локальном новостном/блогерском корпусе;
- bento-карточка, медальоны и VK-карусель нового бренда;
- полностью автоматическая публикация без ручного gate.

## Базовый пользовательский результат

```text
Тема дня: [краткая нейтральная формулировка]

[2–4 предложения сводки: что произошло/обсуждалось, что подтверждается
несколькими независимыми источниками, где есть расхождения.]

[Имя/паблик со ссылкой] подробнее других собрал факты, а
[имя/паблик со ссылкой] показал наиболее сильные кадры. Практические
последствия яснее разобрал [источник со ссылкой]; больше всего обсуждали
[публикацию со ссылкой].

Также о теме писали: [ссылки без повторения уже названных авторов].
```

Публичный текст не показывает внутренние scores, не называет автора «компетентным» без проверяемого основания и не копирует большие фрагменты чужих публикаций.
