# Critical product/design/motion consultation: KenigEvents typed briefing hero

You are the external senior product-design, editorial UX, motion-design, accessibility, experimentation, and static-web architecture consultant for KenigEvents / «Полюбить Калининград Анонсы».

Give a **deep, adversarial, implementable consultation in Russian**. Do not merely endorse the idea. Separate evidence, assumptions, hypotheses, and decisions. Name contradictions and recommend what to cut. This is a research gate, not a request for code or production rollout.

## Product idea

Replace a conventional video/full-screen homepage hero with a compact text-led “live city briefing”. It behaves a little like text being composed on a monitor: 1–3 friendly lines tell the visitor what is new, useful today, useful this weekend, popular, or relevant since the last visit. Event/category/collection names are real HTML links. The component can pause so links remain controllable.

The hero must occupy **no more than 50% of the viewport height on mobile and desktop**, so category actions and the beginning of the event feed are already visible and users can immediately start browsing. Under it: category/navigation chips or tiles, then the event feed.

This is a prototype/research concept only. No code is requested yet.

## Existing product/technical context

- Astro 6 static-first site. Public listing and event pages are generated from a production SQLite export.
- Static HTML remains useful without JavaScript. Client-side personalization is progressive enhancement.
- Core event data remains in Fly SQLite; identity/personalization may use a separate Supabase/Postgres boundary.
- Existing routes include today, tomorrow, weekend, exhibitions, popular, search, and event detail pages.
- Existing visual language: warm cream/paper background, graphite text, terracotta brand accent, strong editorial/poster typography, a characteristic wide/stretchable «О» in the «АнОнсы» identity. The experience must not become a green-on-black hacker terminal or nostalgic CRT skin.
- Possible data pattern: a cacheable global briefing manifest plus a small per-user overlay (golden-persona affinities, explicit favorites/saves, viewed-item history, last visit). Small local state may be cached in localStorage; the UI must not block on a DB request.
- Production copy/scenario variants may later be produced offline by Gemini Lite from strictly grounded event facts. Generated text must never invent popularity, scarcity, personal preference, editorial endorsement, time-to-start, counts, or “since last visit” claims.
- The first viewport must preserve access to search/city/date/category navigation and must not reduce the homepage to a passive ad.
- Desktop can use stronger typography/motion. Mobile must be calmer and manual-first. `prefers-reduced-motion` must receive an immediately readable static experience.
- Links must not type letter by letter or move under pointer/finger. On hover, focus, or pointerdown, any unfinished phrase should complete in about 100–150 ms and the component should stop. A tap on a link must open it on the first tap.
- There must be no infinite autoplay loop. The first useful statement should be visible immediately.

## Working motion hypothesis to critique

- Primary unit: semantic fragments, not all characters.
- Fragment entrance: opacity 0→1, translateY 8px→0, optional blur 2px→0, 220–360 ms, `cubic-bezier(0.16, 1, 0.3, 1)`, 90–180 ms stagger.
- Total phrase composition: roughly 0.8–1.3 s; static reading: 4–8 s.
- Character typing only for very short accents/status text, deterministic punctuation pauses, never random “human hesitation”.
- Important number may appear as a fixed scale accent. Link appears atomically and remains stable.
- Macro transition may use the decorative stretched «О» as a mask/progress/cursor, with real readable text unaffected in the DOM and the decoration `aria-hidden`.
- Desktop may allow a short controlled auto-sequence that pauses on hover/focus/pointerdown. Mobile should show one first scene and continue manually (or at most one automatic transition).

Почему эта концепция сильная
1. Она превращает каталог в рассказ

Категории и карточки требуют от человека самостоятельно анализировать десятки вариантов. Ваш текстовый блок может сделать первый этап выбора за него:

Пока вас не было, появилось 18 новых событий.
Три — в вашей любимой категории: [посмотреть концерты].

Или:

Сегодня вечером особенно много выставок.
Начать можно с [«Название события»], а затем посмотреть [всю афишу на сегодня].

Это уже не декоративный hero, а навигационный слой, который подсказывает несколько осмысленных входов в каталог.

2. Особенно хорошо работает сценарий «с прошлого посещения»

Это, на мой взгляд, самая ценная часть идеи. Сообщения «сегодня 37 событий» или «на выходных 62 события» полезны, но доступны любому каталогу. А фраза:

С вашего прошлого визита в разделе «Концерты» появилось 7 событий

создаёт ощущение продолжения взаимодействия с продуктом. Пользователю не приходится заново проверять уже просмотренное.

Для постоянной аудитории такой сценарий потенциально сильнее обычной персональной рекомендации, потому что он отвечает на очень конкретный вопрос:

Что изменилось с тех пор, как я был здесь в последний раз?

3. Ссылки остаются настоящими интерфейсными элементами

В отличие от видео, каждое упомянутое событие, категория или подборка может быть обычной HTML-ссылкой:

открыть событие;
применить фильтр;
показать новые события;
перейти к выходным;
открыть любимую категорию;
прокрутить страницу к соответствующей подборке.

Текст здесь одновременно работает как контент, навигация и персональная рекомендация.

4. Это хорошо сочетается с вашим визуальным языком

Главный риск: система навязывает пользователю скорость чтения

Буквально печатающийся текст имеет фундаментальный недостаток: человек способен быстро просканировать уже написанную фразу, но вынужден ждать, пока интерфейс её допечатает.

Если делать эффект по одному символу на протяжении всего сценария, он довольно быстро начнёт раздражать:

постоянный посетитель уже понимает механику и не хочет снова ждать;
длинные названия мероприятий печатаются слишком долго;
пользователь замечает интересную ссылку, но сообщение уже начинает исчезать;
интерфейс выглядит эффектно на демонстрации, но медленно в ежедневном использовании;
дружелюбный рассказ может начать восприниматься как рекламный баннер.

Поэтому я бы разделил эффект печати и ритм показа информации.

Оптимальный вариант

Текст появляется не посимвольно в полном объёме, а короткими смысловыми фрагментами:

Пока вас не было,
появилось 18 новых событий.

Три — в разделе [Живая музыка].

Визуально это может выглядеть как печать, но занимать около секунды, а не пять–семь секунд. Затем сообщение остаётся полностью неподвижным достаточно долго, чтобы его можно было прочитать и открыть ссылки.

Для прототипа разумно проверить такой ритм:

появление фразы: 0,6–1,2 секунды;
статичное чтение: 4–8 секунд в зависимости от длины;
4–6 сообщений за один сценарий;
после последнего сообщения блок останавливается;
бесконечного автоматического цикла нет.

Это стартовые параметры для тестирования, а не окончательные нормы.

Не «терминал», а «живой обзор»

Слишком буквальное копирование старого компьютера несёт стилистический риск. Зелёный моноширинный текст, сильные scanlines, мигающий курсор и чёрный CRT-фон могут:

сделать продукт слишком технологичным;
конфликтовать с культурной и городской тематикой;
быстро устареть;
вызвать ассоциации с хакерским интерфейсом;
удешевить существующую спокойную и плакатную айдентику.

Более перспективная формула:

Поведение — от терминала. Внешний вид — от бренда «Анонсы».

То есть:

крупный основной текст остаётся в вашем фирменном гротеске;
моноширинный шрифт используется только для статуса, времени и служебных маркеров;
фон остаётся тёплым бежевым или терракотовым;
курсор становится фирменным графическим элементом;
анимация создаёт ощущение печати, но не имитирует компьютер 1980-х буквально.

Как использовать вытянутую букву «О»

Это может стать хорошей фирменной механикой, но я бы не растягивал буквы прямо внутри читаемых слов. Варианты вроде сегОООдня или нОООвое быстро становятся манерными и ухудшают распознавание текста.

Наиболее удачный вариант

Большая О располагается позади или рядом с текущим сообщением и играет роль:

курсора;
окна;
рамки вокруг важного числа;
перехода между сообщениями;
индикатора прогресса.

При смене сцены О может медленно растягиваться по горизонтали, на короткое время превращаться в линию или маску, а затем собираться вокруг нового акцента:

О  →  О────────────  →  О

Например:

растягивается при переходе;
возвращается вокруг слова сегодня;

Важно, чтобы это была декоративная псевдобуква с aria-hidden="true", а нормальный текст оставался в DOM без искажений. Для движения лучше использовать transform и opacity, а не постоянно менять реальную ширину текста: такие свойства обычно дают более предсказуемую производительность и меньше вмешиваются в layout страницы.

Как должен работать сценарий
Для нового посетителя

У системы ещё нет достоверного профиля, поэтому рассказ строится от контекста:

что происходит сегодня;
что запланировано на выходные;
что сейчас популярно;

Затем:

Последовательность становится более конкретной:

новое с прошлого посещения;
новое в любимых категориях;
актуальное сегодня;
ближайшие выходные;
популярное или редакционное;
один вариант за пределами привычного профиля.

Пример:

Пока вас не было, появилось 14 новых событий.

Ближайшая премьера — уже в пятницу.

Затем:

А сегодня можно успеть на [название события] в 19:00.
До начала ещё четыре часа.

Для частого повторного визита

Не стоит каждый раз проигрывать один и тот же полный обзор. Если человек вернулся через два часа:

С прошлого визита новых концертов пока нет.
Зато в популярное вышло [название события].

Это воспринимается честнее, чем попытка любой ценой сгенерировать «новость».

Формат текста

Каждое сообщение должно содержать одну основную мысль. Не стоит превращать блок в абзац из пяти ссылок.

Оптимальная структура одной сцены:

дружелюбное наблюдение;
один конкретный факт;
одна или две ссылки;
необязательное объяснение персонализации.

Например:

На субботу особенно много событий с детьми.
Начать можно с [семейного спектакля], а остальные мы собрали [в одной подборке].

Или:

В живой музыке появилось три новых события.
Ближе всего к вашим сохранениям — [название концерта].

Важно различать основания рекомендаций

Не следует называть алгоритмическую выборку «самым интересным» без объяснения. Лучше использовать понятные формулировки:

«Выбор редакции»;
«Чаще всего открывают сегодня»;
«Добавлено за последние сутки»;
«По вашим сохранениям»;
«Из любимой категории»;
«Популярно среди пользователей из Калининграда».

Это повышает доверие и снижает ощущение случайной или коммерческой выдачи.

Если категория была определена только по поведению, а не выбрана самим пользователем, формулировка должна быть осторожнее:

Похоже, вам могут подойти эти концерты.

А не:

Ваша любимая категория — концерты.

Взаимодействие: hover, focus и tap

На уровне поведения этот блок фактически является автоматически переключающейся текстовой каруселью. Поэтому для него разумно применять правила управления каруселями.

WCAG требует давать пользователю возможность остановить, скрыть или контролировать автоматически обновляющуюся информацию. Для auto-updating content нет исключения «это длится меньше пяти секунд»: управление всё равно необходимо.

Рекомендованная логика:

Мышь
при наведении текущая фраза быстро допечатывается до конца;
затем сценарий ставится на паузу;
при уходе курсора можно продолжить после небольшой задержки;
если пользователь нажал ручную паузу, автоматическое продолжение не происходит.
Клавиатура
попадание фокуса на блок или любую ссылку останавливает сценарий;
после ухода фокуса он не запускается автоматически;
продолжение происходит только по кнопке Продолжить;
у всех ссылок и кнопок остаётся заметный focus-ring.

Именно такую модель — остановка при hover и keyboard focus, плюс отдельная кнопка остановки — рекомендует WAI для автоматически вращающихся каруселей. При входе клавиатурного фокуса автоматическое вращение не должно возобновляться без явного действия пользователя.

Сенсорный экран

На телефоне нет надёжного hover-состояния; многие устройства вообще не поддерживают удобное наведение, а часть из них лишь имитирует его долгим нажатием. Это можно определять через media features hover и pointer.

Поэтому нельзя строить мобильную механику на модели:

первый тап останавливает, второй тап открывает ссылку.

Пользователь ожидает, что ссылка откроется с первого касания.

Правильнее:

на pointerdown мгновенно остановить таймер;
тот же tap по ссылке должен продолжить обычный click и открыть страницу;
tap по свободной области блока может переключать паузу;
рядом остаётся отдельная видимая кнопка Пауза / Продолжить.

На мобильном я бы вообще не запускал длинную автоматическую последовательность. Лучший вариант:

первая реплика показывается автоматически;
далее пользователь перелистывает сообщения свайпом или кнопкой;
либо допускается только один автоматический переход, после которого сценарий останавливается.
Пауза не должна фиксировать недописанное слово

При наведении в середине печати не стоит оставлять:

Сегодня особенно инте|

Пользователь пришёл читать и нажимать, а не рассматривать техническое состояние анимации.

Хорошая логика:

пользователь наводит курсор или касается блока;
текущая фраза за 100–200 мс полностью проявляется;
таймер перехода останавливается;
ссылки становятся полностью доступными;
сценарий ждёт пользователя.

Так эффект печати остаётся, но не мешает функциональности.

Обязательные элементы управления

Даже при автоматической остановке на hover должны быть видны:

Пауза / Продолжить;
Назад;
Дальше;
индикатор 2 из 5;
Показать все обновления.

После последнего сообщения блок остаётся в статичном состоянии, например:

Это главное на сейчас.
[Открыть все 274 события]

Бесконечный цикл здесь скорее навредит: он превращает персональный обзор в фоновой рекламный экран.

Доступность текста
Не обновлять screen reader посимвольно

Если каждый добавленный символ попадёт в live region, вспомогательная технология может начать постоянно объявлять изменяющийся контент. ARIA live regions предназначены для уведомления об уже произошедших смысловых обновлениях, а не для озвучивания каждого символа анимации.

Лучше разделить:

визуальный слой может имитировать печать;
доступный слой получает сразу завершённое сообщение;
сообщение объявляется не по буквам, а целиком;
при автоматическом воспроизведении aria-live лучше держать выключенным;
в ручном режиме можно использовать aria-live="polite".

Такой режим off при автоматическом вращении и polite после его остановки прямо предусмотрен WAI-паттерном карусели.

Reduced motion

При включённом prefers-reduced-motion следует убрать:

посимвольное появление;
мигающий курсор;
растягивание О;
автоматические переходы.

Вместо этого показывается полностью сформированное первое сообщение и ручные кнопки. Этот media feature предназначен именно для замены или сокращения несущественной анимации.

Мигающий курсор

Курсор может мигать только во время короткого появления текста. После завершения фразы его лучше:

сделать неподвижным;
приглушить;
превратить в кнопку перехода;
убрать совсем.

Постоянное мигание будет отвлекать от ленты событий ниже.

Архитектура манифеста

Идея общего манифеста правильная, но общий контент и персональный профиль лучше не объединять в один объект. Иначе вы ухудшите кеширование, усложните обновления и начнёте дублировать одни и те же события для разных пользователей.

Лучше использовать четыре слоя:

ОБЩИЙ МАНИФЕСТ СОБЫТИЙ
город · даты · категории · популярность · редакционные оценки
                        +
ПЕРСОНАЛЬНЫЙ OVERLAY
интересы · избранное · сегменты · предпочтения · уверенность
                        +
СОСТОЯНИЕ СЕССИИ
последний визит · показы · открытия · сохранения · скрытия
                        ↓
ПЛАНИРОВЩИК СЦЕНАРИЯ
выбирает 4–6 реплик и формирует безопасные ссылки
                        ↓
ТИПОГРАФИЧЕСКИЙ РЕНДЕРЕР
1. Общий манифест

Кешируемый для города или региона:

event_id
title
published_at
starts_at
ends_at
city
venue
categories
age_rating
price
availability
editorial_score
popularity_score
image
canonical_url
expires_at

Он может обновляться раз в несколько минут или часов в зависимости от типа данных.

2. Персональный overlay

«Голден-персоны» лучше хранить не как одно жёсткое определение пользователя, а как набор весов:

live_music       0.78
family_weekend   0.44
free_city        0.31
art_exhibitions  0.27

Один человек одновременно может:

ходить на концерты;
искать мероприятия с детьми;
предпочитать бесплатные события;
иногда покупать дорогие билеты на большие шоу.

Одна персона слишком быстро превращается в стереотип. Набор весов позволяет учитывать контекст: в пятницу вечером и в воскресенье утром одному человеку могут быть нужны разные события.

Персона должна влиять прежде всего на отбор и порядок событий, а не менять стиль общения до неузнаваемости. Голос бренда остаётся единым.

3. Сессионное состояние

Нужно различать как минимум:

impression — сообщение действительно было видно;
opened — событие или подборку открыли;
saved — сохранили;
dismissed — скрыли или отметили неинтересным;
converted — перешли к билету или добавили в календарь.

Критически важно не считать событие просмотренным только потому, что автоматическая сцена мелькнула на экране. Пользователь мог читать другую часть страницы.

Для impression можно использовать условие вроде:

блок находился в viewport;
вкладка была активна;
сообщение было видно не менее определённой доли времени.

Просмотренные события лучше понижать в рейтинге, а не навсегда удалять. Пользователь может захотеть вернуться к событию, которое видел вчера.

4. Манифест сценария

Итоговая история может выглядеть так:

{
  "id": "new-since-last-visit",
  "type": "personal_delta",
  "eventIds": [1842, 1947, 2011],
  "textParts": [
    { "text": "Пока вас не было, появилось " },
    { "text": "12 новых событий" },
    { "text": ". Три — в категории " },
    {
      "text": "Живая музыка",
      "href": "/events?category=music&new_since=2026-07-12"
    },
    { "text": "." }
  ],
  "reasonCode": "explicit_favorite_category",
  "expiresAt": "2026-07-16T00:00:00Z",
  "minDwellMs": 5500,
  "analyticsId": "briefing_scene_2"
}

Ссылки следует передавать как структурированные токены, а не как готовый HTML. Это:

безопаснее;
проще валидировать;
удобнее для аналитики;
позволяет менять представление;
исключает произвольную разметку в тексте.

Данные, полученные из local storage или внешнего manifest, нельзя считать доверенными: OWASP отдельно предупреждает, что клиентское хранилище доступно JavaScript и может быть прочитано или изменено при XSS. Там нельзя хранить токены авторизации и чувствительные пользовательские данные.

Как использовать localStorage

Хранить там весь манифест и большую историю просмотров не стоит.

localStorage работает синхронно: крупное чтение, сериализация или запись могут блокировать выполнение JavaScript. Для значительных объёмов структурированных данных предназначен асинхронный IndexedDB.

В localStorage достаточно положить
версию манифеста;
время последнего визита анонимного пользователя;
настройку autoplayOff;
последний открытый сценарий;
идентификатор города;
несколько небольших интерфейсных предпочтений.
В IndexedDB
кеш событий;
недавние impression;
opened/saved/dismissed;
небольшую историю сценариев;
данные для offline fallback.
На сервере
канонический профиль авторизованного пользователя;
сохранённые события;
категории;
история между устройствами;
рассчитанные предпочтения;
постоянные исключения.

Локальное состояние анонимного пользователя следует считать подсказкой, а не источником истины: оно может быть очищено, недоступно в приватном режиме или отсутствовать на другом устройстве.

Как обновлять данные без нагрузки

Браузер не должен обращаться к базе данных на каждом новом сообщении. Переход между фразами — чисто клиентская операция.

Рациональная схема:

сервер или background job заранее формирует наборы кандидатов по городам, датам и категориям;
первоначальная страница получает уже готовую первую сцену;
после загрузки клиент проверяет версию общего манифеста;
если версия не изменилась, сервер отвечает без повторной передачи всего тела;
обновлённый сценарий принимается фоном;
текущая реплика не меняется посреди чтения;
новая версия вступает в силу на границе между сценами или при следующем посещении.

Для этого хорошо подходят стандартное HTTP-кеширование, ETag и условные запросы. stale-while-revalidate позволяет мгновенно использовать имеющийся ответ и обновлять его в фоне.

Не нужны:

WebSocket для каждого пользователя;
запрос при каждом напечатанном сообщении;
индивидуальная серверная генерация каждого кадра;
постоянный polling базы;
большой service worker уже в первой версии.
При возврате во вкладку

Когда вкладка скрыта, сценарий должен остановиться. После возвращения можно проверить TTL и обновить данные, но не стоит «догонять» пропущенные сообщения. Page Visibility API позволяет определять переход страницы в скрытое состояние и снижать лишнюю работу в фоне.

Производительность анимации

Сам текстовый блок действительно может быть очень лёгким, но его можно испортить неудачной реализацией.

Не следует:

заново рендерить весь hero на каждом символе;
постоянно пересчитывать высоту контейнера;
двигать окружающие блоки при изменении длины фразы;
загружать большую библиотеку анимаций ради одного курсора;
вставлять символы через небезопасный innerHTML;
запускать таймеры в скрытой вкладке.

Лучше:

заранее зарезервировать высоту под три строки;
создавать сразу завершённый DOM сообщения;
визуально проявлять его по словам или фрагментам;
анимировать преимущественно transform и opacity;
обновлять только небольшой локальный слой;
не допускать layout shift;
прекращать анимацию вне viewport.

Поскольку ссылки должны мгновенно реагировать на tap и click, нужно следить не только за загрузкой, но и за runtime responsiveness. INP оценивает задержку взаимодействий в течение всего жизненного цикла страницы; рекомендуемая граница хорошего значения — до 200 мс на 75-м перцентиле отдельно для мобильных и десктопных посещений.

Генерация дружелюбного текста

Для первой версии я бы не генерировал каждую фразу свободной языковой моделью в момент загрузки страницы. Надёжнее использовать библиотеку проверенных шаблонов:

Пока вас не было, появилось {count} новых событий.
{category_count} — в категории {category_link}.
Сегодня можно успеть на {event_link} в {time}.
Остальные варианты на вечер — {collection_link}.
На выходных особенно много {category_link}.
Мы выбрали {count} вариантов, с которых можно начать.

Это даёт:

предсказуемую длину;
правильный тон;
контролируемые ссылки;
отсутствие выдуманных фактов;
возможность редакторской проверки;
стабильную вёрстку.

Для русского языка понадобится нормальная работа с формами:

1 событие;
2 события;
5 событий;
добавилось / добавились;
в Калининграде / в Гусеве;
сегодня / завтра / в субботу.

Свободную генерацию можно использовать серверно для создания вариантов формулировок, но факты, числа, названия и ссылки должны браться исключительно из структурированных полей манифеста. Перед публикацией результат должен проходить ограничения по длине и фактическую валидацию.

Как встроить это в главную
Десктоп

Текстовый обзор может стать центральной частью hero, но город, поиск и быстрые фильтры остаются постоянными:

ЛОГО       Калининград и область ▼     Поиск         Избранное

ВАШ ОБЗОР · ОБНОВЛЕНО 7 МИНУТ НАЗАД                   2 / 5  ⏸

Пока вас не было,
появилось 18 новых событий.

Три — в категории [Живая музыка].

[←] [Дальше →]             По вашим сохранениям

Сегодня · Завтра · Выходные · Бесплатно · С детьми

Справа можно показывать одну–три небольшие афиши событий, упомянутых в текущей фразе. Они не должны конкурировать с текстом, а лишь давать визуальный контекст.

Ещё лучше синхронизировать hero с лентой:

пользователь открывает ссылку «18 новых»;
ниже автоматически активируется соответствующий фильтр;
страница плавно переходит к уже отфильтрованной ленте;
состояние можно сохранить в URL.
Мобильный

На мобильном блок должен стать компактнее:

ВАШ ОБЗОР                                      1 / 4

Пока вас не было,
появилось 8 новых событий.

Три — в [Концертах].

[Назад] [Дальше] [Все обновления]

Без постоянной автоматической печати. Пользователь и так одновременно скроллит страницу, касается ссылок и может быть в движении.

Может ли это вовлекать

Да, и вовлекать лучше видео, потому что пользователь не только смотрит, но сразу действует. Особенно перспективны сообщения:

«Новое с прошлого посещения».
«Сегодня можно успеть».
«На выходных стоит посмотреть».
«Новое в сохранённой категории».
«Выбор редакции».
Один неожиданный вариант вне обычных предпочтений.

Менее сильный сценарий:

Сейчас расскажем о самых интересных событиях города…

Он требует ждать и звучит как реклама.

Более сильный:

Пока вас не было, добавилось 12 событий.
Вот три, которые действительно подходят вашим сохранениям.

Ключевая разница: первое сообщение уже содержит пользовательскую ценность, а не вступление.

При этом успешность нельзя оценивать по времени просмотра анимации. Если человек 25 секунд смотрит печатающийся текст, но ничего не открывает, hero превратился в заставку.

Главные продуктовые метрики:

время до первого открытия события;
переход в релевантную подборку;
сохранение;
добавление в календарь;
переход к билету;
использование фильтра;
возврат на сайт;
доля пользователей, отключивших автоматическую смену.

Дополнительные диагностические показатели:

сколько сообщений было реально показано;
на каком сообщении чаще нажимают;
частота паузы;
частота возврата назад;
сколько пользователей сразу выбирают «Все обновления»;
сколько скрывают персонализацию.

Высокая частота паузы вместе с переходами по ссылкам означает интерес. Высокая частота паузы без дальнейших действий может означать, что текст меняется слишком быстро или недостаточно понятен.

Что тестировать

Я бы сравнил три реализации с одинаковым контентом и одинаковой персонализацией:

A. Статичный персональный обзор

Вся фраза сразу видна.

B. Появление смысловыми фрагментами

Текст проявляется строками или группами слов за одну секунду.

C. Буквальная печать по символам

Классический typewriter.

Моя рабочая гипотеза: вариант B окажется лучшим компромиссом. Он сохранит ощущение живого интерфейса, но не заставит пользователя ждать каждую букву.

Персонализацию и характер анимации желательно тестировать раздельно. Иначе невозможно будет понять, что именно улучшило результат: более релевантные события или визуальный эффект.

Итоговая рекомендация

Концепцию стоит развивать. Она может стать не декоративным hero, а самостоятельным продуктовым компонентом — «Ваш обзор» или «Что нового в городе».

Оптимальная версия:

4–6 коротких содержательных реплик;
одна мысль и максимум две ссылки в каждой;
первая реплика полезна сразу;
появление по фразам, а не длительная печать каждого символа;
обязательные пауза, назад и дальше;
остановка на hover, focus и pointerdown;
отсутствие бесконечного цикла;
ручной режим на мобильном;
глобальный кешируемый манифест отдельно от персонального overlay;
просмотренные события понижаются, а не бесследно исчезают;
localStorage используется только для небольшого состояния;
большая фирменная О становится переходом или курсором, но не ломает читаемые слова;
поиск, город, даты и категории остаются постоянно доступными.

Самая сильная формула для первого экрана:

«Пока вас не было…» → конкретное изменение → персональная причина → настоящая ссылка.

В таком виде механика будет одновременно узнаваемой, лёгкой, функциональной и действительно полезной при каждом повторном посещении.
## Prior analysis B: motion recommendation

Я бы выбрал управляемую кинетику с ease-out, дополненную очень лёгкой имитацией человеческого ритма

Не один из трёх вариантов в чистом виде, а такую комбинацию:

Текст появляется смысловыми фрагментами с коротким выразительным ease-out; внутри фрагмента сохраняется почти равномерный ритм; небольшие паузы возникают только в естественных местах — после знаков препинания, перед важной цифрой или ссылкой.

Это даст ощущение живого, современного и дорогого интерфейса, но не заставит пользователя ждать «актёрскую игру печатной машинки».

Почему не чисто линейная анимация

Равномерное появление по символам хорошо передаёт образ терминала:

С-е-г-о-д-н-я- -в- -К-а-л-и-н-и-н-г-р-а-д-е...

Но визуально оно быстро становится монотонным. Все части сообщения получают одинаковый вес:

служебное вступление;
важное число;
название события;
ссылка;
призыв к действию.

В результате блок выглядит скорее техническим, чем редакционным. Для настоящей консоли это органично, но для эмоционального сайта городских событий — недостаточно выразительно.

Также равномерная скорость создаёт неудобный компромисс:

медленно — пользователю приходится ждать;
быстро — эффект печати почти не считывается;
очень быстро — возникает визуальный шум без функциональной пользы.

Линейный режим можно оставить для мелких служебных элементов:

КАЛИНИНГРАД · ОБНОВЛЕНО 8 МИНУТ НАЗАД

Но не делать его основой больших сообщений.

Почему не стоит имитировать человека слишком буквально

Human-like режим обычно означает случайные задержки:

одна буква появилась через 28 мс;
следующая через 63 мс;
после слова пауза;
иногда небольшая заминка;
иногда внезапное ускорение.

Для чат-интерфейса такая механика иногда уместна: пользователь воспринимает её как присутствие собеседника. Но у вас сайт не должен притворяться человеком, который сидит и в реальном времени набирает текст.

Слишком выраженная неравномерность создаёт несколько проблем.

Она выглядит искусственно

Через несколько посещений пользователь начинает замечать не «живой ритм», а заранее запрограммированные паузы. Особенно неестественно выглядит задержка перед готовой рекомендацией, которая на самом деле уже была рассчитана сервером.

Она ухудшает предсказуемость

Человек не понимает, когда фраза закончится. Одно сообщение печатается секунду, другое — четыре. Это мешает быстро просматривать главную.

Она конфликтует со ссылками

Пользователь увидел начало названия события, навёл курсор, а строка ещё продолжает менять длину. Ссылка может смещаться под курсором или появиться слишком поздно.

Она может показаться манипулятивной

Искусственные паузы вроде:

Кажется, я нашёл кое-что специально для вас…

могут восприниматься как имитация размышления. Для сервиса анонсов лучше звучать дружелюбно, но честно: данные уже есть, интерфейс быстро их показывает.

Поэтому человеческий ритм стоит использовать как музыкальность композиции, а не как случайность каждого символа.

Почему не полный ease-in-out для каждой буквы

Ease-in-out хорош для движения объектов: карточка ускоряется, проходит основную дистанцию и мягко останавливается. Но применённый к каждой букве он часто создаёт ощущение вязкости:

символы медленно «просыпаются»;
середина слишком динамична;
конец каждой микродвижущейся единицы затягивается;
текст кажется плавающим;
читать во время анимации сложно.

Особенно плохо выглядит сочетание посимвольного opacity + translateY + blur с длинной фразой: перед глазами постоянно движутся десятки элементов.

Для текста лучше быстрый ease-out:

появился энергично → мягко зафиксировался → больше не двигается.

А ease-in-out оставить для крупных брендовых переходов: вытягивания О, перемещения фоновой формы, смены сцен.

Рекомендуемая модель движения
1. Появление текста — по смысловым фрагментам

Не по одной букве и не всей фразой сразу. Пример разбиения:

Пока вас не было,

появилось 18 новых событий.

Три — в категории Живая музыка.

Фрагментами могут быть:

короткая строка;
синтаксическая часть предложения;
группа из 2–5 слов;
число с определением;
отдельная ссылка.

Так возникает ритм рассказа, но читать уже появившийся текст можно сразу.

Пример

Сначала:

Пока вас не было,

через 150–250 мс:

появилось 18 новых событий.

затем:

Три — в категории [Живая музыка].

Вся реплика формируется примерно за 0,8–1,3 секунды, а не печатается пять секунд.

2. Для фрагментов — быстрый ease-out

Подходящая визуальная схема:

opacity: 0 → 1;
translateY: 8px → 0;
возможно, очень небольшой blur: 2px → 0;
длительность 220–360 мс;
задержка между фрагментами 90–180 мс.

Характер кривой:

cubic-bezier(0.16, 1, 0.3, 1)

Это выраженный ease-out: начало достаточно энергичное, завершение мягкое. Он даёт ощущение качества, но не заставляет текст долго «доезжать».

Размытие стоит применять очень умеренно или не применять вообще на слабых устройствах. Главный эффект можно построить только на opacity и небольшом вертикальном сдвиге.

3. Внутри отдельных фрагментов — почти линейная печать

Можно сохранить терминальный характер на уровне коротких акцентов:

18 новых событий

или:

ОБНОВЛЕНО 7 МИНУТ НАЗАД

Здесь допустимо быстрое появление по символам, например:

18–28 мс на символ;
небольшая пауза после запятой;
более заметная пауза после точки;
без случайных скачков скорости.

То есть не:

23 мс → 91 мс → 37 мс → 122 мс → 19 мс

а контролируемая система:

обычный символ     24 мс
пробел             14 мс
запятая            +80 мс
точка              +140 мс
длинное тире       +70 мс

Пользователь ощущает речь, но интерфейс остаётся предсказуемым.

Формула движения

Я бы разделил анимацию на три уровня.

Микроуровень: символы

Почти линейный ритм, только для коротких акцентов и служебного текста.

Средний уровень: смысловые фрагменты

Быстрое появление с ease-out. Это основа всей механики.

Макроуровень: переход между сообщениями

Здесь можно применять более выразительный ease-in-out и фирменную букву О:

текущий текст остаётся неподвижным;
большая О начинает вытягиваться;
превращается в горизонтальную маску или линию;
закрывает или вытесняет старое сообщение;
через неё появляется следующее;
О собирается в новой позиции.

Так стильная кинетика происходит между сообщениями, а не мешает чтению внутри сообщения.

Конкретный тайминг одной сцены

Например, реплика:

Пока вас не было,
появилось 18 новых событий.
Три — в категории [Живая музыка].

Может работать так:

Время	Действие
0–280 мс	Появляется «Пока вас не было»
160–500 мс	Появляется «появилось»
320–680 мс	Выразительно появляется число 18
500–820 мс	Появляется «новых событий»
760–1 100 мс	Появляется последняя строка
1 100–5 500 мс	Полностью неподвижное состояние для чтения
5 500–5 900 мс	Фирменный переход через растянутую О
с 5 900 мс	Следующее сообщение

Ключевой принцип:

Анимация текста занимает около одной секунды, чтение — несколько секунд.

Не наоборот.

Как анимировать важные элементы

Не все фрагменты должны появляться одинаково.

Обычный текст

Небольшой вертикальный сдвиг и opacity.

Важное число

Например, 18:

появляется чуть раньше окружающих слов;
может быть заметно крупнее;
получает более выраженный scale: 0.96 → 1;
фиксируется без дальнейшей пульсации.
Ссылка

Ссылка должна появляться сразу целиком, а не печататься посимвольно. Иначе её активная область постоянно меняется.

Можно использовать:

проявление текста;
быстрое раскрытие подчёркивания слева направо;
короткое изменение насыщенности;
появление стрелки ↗.

После появления ссылка должна оставаться полностью неподвижной.

Курсор

Курсор уместен только пока формируется реплика. После завершения:

перестаёт мигать;
становится точкой или фирменной О;
либо исчезает.

Постоянно мигающий курсор будет конкурировать со ссылками и создавать ощущение незавершённости.

Что должно происходить при наведении или тапе

Когда пользователь взаимодействует с блоком, красота движения должна немедленно уступать управляемости.

При hover, focus или pointerdown:

текущая фраза быстро проявляется полностью;
все незавершённые фрагменты заканчивают появление за 100–150 мс;
автоматический переход останавливается;
ссылки остаются в неподвижном состоянии;
появляется или активируется индикатор паузы.

Не нужно буквально замораживать строку в состоянии:

На выходных особенно инте|

Человек должен получить законченный текст, а затем спокойно выбрать ссылку.

Десктоп и мобильный должны иметь разную интенсивность
На десктопе

Можно использовать полную систему:

смысловые фрагменты;
быстрый typewriter для отдельных акцентов;
вытягивание О;
автоматическую смену нескольких реплик;
остановку при hover.
На мобильном

Нужна более спокойная версия:

строка или фрагмент появляется целиком;
минимум вертикального движения;
без длительной посимвольной печати;
переходы преимущественно ручные;
tap по ссылке сразу открывает её.

На маленьком экране пользователь одновременно скроллит, читает и касается интерфейса. Сложная кинетика быстрее превращается в помеху.

Мой итоговый выбор
Основа

Появление смысловыми фрагментами с быстрым ease-out.

Дополнительная текстура

Небольшие детерминированные паузы на пунктуации, а не случайная human-like скорость.

Фирменная выразительность

Ease-in-out для перехода между сценами и анимации большой буквы О, но не для каждой буквы основного текста.
