# Атомарная смена векторов related_v1

Это одноразовая операция для агента релиза на KenigEvents. Рабочая версия v2 кодирует один текст. Версия v3 складывает нормированные векторы исходного текста v2 и краткого текста U. Стандартный проектор пишет таблицы несколькими запросами. Для первого перехода файлы ниже переключают готовые строки одной транзакцией PostgreSQL. Обычные изменения карточек после перехода обрабатывает новый проектор.

Использовать полную актуальную выгрузку production и прямое подключение psql к **personalization Supabase** через действующий operator-профиль. PostgREST не поддерживает общую транзакцию для этих запросов. На DevCoveer опубликованный ранее архив доступен под dev и devester. На рабочей машине выпустить отдельный приватный каталог с правами 0700. Переменная `checkout` — полный checkout кандидата с новым проектором и его обычными зависимостями, `runbook` — каталог этого файла. Подключение PostgreSQL уже выбрано через операторский PGSERVICE или эквивалент. Выбирать рабочую директорию на долговременном диске с доступом 0700 для оператора. Оператор сохраняет rollback.csv и ревизии после сбоя процесса или потери квитанции.

```bash
set -eu
umask 077
: "${checkout:?полный абсолютный путь к checkout}" "${runbook:?абсолютный путь к этому каталогу}"
: "${fresh_preview:?абсолютный путь к первой свежей выгрузке}"
checkout=$(realpath "$checkout")
runbook=$(realpath "$runbook")
fresh_preview=$(realpath "$fresh_preview")
work=$(mktemp -d "${release_dir:?абсолютная постоянная операторская директория}/vector-cutover.XXXXXX")
cd "$work"
tar -xOzf /home/dev/kenigevents-fable-review-20261116/kenigevents-related-690.tar.gz vectors.jsonl > vectors.jsonl
psql -X -f "$runbook/export-v2.sql"
python "$runbook/prepare.py" "$checkout" "$fresh_preview" live-v2.csv vectors.jsonl .
```

Получить `fresh_preview` штатным exporter кандидата из первичной базы. Он должен содержать полный состав с полем `canonical_search_digest` и своим `build.catalog_revision`. На стороне Supabase до начала перехода завершить обычную сверку действующим v2-проектором. `prepare.py` сравнивает текущую версию текста v2 и хеш поискового документа для каждой карточки и использует её фактически записанный вектор v2. Второй компонент берётся из проверенного по SHA архива только при совпадении SHA-256 текущего текста U. Вывод `new_facts_inputs` даёт точное число недостающих уникальных входов. Если их число положительное, команда завершится до первого вызова. В том же каталоге повторить с `--complete-missing` в штатном окружении embedding worker. Проектор обращается к обычному GoogleAIClient; успешно полученные результаты записываются в приватный локальный `facts-cache.jsonl`. Завершившиеся ответы переиспользуются при повторе. Сбой провайдера останавливает подготовку. Файл `forward.csv` формируется только после полного покрытия. При каждой новой попытке проверять успешное завершение подготовки именно текущей выгрузки.

Чтобы проверить изменения canonical-only на границе двух разных баз, на короткое окно переключения приостановить существующие пишущие в карточки процессы, vector sync и повторные static exports. Сам PostgreSQL не видит `event.search_digest` из SQLite. **Свежую** повторную полную выгрузку получить после остановки записи. Полностью повторить `export-v2.sql` и `prepare.py` с этим файлом. Обязательно сверить обе ревизии ниже до вызова apply. При различии отменить переключение и заново подготовить текущий каталог. Недостающий компонент можно считать заранее при работающем сервисе. Удерживать окно только на повторной проверке и смене версии. При невозможности согласовать окна между SQLite и Supabase оставить v2 действующим.

```bash
# fresh_preview и final_preview — разные файлы, полученные отдельными штатными экспортами.
final_preview=$(realpath "${final_preview:?абсолютный путь к повторному экспорту}")
cp revision.json planned-revision.json
psql -X -f "$runbook/export-v2.sql"
python "$runbook/prepare.py" "$checkout" "$final_preview" live-v2.csv vectors.jsonl .
cmp planned-revision.json revision.json
test ! -e rollback.csv
psql -X -f "$runbook/apply.sql"
```

SQL загружает готовые значения в pg_temp, блокирует конкурирующие записи обеих таблиц, сравнивает состав, исходные хеши и числа старых векторов, сохраняет прежнее и ожидаемое состояние в локальный `rollback.csv`, обновляет строки и проверяет результат до COMMIT. Читающий RPC в своём снимке видит одну версию. `search_v3` сохраняет числа и хеш текста, получает metadata актуальной ревизии каталога. У всех `related_v1` обновляются vector, text_hash, embedded_at и metadata. Документ получает related_doc_version, related_text_hash и corpus metadata.

В новой сессии проверить полный охват и единственную версию на всех ожидаемых ID через штатный отчет coverage. На SW/worker выставить release с тем же проектором до возобновления vector writes. Передать `revision.json → corpora.related_v1.revision` штатному exporter через `--related-corpus-revision` и проверить его receipt и повторную сборку публичного графа. При первом переходе проверить совместно новую PGVECTOR_RELATED_CACHE_SCHEMA_VERSION и related_corpus_revision: scoped refresh сам по себе мог принять старых соседей с другой ревизией. Оставить последний успешно собранный публичный граф действующим до успешного завершения обычного exporter receipt, проверки новой схемы, ревизии и контрольных карточек. Не инициировать отдельную массовую переоценку Gemma ради миграции. При откате передать прежнюю ревизию из последнего успешно опубликованного v2 receipts и восстановить соответствующую версию кода и графа. При отсутствии подтверждённого статуса последнего COMMIT сверить `related_doc_version`, оба хеша и `embedding_corpus_revision` по таблицам с ожидаемым манифестом. Сохранить прежний rollback.csv, не перезаписывать его запуском apply.

```bash
# из того же приватного каталога, при остановленных писателях и подтверждённом v3
psql -X -f "$runbook/rollback.sql"
```

Откат сравнивает все ожидаемые строки с состоянием сразу после применения. При новой/удалённой карточке или изменении связанной строки транзакция завершается до записи. После возобновления обычных записей не накатывать старый снимок на изменившуюся базу. Для возврата позднее взять текущую полную выгрузку и действующий v2-проектор, восстановить v2 сначала в изолированной копии sidecar, пересчитать недостающие исходные входы по свежим хешам и провести обратный переход по отдельному полному манифесту. При более позднем откате шаг merge старого материала с актуальными карточками этим одноразовым скриптом не автоматизирован.
