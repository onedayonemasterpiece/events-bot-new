Дизайн-система для бренда «Полюбить Калининград» и продукта «Анонсы»
Краткий вывод и рекомендуемая модель
Рекомендация исследования: строить единую слоистую дизайн-систему, а не две независимые системы — «брендовую» и «продуктовую». Общими должны быть брендовые принципы, визуальные foundations, семантические design tokens, правила доступности, редакционные основы и процессы контроля. Конкретные цифровые продукты должны подключать этот общий слой и добавлять собственные компоненты, шаблоны и продуктовые паттерны.

Целевая модель выглядит так:

text
Копировать
«Полюбить Калининград» — зонтичный бренд
│
├── Brand system
│   ├── позиционирование и характер
│   ├── логотип и правила именования продуктов
│   ├── типографика, цвет, фотография, иллюстрация
│   ├── иконографика, motion, голос и редакционные принципы
│   └── правила для web, email, social, печати и партнёрских материалов
│
├── Shared foundations
│   ├── primitive tokens — внутренние исходные шкалы
│   ├── semantic tokens — публичный контракт системы
│   ├── accessibility baseline
│   ├── layout, typography, focus, motion, imagery
│   └── правила темизации и каналов
│
├── «Полюбить Калининград Анонсы»
│   ├── Astro component library
│   ├── продуктовые компоненты событий
│   ├── паттерны поиска, фильтрации и представления событий
│   ├── шаблоны страниц
│   └── схема и правила редакционных данных
│
└── Будущие продукты
    └── собственные extensions поверх тех же foundations
Такая архитектура ближе всего к сочетанию практик GitHub Primer, где отдельно существуют Product UI, Brand UI и Brand Toolkit, но они опираются на общие primitives и правила доступности, и IBM Carbon, где общая система допускает специализированные расширения вроде Carbon for IBM.com. DSFR также формально различает foundations, компоненты, расширения, документацию и governance. 

Однозначная рекомендация по поставке на текущей стадии: разместить систему внутри репозитория Astro-сайта, но как явно изолированный системный модуль с собственными токенами, документацией, тестовыми стендами и changelog. Сейчас не следует создавать отдельный репозиторий, отдельный monorepo или набор публикуемых пакетов. Пока существует только один реальный потребитель, такое разделение добавит процессы синхронизации, публикации и обновления, не устраняя ни одного существующего организационного ограничения.

Source of truth: релизный Git-коммит сайта и дизайн-системы. В нём должны находиться:

исходные семантические токены;
исходники компонентов и паттернов;
брендовые assets;
документация и ADR — записи архитектурных решений;
тестовые примеры;
версия системы и changelog;
ссылка на соответствующую версию Figma-библиотеки.
Figma при этом остаётся средой проектирования, но не должна быть единственным хранилищем значений. В готовом релизе ни цвет, ни отступ, ни состояние компонента не должны существовать только в Figma.

Публичный API системы следует считать состоящим из семантических токенов, Astro-компонентов, их props и slots, разрешённых CSS custom properties, продуктовых паттернов и редакционных контрактов. Именно изменения этого API должны управлять версиями. SemVer предполагает, что система сначала определяет публичный API, после чего patch означает совместимое исправление, minor — совместимое расширение, major — несовместимое изменение; ветка 0.y.z предназначена для нестабильного начального развития. 

До запуска достаточно версии вида 0.1.0–0.9.x. Переход к 1.0.0 имеет смысл только после того, как минимальный API применён в production, прошёл хотя бы один цикл изменений и больше не перестраивается каждую неделю.

Сравнение референсных дизайн-систем
Ни одна из исследованных систем не должна копироваться целиком. Государственные системы лучше всего показывают правила доступности, исследования и управление качеством; продуктовые — архитектуру токенов, кодовую поставку и расширяемость. Для небольшого культурного продукта нужен осознанно сокращённый гибрид.

GOV.UK Design System	Публичная документация styles, components и patterns; код govuk-frontend, npm-пакет и репозиторий. Код распространяется по MIT, документация — по Open Government Licence. Сайт документации также имеет публичный репозиторий. 
Визуальный язык государства оформлен как styles; компоненты являются повторно используемыми единицами, а patterns описывают пользовательские задачи. Опубликованные компоненты и паттерны отделены от экспериментальных предложений сообщества. 
Есть changelog, релизы пакета и формальный contribution process: обоснование задачи, пользовательские исследования, accessibility evidence, review и принятие. Использование компонентов не гарантирует доступность всего сервиса; сама система отдельно тестируется и аудируется. 
Разделение «стили — компоненты — паттерны»; статус зрелости; критерии приёма компонента; исследовательские примечания; явное предупреждение, что библиотека не заменяет аудит продукта.	Государственную визуальную строгость, большой коллегиальный governance и требование обширной доказательной базы для каждого небольшого изменения.
U.S. Web Design System	Публичные документация, GitHub-репозиторий, npm-поставка и дизайнерские kits. Figma-kit обновляется и версионируется отдельно. Код федерального происхождения в значительной части относится к public domain/CC0, а сторонние части сохраняют собственные лицензии. 
Развита иерархия токенов и theme settings. Документация рекомендует обращаться к токенам и системным функциям, а не копировать конечные значения. 
USWDS предлагает maturity model от принципов и guidance до использования кода, позволяющую внедрять систему постепенно. Компоненты проходят автоматические axe/pa11y-проверки на изменениях, ручные keyboard, screen-reader, zoom и device-тесты; опубликованы отчёты о соответствии компонентов. 
Модель постепенной зрелости; системный запрет случайных значений; проверяемая матрица доступности; разделение theme configuration и устанавливаемого package-кода.	Федеральный объём документации, Section 508-процедуры, VPAT/ACR для каждого компонента и многоуровневую конфигурацию, не оправданную одним сайтом.
DSFR	Публичные документация, Figma-assets, GitHub и npm. Код репозитория указан под MIT; применение самой государственной идентичности и использование DSFR регулируются отдельными правовыми и организационными условиями. Поэтому открытая лицензия кода не равна свободному использованию бренда. 
Особенно чётко различены option/primitive colors и decision/contextual tokens. Семантические токены используются в Figma и коде; foundations, компоненты, расширения и документация определены как разные уровни системы. 
Figma-библиотеки и код выпускаются по версиям; описан контролируемый процесс обновления библиотек, а detaching компонентов считается потерей обновляемости. Документация постепенно размещается рядом с кодом; используются releases и Storybook. 
Семантические decision tokens; явная версия Figma-библиотеки; разделение core и extensions; запрет detach и локальных копий; документация рядом с реализацией.	Юридическое согласование применения, обязательные approval-процедуры и административные пороги аудита.
GitHub Primer	Публичные сайты Product UI, Brand UI и Brand Toolkit; репозитории primitives и React-компонентов под MIT; Octicons и документация. Некоторые внутренние мобильные библиотеки Figma не являются публичной поставкой. 
Токены разделены на base, functional и component/pattern. Base tokens не предназначены для прямого использования продуктом; основной публичный слой — functional tokens. Отдельные brand и product surfaces используют общий фундамент. 
Документация показывает доступность компонентов в разных реализациях и их maturity/status. Крупные изменения сопровождаются major-релизами и migration guidance; экспериментальные компоненты переводятся в stable явно. 
Лучшая референсная модель для зонтичного бренда: общий token core, отдельные brand/product применения; статус реализации по платформам; функциональные токены как контракт.	React-центричность, девять тем, сложную многоплатформенность и component-level tokens до появления доказанной необходимости.
IBM Carbon	Публичные документация, дизайн-ресурсы и Apache-2.0 monorepo с React, web components, Sass, tokens, icons и tooling. 
Carbon опирается на IBM Design Language. Темы меняют значения токенов, сохраняя их семантические роли. Специализированные системы могут расширять общий core; Carbon for IBM.com является официальным примером такого расширения. 
Есть формальные критерии component completeness и maturity. На страницах компонентов виден фактический статус автоматических, ручных, keyboard и screen-reader тестов, включая частично проверенные состояния. 
Прозрачная матрица качества вместо бинарной надписи «accessible»; core + product extension; стабильные семантические роли темы.	Размер monorepo, десятки пакетов, enterprise lifecycle и универсальность для сложных бизнес-интерфейсов.
Adobe Spectrum	Публичная документация, Spectrum CSS, React Spectrum и design-data repositories под Apache-2.0; пакеты компонентов и токенов. 
Spectrum CSS-компоненты зависят от общего token package. Для контролируемой кастомизации предусмотрены публичные component custom properties с префиксом --mod, вместо произвольного переписывания внутренних селекторов. 
Есть независимые версии, Storybook, visual comparison tooling и changelog. React Spectrum разделяет визуальные компоненты, поведение и state/internationalization; accessibility проверяется на разных устройствах и screen readers. 
Явный sanctioned override API; motion tokens; разделение разметки, поведения и состояния; ограниченная кастомизация через slots и custom properties.	Пакет на каждый компонент, React Aria/Stately-архитектуру и сложную поддержку density/theme/context для первого статического сайта.
NHS Design System	Публичный service manual, styles, components, patterns, content guidance и npm/GitHub-код. nhsuk-frontend распространяется под MIT, документация — по Open Government Licence. 
Компоненты отделены от patterns и редакционного руководства. Система ориентирована на semantic HTML и progressive enhancement; текущие migration guides отдельно описывают изменения поведения без JavaScript. 
Релизы имеют changelog и migration guidance; accessibility-рекомендации включаются прямо в документацию компонентов, включая объяснение, почему визуально привычные решения могут быть недоступны. 
Особенно полезный референс для Astro: HTML-first, отсутствие обязательного JS, единое содержание style guide, components и service patterns.	Медицинскую специфику, NHS brand restrictions и паттерны, требующие клинического контекста.
Helsinki Design System	Публичные документация, design kit из releases, GitHub-код под MIT, компоненты, tokens и visual assets. 
Городская идентичность соединена с token package и повторно используемыми компонентами. Contribution guidance требует применять design tokens вместо собственных пикселей, цветов, шрифтов и breakpoints. 
Есть release-specific documentation и migration guides, в которых отдельно отмечаются accessibility-изменения и совместимость. 
Масштаб муниципального культурного сервиса, token enforcement, design kit из релизов и практическая документация без федерального governance.	React-специфические реализации и всё множество городских сервисных сценариев.

Из сравнения следуют пять практически важных выводов.

Система не равна библиотеке компонентов. GOV.UK и NHS отделяют patterns от components; DSFR — foundations от extensions; Primer — брендовые и продуктовые применения; Carbon — core от специализированных систем. 

Семантические токены должны быть основным контрактом. USWDS, DSFR, Primer и Carbon сходятся в том, что продукту следует обращаться к ролевым значениям — text-primary, surface-accent, space-component-gap, — а не к исходному синему оттенку или конкретным восьми пикселям. 

Доступность должна иметь проверяемый статус. GOV.UK прямо предупреждает, что использование системы само по себе не делает сервис доступным; Playwright и Carbon показывают ценность сочетания автоматических и ручных тестов и фиксации того, какие состояния реально проверены. 

Документация, дизайн и код должны выпускаться согласованно. DSFR версионирует Figma-assets и описывает обновление libraries, GOV.UK и NHS ведут changelog и migration guidance, а Helsinki распространяет design kit через releases. 

Маленькой команде нужна не упрощённая копия enterprise-системы, а система с меньшей поверхностью. Уменьшать следует количество компонентов, пакетов, ролей и церемоний, но не качество токенов, доступности, тестов и версионной дисциплины.

Отдельный разбор Госуслуг и Гостеха
Что является каноническим публичным источником
На дату исследования подтверждается следующая официальная цепочка материалов:

Учебная страница Гостеха «Знакомство с проектированием интерфейсов ГИС» на platform.gov.ru перечисляет требования к интерфейсам, редакционную политику, библиотеку Cardbox и Cardbox ARM. 
Официальные методические рекомендации по проектированию интерфейсов систем управления ссылаются на guides.gosuslugi.ru и на конкретные разделы Cardbox и Cardbox ARM. 
В рекомендациях зафиксированы отдельные публичные адреса:
guides/gosuslugi.ru/guides/ui — базовый Cardbox;
/guides/arm — Cardbox ARM;
/guides/redpolitica — редакционная политика;
/guides/picture — иллюстрации;
/guides/icons — иконки;
/guides/accessibility — доступность;
/guides/principles — общие принципы. 
Методические материалы описывают guides.gosuslugi.ru как открытый корпус интерактивных руководств. Для руководств предусмотрены номер версии и дата; материалы обновляются итеративно, а проект может зафиксировать версию, действовавшую на момент начала работ. Это важная практика: система не должна незаметно меняться под уже разработанным продуктом. 

Критическое уточнение о статусе открытости: в ходе исследования не удалось подтвердить канонический публичный репозиторий исходного кода Cardbox/Cardbox ARM, публичный package registry или лицензию на код. Поэтому корректная формулировка — публично доступные руководства и дизайн-материалы, но не «open-source дизайн-система». Наличие публичной документации или доступного дизайн-файла само по себе не подтверждает open-source-статус.

Границы Cardbox и Cardbox ARM
Базовый Cardbox описывает общие визуальные элементы: цвета, шрифты, базовые controls и правила интерфейса. Cardbox ARM — отдельный специализированный набор для систем управления: контекстные меню, фильтры, информационные карточки, таблицы, графики и dashboards. 

Это ценный архитектурный прецедент:

text
Копировать
Общие правила и визуальные основы
        ↓
Cardbox — базовые элементы
        ↓
Cardbox ARM — extension для рабочего места и сложных ГИС
Для «Полюбить Калининград» аналогия должна быть такой:

text
Копировать
Общий бренд и foundations
        ↓
Базовые web-компоненты
        ↓
«Анонсы» — extension для событий и культурной навигации
При этом Cardbox ARM не следует использовать как визуальный образец публичного культурного сайта. Его таблицы, dashboards, плотные формы и контекстные меню предназначены для информационных систем и автоматизированных рабочих мест, тогда как «Анонсы» — преимущественно контентный публичный сервис.

Что полезно перенести
Версионируемые руководства. Каждая опубликованная редакция системы должна иметь номер, дату и changelog. Сайт должен знать, на какой редакции он построен.

Разделение общих и специализированных паттернов. Компоненты события, расписания, площадки и статуса не должны попадать в базовый брендовый слой только потому, что появились первыми.

Редакционная политика как часть системы. Официальный корпус Госуслуг отделяет редакционные правила, иллюстрации, иконки и доступность, но связывает их с проектированием интерфейса. Это подтверждает, что визуально-коммуникационная система шире UI kit. 

Допустимое совмещение ролей. Методические материалы описывают широкую ролевую модель, но допускают совмещение ролей одним специалистом и рекомендуют внешнюю экспертную проверку там, где в команде нет компетенции. Это применимо к небольшой команде: governance должен определять ответственность, а не требовать отдельного сотрудника на каждую функцию. 

Что переносить не следует
Не требуется воспроизводить процесс проектирования ГИС целиком, формальную ролевую структуру, набор ARM-компонентов, документооборот согласований или обязательную унификацию с государственным порталом. Для культурного бренда важна узнаваемая собственная идентичность, а не стилистическое сходство с Госуслугами.

От Cardbox следует взять архитектурный принцип core + domain extension, дисциплину guides и связь с редакционными правилами — но не конкретную эстетику и не организационный масштаб.

Архитектура системы для «Полюбить Калининград»
Границы пяти системных областей
Brand system отвечает за то, как бренд выглядит, звучит и узнаётся вне конкретного интерфейса. В неё входят:

архитектура бренда и именование продуктов;
логотип, знак, охранное поле, минимальные размеры и lockups;
основная типографика и кириллические требования;
фирменная цветовая территория;
фотографический и иллюстративный язык;
иконографика;
принципы motion;
tone of voice;
правила для email, social cards, PWA assets, партнёрских материалов и печати.
Brand system не должна содержать API Button или логику фильтрации событий.

Design system — управляющая оболочка всей системы. Она связывает бренд, foundations, tokens, компоненты, паттерны, редакционные правила, документацию, версии, тесты, contribution process и исключения. Design system — это не отдельная папка с компонентами, а контракт между дизайном, контентом и реализацией.

Component library содержит готовые технические реализации повторно используемых UI-единиц: Astro-компоненты, CSS, разрешённые behaviors, типы props, accessibility semantics и тестовые fixtures. Библиотека не определяет, какие события считаются перенесёнными или как редактор описывает площадку.

Product patterns описывают составные решения пользовательских задач: поиск события на выходные, просмотр программы дня, представление перенесённого события, переход к регистрации, фильтрацию по району или возрасту. Паттерн может объединять несколько компонентов, URL-state, правила текста, event schema и требования доступности.

Editorial system определяет структуру и качество содержания:

обязательные поля события;
словарь категорий;
форматы даты, времени, адреса и цены;
правила для отмены, переноса, sold out и регистрации;
названия площадок и организаторов;
alt-тексты и подписи;
авторские права и credits;
tone of voice;
длину заголовков и описаний;
правила social/email-анонсов.
Редакционная система не должна менять CSS, но от неё зависит API продуктовых компонентов: например, поддерживает ли EventCard несколько площадок, диапазон дат, возрастное ограничение и статус отмены.

Component-level token оправдан только если одновременно выполняются три условия:

значение действительно должно настраиваться независимо от общей роли;
оно используется более чем в одном месте или theme;
настройка является поддерживаемой частью публичного API.
Для редких отклонений сначала предпочтительнее композиция, variant или документированная CSS custom property в духе Spectrum --mod-*, а не переопределение внутреннего селектора. Spectrum прямо оформляет такие custom properties как разрешённый override API. 

Каналы не должны принудительно разделять один код
Web, PWA, email и social cards могут разделять:

semantic color map;
typography roles;
логотипы и assets;
image rules;
content schema;
voice;
статусные формулировки;
version manifest.
Но они не обязаны использовать одинаковые компоненты. HTML email имеет иные ограничения, чем современный браузер; social card может рендериться отдельным шаблоном или image pipeline. Общность должна проходить через foundations и content contracts, а не через попытку применить EventCard.astro в письме.

Темизация
На первом этапе нужна одна основная брендовая тема и ограниченный набор контекстов:

стандартная светлая поверхность;
инвертированная брендовая поверхность;
информационный, успешный, предупреждающий и критический статус;
prefers-reduced-motion;
системный forced-colors/high-contrast режим должен оставаться работоспособным.
Полноценную пользовательскую dark theme не следует включать в MVDS без отдельного продуктового требования. Primer поддерживает много тем, включая high-contrast и colorblind variants, но это следствие масштаба GitHub, а не обязательный стартовый уровень для каждого продукта.

Foundations не должны становиться npm-пакетом: это логический слой, а не поставляемый artefact. На старте также не нужны отдельные пакеты tokens, components, theme и brand. Достаточно внутренних каталогов и path aliases, например @ds/components/*.

Отдельный @love-kaliningrad/tokens оправдан только тогда, когда токены независимо потребуются генератору писем, social graphics, нативному приложению или внешнему подрядчику.

Один Git-коммит может иметь и site tag, и DS tag, если выпуск сайта и системный milestone не совпадают.

После выделения:

json
Копировать
{
  "dependencies": {
    "@love-kaliningrad/design-system": "1.3.2"

}
Следует использовать точную версию без ^ и ~ и коммитить lockfile. npm документирует, что точная запись соответствует только указанной версии, а package-lock.json фиксирует точное дерево зависимостей; npm ci завершается ошибкой, если lockfile не соответствует package.json. 

Правила SemVer:

Изменение	Версия
Исправлена неправильная разметка или contrast без изменения API	patch
Добавлен совместимый variant или новый компонент	minor
Компонент помечен deprecated	minor
Переименован semantic token, удалён prop, существенно изменена DOM/keyboard semantics	major
Изменён только внутренний primitive token без видимого или контрактного эффекта	patch
Изменён внешний вид многих компонентов из-за новой брендовой основы	minor, либо major, если нарушаются документированные визуальные/интеграционные ожидания

SemVer прямо относит совместимые исправления к patch, совместимую функциональность и deprecation — к minor, несовместимые изменения API — к major.

Компонентная архитектура Astro
Astro-компоненты по умолчанию рендерятся в HTML и не добавляют клиентский JavaScript. Framework components без client:* также рендерятся как статический HTML; hydration подключается только через client:load, client:idle, client:visible, client:media или client:only. Astro также поддерживает обычные scripts и custom elements без обязательного UI-фреймворка. 

Поэтому рекомендуемая иерархия реализации:

text
Копировать
Семантический HTML
    ↓ при необходимости
Astro .astro component
    ↓ при необходимости поведения
небольшой script или custom element
    ↓ только при сложном интерактивном состоянии
framework island с точечной hydration
Практически:

Button.astro, EventCard.astro, Header.astro, Notice.astro — обычные Astro-компоненты без runtime;
раскрываемые дополнительные сведения — нативный <details> там, где его semantics подходят;
мобильное меню или filter panel — небольшой custom element;
тяжёлый интерактивный календарь или сложный autocomplete — отдельный island, если подтверждена необходимость;
client:only не использовать для критического содержания, поскольку он пропускает server rendering;
hydration, необходимая для доступности видимого control, не должна откладываться до client:visible.
Astro Content Collections подходят для типизированных наборов структурированного контента, поддерживают schema validation и TypeScript types, а build-time collections предназначены для относительно статичных данных и могут генерировать полностью prerendered routes. Это хорошо соответствует каталогу событий, если обновление данных запускает новую сборку сайта.

Система автоматического и ручного контроля соответствия
Контроль должен проверять не намерения и не наличие страницы документации, а фактическую сборку сайта. Он состоит из четырёх контуров.

Профилактические проверки
Механизм	Что предотвращает
Семантические токены как единственный публичный слой	Прямое использование palette и случайное закрепление конкретного значения
Stylelint allow/disallow rules	Raw #hex, rgb(), случайные units, запрещённые properties и !important
Ограниченные import paths	Импорт внутренних primitives и обход публичных компонентов
Public variants, slots и --mod-*-подобные custom properties	Переопределение внутренних селекторов
Component definition of done	Появление компонента без состояний, docs, fixture и tests
Event schema validation	Неконсистентные даты, статусы, credits и обязательные поля
PR templates	Изменение UI без указания accessibility, screenshots и migration impact

Stylelint предоставляет правила для запрещённых и разрешённых комбинаций property/value и property/unit; их можно использовать как основу, но применять по областям, а не запрещать все числовые значения во всём проекте. Например, aspect-ratio, image sizes и технические offsets иногда законно имеют локальные значения. 

Рекомендуемые ограничения:

text
Копировать
В product CSS запрещены:
  raw hex/rgb/hsl цвета
  прямые primitive tokens
  неизвестные CSS custom properties
  !important
  селекторы, заходящие внутрь другого DS-компонента
  локальное копирование .ds-* правил

Разрешены:
  semantic tokens
  documented component custom properties
  локальные значения, явно разрешённые для content geometry

Проверка официальных компонентов не должна требовать оборачивать абсолютно каждый HTML-тег. Нативные <p>, <ul>, <article>, <time> и <address> полезны сами по себе. Контроль нужен для элементов с устойчивым API и риском расхождения: buttons, fields, error states, notices, tags, navigation, event status и cards.

CI-гейты
Каждый pull request должен проходить следующий минимальный pipeline:

Gate	Условие прохождения
Build and types	Astro build, strict TypeScript и content schemas проходят без ошибок
Token compliance	Нет запрещённых raw values, primitive usage и неизвестных variables
Component boundary	Нет запрещённых imports, копий selectors и импортов deprecated-компонентов
Markup	HTML имеет валидную структуру; landmarks, labels, headings и language заданы
Accessibility automation	axe не обнаруживает новых нарушений на component fixtures и критических страницах
Keyboard interactions	Критические flows выполняются Tab, Shift+Tab, Enter, Space, Escape и arrows там, где это соответствует паттерну
Visual regression	Component gallery и page archetypes не имеют необъяснённых screenshot diffs
Performance and delivery	Не превышены бюджеты JS, CSS, изображений и Lighthouse regressions
Documentation	Изменённый public API сопровождается docs, changelog и migration note
Exceptions	Все suppression имеют owner, issue и неистёкшую дату

Playwright официально поддерживает screenshot comparison через toHaveScreenshot() и рекомендует генерировать и сравнивать baselines в одинаковой среде, поскольку результат зависит от ОС, браузера и шрифтов. Baseline-файлы следует коммитить и пересматривать как часть PR, а не обновлять автоматически после ошибки. 

Playwright также позволяет моделировать клавиатурные действия и взаимодействовать с controls через доступные roles и labels. Тесты, обращающиеся к getByRole() и getByLabel(), одновременно проверяют пользовательскую семантику лучше, чем тесты по случайным CSS-классам. 

Для accessibility CI практичен @axe-core/playwright. Официальная документация Playwright подчёркивает, что автоматические проверки находят только часть проблем и должны сочетаться с ручной оценкой и inclusive testing. 

Lighthouse CI может запускаться на каждом изменении, хранить результаты, контролировать performance budgets и блокировать regressions по performance, accessibility, SEO и best practices. Его accessibility score следует считать индикатором регрессии, а не сертификатом WCAG. 

Матрица тестов
Для каждого stable-компонента следует публиковать не общее обещание, а матрицу:

text
Копировать
EventCard
  semantic HTML       pass
  axe default state   pass
  cancelled state     pass
  keyboard            not applicable
  200% zoom           pass
  400% reflow         reviewed

Carbon публично показывает, что некоторые состояния могут быть автоматически проверены, другие не проверены, а keyboard или screen-reader coverage — частичными. Такая честность полезнее декоративного badge «WCAG compliant». 

Целевой baseline для сайта — WCAG 2.2 AA. W3C рекомендует использовать актуальную WCAG 2.2; её соответствие оценивается для полных страниц и responsive-вариантов, а не только изолированных компонентов. 

Периодический аудит production
После каждого значимого релиза и дополнительно по расписанию следует проверять уже развернутый сайт.

Ежемесячный автоматический crawl:

все page archetypes и выборка событий;
axe;
broken links;
отсутствующие title, descriptions и canonical metadata;
пропущенные alt и image credits;
неизвестные цвета и CSS variables в собранных assets;
размер CSS/JS и изображений;
console errors;
service-worker errors, если PWA появится;
наличие deprecated component signatures в HTML/CSS bundles.
Ежеквартальный ручной аудит:

клавиатурный проход по главным сценариям;
VoiceOver/Safari и NVDA/Firefox;
200% zoom и 400% reflow;
forced colors;
качество focus order;
понятность статусов события;
соответствие фотографий бренду;
качество crop, alt и credits;
редакционная последовательность карточек;
проверка email и social cards;
поиск локальных визуальных исключений.
Автоматика может определить отсутствие alt, но не может решить, описывает ли он изображение адекватно контексту; W3C прямо указывает на необходимость человеческой оценки содержательности альтернативного текста. 

Контролируемые исключения
Любое исключение должно быть машиночитаемым:

yaml
Копировать
- id: DS-EX-014
  rule: no-raw-color
  scope: src/pages/festival-map.astro
  value: "#2b6fff"
  reason: "Цвет встроенной сторонней схемы площадки"
  owner: "frontend"
  issue: "PROJECT-312"
  approvedBy: "design-system-owner"
  createdAt: "2026-10-02"
  expiresAt: "2026-11-30"
  risk: "low"
CI должен блокировать:

исключение без owner или issue;
wildcard scope на весь проект;
бессрочное исключение;
suppression accessibility rule без объяснения конкретного defect;
истёкший срок;
расширение области исключения без нового review.
Playwright рекомендует не отключать целиком accessibility rules или большие DOM-поддеревья без необходимости, поскольку это скрывает все нарушения в исключённой области. Для известных проблем предпочтительнее точный fingerprint конкретного нарушения. 

Minimum Viable Design System и развитие после запуска
Обязательные foundations до запуска
Область	Минимальный результат
Архитектура бренда	Зафиксированное отношение зонтичного бренда и «Анонсов», правила написания названий и logo lockup
Цвет	Primitive palette, semantic roles, интерактивные состояния, status colors, contrast matrix
Типографика	Лицензированный шрифт с полной кириллицей; fallback stack; роли display, heading, body, caption, metadata
Spacing и layout	Шкала отступов, content width, gutters, grid, breakpoints и правила vertical rhythm
Shape	Borders, radii и shadows только в реально используемом объёме
Focus	Единый видимый focus ring, правила focus order и skip link
Imagery	Соотношения сторон, crop, минимальное качество, credits, alt и placeholder
Icons	Согласованный набор, размеры, optical alignment, правила decorative/informative
Motion	Duration/easing tokens, разрешённые типы движения, prefers-reduced-motion
Accessibility	WCAG 2.2 AA target, keyboard baseline, zoom/reflow, forced colors, screen-reader matrix
Editorial	Tone, заголовки, даты, время, адреса, цены, статусы, alt и credits
Channels	Минимальные правила web, favicon/PWA assets, email header/footer и social/OG templates

Spectrum формализует motion через purpose, duration и easing tokens, а также подчёркивает предпочтительность нативных controls там, где они обеспечивают ожидаемое доступное поведение. 

Минимальный набор компонентов
Компонент должен появляться в MVDS только при наличии хотя бы двух применений, сложной accessibility semantics или необходимости строго поддерживать бренд.

Каркас и навигация: PageShell, SkipLink, Header, PrimaryNavigation, Breadcrumbs только если иерархия действительно глубока, Footer.

Текст и действия: Link, Button, Icon, Prose, Picture, Tag, Notice.

Формы и фильтрация: FormField, TextInput/SearchInput, Select, Checkbox, Radio, FieldHint, FieldError, ErrorSummary, FilterGroup.

События: EventCard, EventMeta, EventStatus, VenueLink, PriceLabel, DateGroup, EventList, EventDetailHeader.

Не следует включать до запуска без подтверждённого сценария:

Копировать
Modal
Tooltip
Tabs
Carousel
Data table
Complex date picker
Drag-and-drop
Generic dashboard
Skeleton system
Toast notifications
Command palette
Особенно нежелательно создавать generic Card, а затем собирать EventCard через десятки свободных slots и modifiers. Если 90% карточек — события, лучше иметь явный domain API с корректными датами, статусами, площадкой и доступным названием.

Обязательные продуктовые паттерны событий
Лента событий. Группировка по дате, ясное различение даты публикации и даты события, предсказуемая сортировка.

Карточка события. Заголовок, время, площадка, категория, цена/«бесплатно», image и статус. Ссылка карточки должна иметь понятное accessible name; не следует превращать каждую вложенную строку в отдельную конкурирующую ссылку.

Страница события. Канонический заголовок, дата и timezone, адрес, описание, организатор, accessibility information, цена, регистрация, источник и дата обновления.

Поиск и фильтры. Категория, дата/период, география, аудитория и цена только при наличии качественных данных. URL-state, reset, число результатов, no-results и no-JS baseline обязательны.

Статусы. scheduled, postponed, cancelled, sold-out, registration-closed, moved-online. Цвет не должен быть единственным носителем статуса.

Многодневность и повторяемость. Отдельно определить series, occurrence и festival programme. Не дублировать событие вручную, если оно имеет несколько сеансов.

Площадка и организатор. Нормализованные entities, чтобы адрес и название не расходились между событиями.

Нет результатов и ошибки. Полезные альтернативы: снять фильтр, показать соседнюю дату, перейти к категории.

Шаринг и карточки социальных сетей. Один контролируемый шаблон с читаемым заголовком, датой и источником изображения.

Письмо-анонс. Отдельный email template, использующий те же content roles и semantic colors, но не общий web DOM.

Правила внесения изменений
Изменение может быть принято, если оно отвечает на конкретный повторяемый сценарий, не дублирует существующий API, использует semantic tokens, документирует content/accessibility, имеет fixture и тесты и определяет влияние на SemVer.

Новый компонент проходит четыре состояния:

text
Копировать
experimental
  можно использовать только в одном пилотном сценарии

beta
  API может меняться; есть docs и основные tests

stable
  API версионируется; есть accessibility и visual coverage

deprecated
  указан replacement и срок удаления
Необходимые роли можно совмещать:

system owner — принимает архитектурные решения;
design reviewer — проверяет бренд и композицию;
implementation owner — отвечает за API и код;
content/accessibility reviewer — может быть внутренним или внешним специалистом.
Для небольшой команды это могут быть два человека и периодический внешний аудит, а не четыре штатные позиции.

Поэтапное развитие
Этап	Действия	Критерий завершения
До запуска	Foundations, semantic tokens, минимальные компоненты, event patterns, docs, CI, component gallery, критические page screenshots	Нет undocumented raw values; основные flows доступны без мыши; все page archetypes проходят CI
Первые недели production	Исправление реальных проблем, сбор списка локальных отклонений, аудит контента и изображений, стабилизация API	Нет повторяющихся локальных решений; известны фактические пробелы системы
После первого цикла изменений	Удаление лишних variants, формализация deprecation, расширение screen-reader matrix, подготовка 1.0.0	Публичный API стабилен и имеет migration policy
При появлении второго продукта	Анализ реально общих частей; выделение одного package/repository; продуктовые extensions остаются отдельно	Два production-потребителя используют один release без копирования
При развитии каналов	Генерация email/social assets из общих tokens и content schema; channel-specific tests	Каналы единообразны по бренду, но не связаны неподходящим общим DOM
На зрелой стадии	Автоматизация token export в Figma, release dashboard, production conformance crawler	Автоматизация экономит больше времени, чем требует на поддержку

Основные риски, открытые решения и источники
Риски и решения, которые нельзя отложить
Риск или открытый вопрос	Последствие	Рекомендуемое решение
Не определено отношение названий «Полюбить Калининград» и «Анонсы»	Разные logo lockups, заголовки и подписи в каналах	До UI зафиксировать brand architecture и правила совместного написания
Шрифт не проверен на кириллице и лицензирование	Неравномерная типографика, медленная загрузка, юридический риск	Проверить все начертания, ё, кавычки, цифры, валюты, license и webfont subset
Primitive tokens доступны продукту	Компоненты начинают закреплять конкретные оттенки и размеры	Экспортировать продукту только semantic layer
Generic components проектируются раньше domain patterns	Сложный API и множество modifiers	Сначала EventCard/EventStatus/EventDetail, затем извлекать общие части
Figma считается единственным source of truth	Код отстаёт, а production невозможно проверить	Git release manifest; Figma version привязана к релизу
Отдельный репозиторий создаётся слишком рано	Release overhead и синхронизационные PR	Оставить систему в site repo до второго потребителя
Фильтрация зависит от JavaScript	Недоступный baseline и пустой интерфейс при ошибке	Предсобранные архивы и URL-state; JS как enhancement
Непроработаны recurrence и timezone	Неверные даты и дубли событий	Зафиксировать event data model до стабилизации компонентов
Цвет используется для категорий и статусов без текста	Недоступность и неоднозначность	Текст, icon/shape и programmatic status вместе с цветом
Автотесты принимаются за полную WCAG-проверку	Ложное чувство соответствия	Ручные keyboard, zoom, screen-reader и content reviews
Локальные overrides накапливаются незаметно	Визуальный и технический дрейф	Stylelint, import rules, audit bundles и exceptions с expiry
PWA создаётся «потому что можно»	Сложное кеширование и устаревшие события offline	Service worker только после определения реального offline/install сценария
Email пытается использовать web-компоненты напрямую	Нестабильность в почтовых клиентах	Общие tokens/assets/content, но отдельная email implementation
Изображения не имеют прав, credits и редакционного контроля	Юридический и репутационный риск	Обязательные source/credit/license fields и ручной review

Главный архитектурный риск — не недостаток компонентов, а преждевременная универсальность. Система должна начинаться с небольшого стабильного semantic core и нескольких хорошо проверенных event patterns. Расширение должно происходить после повторного использования, а не в ожидании гипотетических продуктов.
