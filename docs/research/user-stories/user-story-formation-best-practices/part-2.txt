Выбор масштаба и вертикальная декомпозиция
Правильный масштаб определяется не количеством текста, story points или числом экранов. Хорошая история должна давать законченное наблюдаемое изменение, быть достаточно небольшой для короткого цикла и допускать самостоятельную проверку. Agile Alliance определяет splitting как разбиение с сохранением измеримой ценности каждого получившегося элемента; Scrum Guide требует, чтобы выбранный Product Backlog item можно было довести до Done в одном Sprint. 

История, вероятно, слишком крупная, если:

в ней больше одного независимого пользовательского результата;
acceptance criteria распадаются на многочисленные группы несвязанных правил;
невозможно определить, что сознательно останется за границами первой версии;
команда не может показать работающий результат раньше окончания большой инициативы;
внутри одновременно присутствуют несколько каналов, ролей, режимов, интеграций и вариантов данных;
её нельзя завершить без последовательных handoff между специализированными командами.
История, вероятно, слишком мелкая, если:

результат виден только разработчику;
пользователь ничего нового не может сделать;
отдельная поставка не имеет смысла;
критерий завершения звучит как «компонент создан», а не «поведение работает»;
элемент существует только потому, что команда разрезала работу по слоям.
Не делите так:

text
Копировать
Создать таблицы
→ реализовать API
→ сверстать экран
→ добавить тесты
Это план реализации одной истории, а не четыре пользовательские истории. Mike Cohn подчёркивает, что хороший срез проходит через столько слоёв стека, сколько необходимо для пользовательской способности. 

Делите по пути поведения.

Большая история:

text
Копировать
Покупатель может оформить заказ с любым способом доставки и оплаты.
Вертикальные срезы:

text
Копировать
Покупатель оформляет заказ с заранее заданной стандартной доставкой
и оплатой одной поддерживаемой картой.

Покупатель выбирает ускоренную доставку.

Покупатель оплачивает через цифровой кошелёк.

Покупатель восстанавливает оформление после отклонённого платежа.
Каждый срез включает интерфейс, правила, данные и интеграцию, но ограничивает сценарий. Cohn приводит аналогичный приём: сначала поддержать один простой путь доставки, а дополнительные варианты вынести в следующие истории. 

Практические оси вертикального разбиения:

Ось	Как использовать
Путь	Сначала основной успешный путь, затем альтернативные и восстановительные пути
Бизнес-правила	Сначала базовое правило, затем скидки, исключения, лимиты и специальные категории
Тип данных	Сначала один распространённый формат или категория, затем остальные
Роль и разрешения	Сначала основной получатель, затем администратор, делегат, наблюдатель
Канал	Сначала основной канал, затем мобильный, email, импорт или API, если каждый даёт законченный результат
Этап жизненного цикла	Создать → просмотреть → изменить → отменить, если каждый этап самостоятелен и полезен
Объём	Один объект → несколько объектов → массовая операция
Качество	Сначала функциональный срез с обязательным базовым качеством, затем отдельное измеримое усиление производительности или устойчивости
Частота и автоматизация	Ручной, но рабочий процесс → полуавтоматический → полностью автоматический
Интеграция	Сначала один поставщик или источник, затем дополнительные
Неопределённость	Короткий spike или experiment для неизвестного, затем delivery story

Humanizing Work рекомендует оценивать получившиеся части как вертикальные end-to-end-срезы, а не архитектурные компоненты. Разбиение рассматривается как командная деятельность: продукт помогает сохранить ценность, разработка выявляет технические варианты, тестирование — правила и исключения. 

Не откладывайте все ошибки «на потом». Happy path first не означает выпуск небезопасного или разрушающего данные продукта. В первый срез обязательно включаются ошибки, без которых основной результат нельзя считать завершённым: двойное списание, потеря введённых данных, несанкционированный доступ, невозможность понять исход операции. Второстепенные варианты можно вынести отдельно.

Используйте walking skeleton. Это минимальная сквозная версия, проходящая через ключевые части пользовательского пути и системы. Она может быть узкой, но должна работать целиком:

text
Копировать
Войти
→ найти один тип объекта
→ выбрать
→ выполнить основное действие
→ увидеть подтверждение
Story Mapping располагает действия пользователя вдоль горизонтальной «backbone», а детали — ниже; первый горизонтальный срез формирует barebones, но работоспособную версию продукта. 

Walking skeleton отличается от набора инфраструктурных заготовок. «Поднять Kubernetes, создать базу и настроить CI» — архитектурный фундамент, но не skeleton пользовательского поведения. Настоящий skeleton должен позволить пройти хотя бы один узкий пользовательский сценарий от начала до результата.

Объединяйте истории, когда по отдельности они не дают результата, будут всегда разрабатываться и проверяться вместе или лишь искусственно разделяют одно правило.

Разделяйте, когда части можно независимо приоритизировать, проверить или отложить либо когда разные группы критериев соответствуют разным результатам.

Удаляйте, когда нет свидетельств потребности, продукт уже обеспечивает результат, изменение не повлияет на наблюдаемое поведение или стоимость поддержки превышает ожидаемую ценность.

Переводите в исследование, когда команда не может ответить, кому нужен результат, какое поведение изменится, насколько проблема распространена или допустима ли предполагаемая технология.

Acceptance criteria и конкретные примеры поведения
Acceptance criteria — это условия результата, при невыполнении которых история не может быть принята. Они не должны повторять формулировку истории и не обязаны перечислять каждую тестовую комбинацию. GOV.UK определяет их как перечень outcomes, подтверждающий, что сервис выполнил свою работу; Mike Cohn рекомендует включать только условия, достаточно важные, чтобы отклонить историю при их невыполнении. 

Рабочая иерархия:

text
Копировать
История:
какой результат становится возможен.

Acceptance criterion:
какое правило должно выполняться.

Конкретный пример:
как правило проявляется при определённых данных.

Тестовый сценарий:
точная процедура проверки, данные и ожидаемые результаты.
Пример:

text
Копировать
История:
Покупатель может сохранить объявление и вернуться к нему позже.

Критерий:
Повторное сохранение того же объявления не создаёт дубликат.

Пример:
Дано: объявление уже находится в подборке.
Когда: покупатель снова выполняет сохранение.
Тогда: в подборке остаётся одна запись,
а продукт сообщает, что объект уже сохранён.

Тесты:
повтор из карточки, повтор из результатов поиска,
два параллельных запроса, повтор после timeout.
Формулируйте критерии через наблюдаемое поведение.

Плохо:

text
Копировать
Использовать Redis для кэширования результатов.
Хорошо:

text
Копировать
Повторное открытие последней подборки при штатной нагрузке
возвращает результат не более чем за установленный продуктом предел.
Первый вариант — решение. Второй — проверяемое требование к качеству. Если Redis уже является обязательным архитектурным ограничением, это следует записать отдельно.

Покрывайте четыре класса поведения:

Основной результат: что происходит при корректном действии.
Значимые границы: лимиты, пустые значения, сроки, роли, состояния объекта.
Ошибки: что пользователь узнаёт и что не должно произойти.
Восстановление: как продолжить, повторить, отменить или вернуть данные.
Для форм, финансовых операций и изменения сохранённых данных WCAG требует идентифицировать ошибки текстом, по возможности предлагать исправление и предоставлять возможность проверки, подтверждения, коррекции или отмены значимых действий. 

Используйте Given–When–Then для неоднозначных правил, но не превращайте всё в Gherkin.

text
Копировать
Дано, что заказ ещё не был отправлен,
когда покупатель отменяет заказ,
тогда заказ получает статус «Отменён»,
товар возвращается в доступный остаток,
а покупатель видит подтверждение возврата.
Given–When–Then описывает контекст, событие и наблюдаемые последствия; BDD возник как способ говорить о поведении, а не как требование использовать конкретный инструмент автоматизации. 

Проводите Example Mapping до разработки, если:

правило допускает разные трактовки;
есть состояния, даты, лимиты или вычисления;
несколько систем участвуют в операции;
ошибки способны привести к потере денег или данных;
история вызывает много уточняющих вопросов;
команда расходится в представлении о «готово».
Example Mapping использует конкретные примеры как основу для acceptance tests и отдельно сохраняет правила, вопросы и обнаруженные будущие истории. 

Проверяйте следующие аспекты только там, где они релевантны, но не забывайте о них системно:

Аспект	Вопросы для criteria и примеров
Устройства	Сохраняется ли результат между desktop и mobile? Что происходит при изменении размера, ориентации или метода ввода?
Каналы	Одинаково ли трактуются статусы в web, приложении, email и поддержке?
Accessibility	Доступен ли результат с клавиатуры и assistive technologies? Объявляются ли ошибки и динамические статусы?
Authentication	Что происходит с намерением пользователя после входа? Как обрабатывается истёкшая сессия?
Authorization	Кто может видеть и изменять объект? Проверяются ли права сервером, а не только интерфейсом?
Пустые состояния	Понимает ли пользователь, почему данных нет и что можно сделать?
Сетевой отказ	Сохранены ли введённые данные? Известен ли фактический статус операции?
Повторные действия	Не создаёт ли повтор дубликаты, двойные списания или повторные уведомления?
Сохранение	Где и как долго хранится результат? Доступен ли он после возвращения и на другом устройстве?
Приватность	Какие данные показываются, передаются, журналируются и удаляются?
Безопасность	Не раскрывает ли ошибка существование аккаунта, секреты или лишние данные?
Существующее поведение	Какие текущие сценарии не должны измениться? Нужны ли регрессионные criteria?

Для операций с внешним побочным эффектом OWASP рекомендует идемпотентность: повтор запроса не должен приводить к повторной оплате, переводу или выпуску ваучера. Для авторизации OWASP рекомендует минимальные привилегии и отказ по умолчанию. 

Accessibility-критерии должны быть специфичными и проверяемыми, но описывать требуемый результат, а не навязывать конкретную реализацию. GOV.UK также рекомендует ссылаться на общие стандарты вместо копирования всех общих правил в каждую историю. 

Не раздувайте карточку до полной системной спецификации. Применяйте трёхуровневое хранение:

text
Копировать
В карточке:
несколько обязательных критериев и ключевых примеров.

По ссылке:
общие доменные правила, дизайн-система, security policy,
стандарты accessibility и контракты интеграций.

В тестовой системе:
полный набор комбинаций, регрессия и автоматизированные проверки.
Если список criteria стал длинным, сначала проверьте, не скрываются ли внутри несколько историй. Если требования повторяются во многих историях, перенесите их в Definition of Done, quality policy, дизайн-систему или общий нормативный документ. Definition of Done описывает общие меры качества инкремента, тогда как acceptance criteria относятся к конкретному результату. 

Различия между историями, epics, job stories, use cases, тестами и технической работой
Артефакт	Что описывает	Когда использовать	Что не следует делать
Пользовательская потребность	Устойчивое затруднение или прогресс, необходимый человеку	Discovery, приоритизация, проверка ценности	Подменять конкретной функцией
User story	Небольшое полезное изменение, пригодное для разговора, поставки и проверки	Планирование ближайшей разработки	Делать полной спецификацией
Epic	Крупную область результата, которую ещё необходимо разделить	Долгосрочный реестр, roadmap, story map	Брать в разработку как единый item
Job story	Ситуацию, мотивацию и желаемый исход	Когда контекст важнее устойчивой роли или persona	Механически заменять слова в user story
Use case	Полный набор путей взаимодействия с системой для достижения цели	Сложные многошаговые процессы, много исключений, регулируемые системы	Считать обязательно тяжёлым документом или одной историей
Acceptance criterion	Обязательное правило принятия конкретной истории	Confirmation, refinement, приёмка	Переписывать историю другими словами
Конкретный пример	Проявление правила при определённых условиях	Example Mapping, BDD, уточнение границ	Использовать один пример как полное правило
Тестовый сценарий	Детальный способ проверки с данными и ожидаемыми результатами	QA, автоматизация, регрессия	Перегружать им карточку истории
Техническая задача	Шаг реализации: миграция, endpoint, индекс, компонент	План разработчиков внутри истории или Sprint Backlog	Выдавать за пользовательский результат
Technical enabler	Самостоятельное техническое изменение, создающее возможность, снижающее риск или поддерживающее качество	Архитектурная работа, платформенные изменения, устранение ограничений	Придумывать ложного пользователя
Нефункциональное требование	Измеримое свойство качества: безопасность, доступность, производительность, надёжность	Общая policy, Definition of Done или criteria конкретной истории	Писать неопределённо: «быстро», «безопасно», «удобно»

User story обычно является небольшим срезом результата. Epic — та же область на более крупном масштабе, ещё не пригодная для ближайшей поставки. Mike Cohn описывает epics как большие истории, которые должны быть разделены до начала реализации. 

Job story особенно полезна, когда различия определяются ситуацией, а не типом человека:

text
Копировать
Когда я открываю продукт после длительного перерыва,
я хочу быстро понять, где остановился,
чтобы продолжить, не восстанавливая контекст вручную.
Intercom описывает Job Stories как способ фиксировать ситуации, мотивации и outcomes. Они не отменяют user stories: job story может использоваться на discovery-уровне, а несколько небольших user stories — реализовывать этот job. 

Use case обычно шире: он охватывает основной сценарий, альтернативы и исключения вокруг одной пользовательской цели. Ivar Jacobson определяет его как все способы использования системы для достижения определённой цели; современный Use-Case 2.0 допускает incremental slices, из которых могут появляться истории. 

Практическая комбинация для сложной системы:

text
Копировать
Use case:
Пациент записывается на приём.

Slices / stories:
Пациент выбирает доступное время в одной клинике.
Пациент переносит существующую запись.
Пациент восстанавливает процесс после истечения резервирования.
Пациент получает доступную альтернативу, если слотов нет.
Technical enabler следует называть прямо:

text
Копировать
Enabler:
Перевести хранение документов на версионируемую модель,
чтобы будущие изменения формата не требовали одновременного
обновления всех потребителей.
Это допустимый Product Backlog item, но не пользовательская история. Scrum Guide допускает в бэклоге всё необходимое для улучшения продукта, включая research, development, maintenance и operational work. 

Нефункциональное требование должно быть измеримо и находиться на правильном уровне. ISO/IEC 25010:2023 предлагает модель характеристик качества, применимую к определению требований, тестовых целей и acceptance criteria. 

text
Копировать
Плохо:
Поиск должен быть быстрым и безопасным.

Лучше:
Для 95% запросов из поддерживаемого региона
первая страница результатов возвращается не позднее 1,5 секунды.

Пользователь может получить только результаты,
доступные его организации и роли.
